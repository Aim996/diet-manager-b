## 4. 0.3 冻结的产品和架构约束

### 4.1 Agent 与后端职责

- Agent 负责理解用户原话，提取意图、主体、已发生状态、食物/饮品/商品、数量、单位、时间、目标和更正方向。
- Agent 提交带原文证据的结构化提案，不是只传原话，也不能直接写数据库。
- 后端负责查真实库存、选择营养来源、执行事务、持久化、幂等、计算进度和冻结回执。
- Agent 只能根据后端真实结果组织自然回复，不能口算库存、营养或进度，不能把聊天记忆当存储。
- 一条用户消息最多产生一次顶层业务调用。一条消息内的多食物、多库存联动和进度更新必须由后端一次编排。

### 4.2 写入安全边界

- 明确否定、未来计划、假设、咨询和纯他人事件对本人账本零写入。
- 私人 Agent 中，已发生且没有明确他人证据的饮食表达默认本人。
- 混合主体只写当前用户明确发生的部分。
- 关键数量缺失时只追问一个最小问题；不能要求用户重说整句话。
- 同一宿主消息/业务请求的技术重放不重复写入。
- 两条不同用户消息即使文字完全相同，也视为两个新事件，不能按文本或短时间窗口去重。
- `committed=false` 时禁止通过便签、记忆、文件或第二数据库兜底后声称成功。

### 4.3 数据与事务

- SQLite 是唯一权威业务账本；聊天上下文不是权威数据。
- 保留 0.2.2 的事件追加、纠正事件、幂等记录、效果 outbox、最终器、备份和恢复原则。
- 多项目餐食的事实写入必须原子；不能只写一半食物。
- 库存不足不改变“用户实际吃了多少”的事实。存在多少扣多少，不允许负库存；未覆盖部分如实说明。
- 更正是对目标事实的版本化修改，撤销和恢复保留历史，不物理删除业务证据。
- 任何数据库迁移必须向前兼容、可在备份副本上验证，并能拒绝未知/损坏数据库；不得修改 migration v1 的历史 SQL 或校验值。

### 4.4 营养来源

固定优先级：

1. 用户为具体商品保存的本地包装营养表；
2. Skill 本地通用营养库；
3. 带来源、地址、检索时间、匹配依据和置信状态的互联网结果；
4. 明确标注“营养来源：估算数据”的估算；
5. 无法形成合理依据时才是未知。

营养匹配与库存匹配相互独立：没有库存仍可匹配营养；有库存但无营养表必须继续寻找来源。采用的联网结果在许可允许时写入营养库复用；不得缓存禁止再分发的数据。营养最终未知也不能阻止明确发生的饮食事实落库。

### 4.5 库存双单位

- 同一批次同时保留包装数量单位和基础净含量单位，例如 `2 盒 × 250 ml/盒 = 500 ml`。
- 可以按盒、包、片等包装单位消费，也可以在换算关系确定时按 ml 或 g 消费。
- 部分消费后允许显示 `1 盒 + 150 ml` 这类真实余额，不能伪装成整数盒。
- 没有单包装规格时只能按包装单位管理，不能猜测基础量。
- g 与 ml 之间没有可靠密度时禁止自动换算。
- 无库存匹配时回执使用“未匹配有效库存”。

### 4.6 目标和进度

- 推荐目标在用户确认前永远是 `pending`，不得参与正式进度计算。
- 建档后至少推荐热量、蛋白、脂肪、碳水和纤维五项；资料足够时同时推荐饮水。
- 用户确认或主动设置后才创建正式目标版本；修改目标关闭旧版本并创建新版本。
- 固定六项顺序和展示名：热量、蛋白、脂肪、碳水、纤维、饮水；进度 UI 第二项只能写“蛋白”。
- 每个终态成功的饮食、含营养饮品或白水写入，回复末尾必须有且只有一个完整六项进度块。
- 多食物同一请求合并成一个进度块；影响累计的更正、撤销、恢复按受影响日期返回冻结进度。
- 无正式目标仍必须返回六项进度反馈，并显示“目标未配置，进度条不可用。”；不得生成百分比或假目标。
- 正式进度条正好 10 格，只使用 `█` 和 `░`；未知不能当零，饮水不完整时用已知下界 `≥`。
- 百分比、填充格、本轮增量和跨日结果全部由后端最终器冻结；Agent 和适配器只渲染。
- 进度块必须位于成功回执最后；其后不追加表扬、警告、建议或下一餐推荐。

### 4.7 回执

正文短而真实，推荐形态：

```text
已记录晚饭：全麦面包 2 片、苹果 1 个。面包库存仅 1 片，已扣减，当前库存 0；苹果未匹配有效库存。
```

随后是强制六项进度块。详细批次、换算过程、营养检索、来源和审计字段保留在结构化结果中，用户查询详情时再展开。不能为了简短省掉未知或失败事实，也不能在正文重复完整进度数据。

## 7. 公共接口目标

### 7.1 Agent Command v2

v2 仍禁止 Agent 提交数据根和宿主权威字段：

```ts
export interface AgentCommandV2 {
  readonly schema_version: "diet-manager/agent-command/v2";
  readonly action: DietManagerAction;
  readonly source_text: string;
  readonly semantic_proposal?: SemanticProposalV2;
}
```

`HostExecutionContextV1` 继续由适配器/CLI 构造并与模型参数分离，至少包含可信 `operation_id/source_message_id/conversation_id/received_at/timezone`。模型提交这些字段必须被精确 Schema 拒绝。

### 7.2 结构化语义提案

`SemanticProposalV2` 是按 `kind` 区分的 union：

```ts
export type SemanticProposalV2 =
  | MealProposalV2
  | WaterProposalV2
  | InventoryProposalV2
  | ProfileProposalV2
  | GoalProposalV2
  | RecordMutationProposalV2;
```

共同约束：

- 原文逐字保留；
- 用户明确说出的事实带 `evidence_span`；
- 默认值带枚举化 `basis`，不能伪造成原文；
- 未知使用 `unknown/null`，不能使用 0 代替；
- 规范化名称只是 hint，商品身份、库存批次和记录目标仍由后端确定；
- 更正、撤销和恢复只能提交用户描述与筛选证据，Agent 不能提供权威数据库 ID；
- 每层精确拒绝未知字段、getter、自定义原型、非有限数和超界数组。

最低提案字段：

```ts
interface MealProposalV2 {
  readonly kind: "meal";
  readonly subject: SubjectEvidence;
  readonly occurrence: "completed";
  readonly meal_slot: "breakfast" | "lunch" | "dinner" | "snack" | "unknown";
  readonly items: readonly IntakeItemEvidence[];
  readonly occurred_at: TimeEvidence;
}

interface WaterProposalV2 {
  readonly kind: "water";
  readonly subject: SubjectEvidence;
  readonly amount: ExactAmountEvidence | UnknownAmount;
  readonly occurred_at: TimeEvidence;
}

interface InventoryProposalV2 {
  readonly kind: "inventory";
  readonly product: ProductEvidence;
  readonly package_amount: ExactAmountEvidence;
  readonly per_package_content: ExactAmountEvidence | null;
  readonly location: EvidenceValue<string> | null;
  readonly expires_at: TimeEvidence | null;
  readonly price: PriceEvidence | null;
}

interface GoalProposalV2 {
  readonly kind: "goal";
  readonly operation: "confirm" | "update" | "clear";
  readonly values: Readonly<Partial<Record<GoalField, EvidenceValue<number> | null>>>;
}
```

### 7.3 冻结结果

成功的摄入类结果必须结构化包含：

```ts
interface FrozenIngestionOutcomeV2 {
  readonly status: "committed" | "committed_with_issues";
  readonly committed: true;
  readonly operation_id: string;
  readonly record_ids: readonly string[];
  readonly receipt: FrozenReceiptV1;
  readonly progress: readonly FrozenDateProgressV1[];
}
```

同一幂等请求必须返回第一次冻结的 `receipt + progress`；即使当天后来又吃了东西，也不得用新累计重建旧回执。

## 8. 开发方法和每批统一门禁

### 8.1 TDD 循环

每个行为变更固定执行：

1. 在最靠近真实边界的测试中写一个最小失败用例。
2. 运行该用例，确认失败原因正是缺少目标行为，不是 fixture、路径或语法错误。
3. 写最小生产实现，不顺手扩范围。
4. 运行聚焦测试并看到绿色。
5. 运行相邻层测试和 TypeScript 构建。
6. 必要时重构，保持绿色。
7. 更新 `已知问题.md` 的状态和证据。
8. `git diff --check`，只暂存本批文件，提交一个可审查结果。

测试先通过再写测试，不算 TDD。发现缺陷后必须先建立能复现缺陷的红灯。

### 8.2 测试命令

先通过 Codex 工作区依赖工具定位 Node 24，不要硬编码历史临时路径。如果工作区已经把正确 Node 放入 PATH，可以使用下面的命令；如果没有，就把依赖工具本次返回的 Node 绝对路径赋给同一个任务专用变量：

```powershell
$DietNode = (Get-Command node -ErrorAction Stop).Source
& $DietNode --version
& $DietNode .\node_modules\vitest\vitest.mjs run tests\contracts\agent-command-v2.test.ts --maxWorkers=1 --minWorkers=1
& $DietNode .\node_modules\typescript\bin\tsc -p tsconfig.json
```

新工作树没有依赖时，先确认 `pnpm-lock.yaml` 未变化。需要联网安装依赖必须请求批准并使用冻结锁文件；不得删除别的工作树现有 `node_modules`，不得提交 Junction 或依赖目录。

### 8.3 每批完成门

- 聚焦红灯真实出现并保留结果摘要；
- 聚焦 GREEN 全绿；
- 相邻 contract/application/domain/repository 测试全绿；
- TypeScript 构建退出码 0；
- 新增迁移时，空库、0.2.2 数据库升级、重复启动和故障注入均通过；
- `git diff --check` 通过；
- 没有秘密、数据库、构建产物或用户无关改动进入暂存区；
- 提交信息只描述当前批次；
- 未达到门禁时不得打包、部署或汇报该批完成。

完整回归成本高，可以在每个独立里程碑末尾运行一次；发布前必须运行一次全新完整回归。历史测试计数只能参考，不能代替当前结果。

## 11. 发现问题后的统一处理流程

### 11.1 先分类，不边测边猜修复

按最靠近根因的层级归类：

```text
AGENT_ROUTE          模型未选择 Skill/动作
SEMANTIC_PROPOSAL    Agent 提案丢字段、串项目或证据错误
SEMANTIC_GATE        后端验证误拒绝或误放行
APPLICATION          编排、事务、幂等或状态机错误
INVENTORY            商品匹配、单位、批次或扣减错误
NUTRITION            来源选择、缓存、快照或估算错误
GOAL_PROGRESS        目标版本、累计、舍入、未知或冻结错误
MUTATION_QUERY       更正、撤销、恢复或读模型错误
RECEIPT              回复与结构化结果不一致
ADAPTER_PACKAGE      OpenClaw/CLI、Skill 路径、安装或包内容错误
HOST_ENVIRONMENT     Gateway、模型、容器、网络或权限问题
```

### 11.2 每个缺陷必须记录的证据

在 `已知问题.md` 追加或更新：

- 唯一编号、发现日期、严重度和状态；
- 完整自然输入与必要前置状态；
- 期望行为；
- Agent 回复；
- 脱敏后的工具请求/结果；
- SQLite 前后计数和相关行；
- 最小稳定复现；
- 初步分类；
- 根因证据，不能只写猜测；
- 对应红灯测试名、修复提交和复验结果；
- 是否影响发布门。

### 11.3 什么时候自行处理，什么时候停下询问

可以自行处理：

- 已冻结规则下的明确实现缺陷；
- 测试、类型、命名和内部文件拆分；
- 不改变外部契约的性能或可维护性修复；
- 环境 fixture、构建脚本和可复现安装问题。

必须停下询问用户：

- 需要改变已确认产品行为、回执格式或进度规则；
- 需要重命名插件/Skill/数据库或破坏 v1 兼容；
- 需要删除、清空、重置、迁移真实用户数据；
- 需要新增付费/有许可证限制的外部营养源；
- 需要连接非专用测试环境、公开发布、推送 GitHub 或创建 Release；
- 两份高优先级 0.3 规范无法同时满足。

### 11.4 修复纪律

1. 保留失败现场。
2. 写最小红灯复现。
3. 运行并确认正确失败。
4. 定位根因后修最小层，不用扩大正则或删除安全守卫掩盖问题。
5. 增加相反安全用例，尤其是他人、否定、未来、重复、跨会话、并发和数据迁移。
6. 跑聚焦、相邻和必要全量回归。
7. 更新问题状态，但不删除历史。
8. 真实环境失败只在本地修好一个有用户价值的批次后统一重新部署，避免反复污染五环境。
