# 库存与营养

## 何时读取

当请求包含食品入库、包装规格、库存扣减/不足、营养来源、饮品或营养未知时读取。

## 入库提案与双单位

`inventory` 提案保留用户明确说出的商品、包装数量、单包装内容量、位置、到期表达和价格。包装单位与基础内容单位必须分开：两盒、每盒 250ml 是包装数量 `2 盒` 和单包装内容 `250 ml`；总量、批次和余额由后端计算。

没有明确规格时允许按盒/袋/瓶管理，但不能猜每包装容量；没有确认密度或商品规格时不能在 `g` 与 `ml` 间换算。Agent 不生成商品、批次或库存流水 ID。

到期表达由后端使用宿主提供的可信接收时间和 `Asia/Shanghai` 时区解析；当前只接受明确日期、明天/后天和“下周/下星期 + 星期”。无法安全解析时只追问到期日，不把原文猜成日期。明确总价作为原批次证据原样保留，Agent 不自行拆算单价；库存查询只能展示后端返回的到期时间、位置和价格。

## 消费与库存

Agent 只提交用户实际吃/喝的事实，不先根据聊天上下文口算库存。后端高可信匹配后按先进先出扣减；无库存、库存不足、候选歧义或单位无法可靠换算时，仍保留已经发生的摄入事实，并在结构化结果中说明实际扣减和缺口。

库存不足不能缩小用户陈述的消费量：吃了 2 片而库存只有 1 片，营养仍按实际 2 片处理，库存最多扣到 0。未匹配库存不能被说成已经扣减。

## 营养来源

营养匹配与库存匹配是独立链路。优先级固定为：

1. 用户确认的具体商品包装营养表；
2. Skill 本地通用营养库；
3. 带来源、时间、匹配依据和置信状态的互联网结果；
4. 明确标注的估算数据。

本地商品标签绑定商品和规格版本，不能被通用数据静默覆盖。联网失败或营养未知不阻止已发生事实；未知不能写成 0。Agent 只使用后端返回的营养数值和来源标签，不自行搜索后拼进成功回执，也不把估算说成包装实测。

牛奶、豆浆、果汁和其他含营养饮品同时参与营养及已知水分；白水使用饮水动作。白水与饮品水分不得重复计算，饮品水分未知时由后端返回已知下界。

## 回执边界

普通正文只说明已记录项目与关键库存结果。详细批次、换算、来源和审计留在结构化结果；正文后的六项进度直接使用后端冻结内容，不重复展开营养累计。
