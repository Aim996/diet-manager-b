# 自然语言边界

## 何时读取

当原话包含省略主体、他人、混合主体、否定、假设、未来、数量缺失、多个项目或弱模型不确定性时读取。

## 先判断是否属于本人已发生事实

| 原话类型 | 业务行为 |
|---|---|
| “我刚吃了……” | 本人已发生，形成一次写入请求 |
| 私人 Agent 中省略“我”的“中午吃了……” | 可使用当前用户默认主体，但默认不能伪造成原文证据 |
| “我没吃那个蛋糕” | 否定，零调用、零写入 |
| “明天准备喝牛奶” | 未来计划，零饮食调用；只有明确要求提醒时才进入独立提醒能力 |
| “如果晚上吃两个鸡蛋会怎样” | 假设/咨询，零调用 |
| “我妈吃了两个鸡蛋” | 纯他人事件，当前用户零调用 |
| “我和老婆各吃了一个鸡蛋” | 一次请求中只提取本人 1 个，并标记他人片段 |
| “本来想吃蛋糕但没吃，后来吃了一个苹果” | 一次请求只保留本人已吃的苹果 |

混合主体不能整句丢弃，也不能把他人份额写进当前用户。系统没有明确家庭成员账户能力时，不为他人新建档案。

## 保持项目对应关系

一条原话包含多种食物或含营养饮品时，保持项目顺序，并把数量、单位和修饰词绑定到各自项目。例如“一碗米饭、两个煮鸡蛋、300 毫升无糖豆浆”是同一餐次的三个项目，只产生一次顶层调用；“煮”和“无糖”不能串位。豆浆、牛奶、果汁等饮品属于摄入项目，白水才使用 `record_water`。

## 缺失与冲突

能由明确原文、私人 Agent 主体边界或确定单位换算得到的字段直接提交。数量完全不明时在 v2 提案中使用 `unknown`，让后端保存待补候选并返回最短问题；不要为了通过 Schema 猜数字。

后端返回 `needs_clarification` 后只问 `question` 指定的一个缺口，保留已经明确的项目。用户回答“不知道”时允许后端按未知结束；用户说“不记了”时取消候选。协议失败不等于可连续尝试多个猜测。

受限模型只确定鸡胸肉数量未知、一碗饭明确时，安全提案是：

```json
{
  "schema_version": "diet-manager/agent-command/v2",
  "action": "record_meal",
  "source_text": "中午吃了点鸡胸肉和一碗饭。",
  "semantic_proposal": {
    "kind": "meal",
    "subject": {
      "kind": "self",
      "basis": "private_agent_default",
      "evidence_span": null,
      "explicit_other_spans": []
    },
    "occurrence": "completed",
    "meal_slot": "lunch",
    "items": [
      {
        "raw_name": "鸡胸肉",
        "normalized_hint": "chicken breast",
        "amount": { "kind": "unknown" }
      },
      {
        "raw_name": "饭",
        "normalized_hint": "rice",
        "amount": {
          "kind": "exact",
          "value": 1,
          "unit": "碗",
          "evidence_span": "一碗饭"
        }
      }
    ],
    "occurred_at": {
      "kind": "source_text",
      "evidence_span": "中午"
    }
  }
}
```

## 零调用回复

非事件、纯他人事件或无工具环境都要准确说明没有保存。可以回答咨询或整理待提交内容，但不能说“已记录”“已扣库存”或“进度已更新”，也不能改用聊天记忆兜底。
