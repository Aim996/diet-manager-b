## 使用方式

每个场景固定描述五件事：

1. 普通用户会怎么说。
2. Agent 应该理解出什么业务含义。
3. 后端应该查询和改变哪些真实数据。
4. 用户最终应该看到什么回执。
5. 哪些行为属于验收失败。

这里描述的是开发目标，不代表 0.3 当前已经实现。

## AC-001：已发生的单项饮食记录与库存联动

### 用户原话

> 我刚吃了一个鸡蛋。

用户不需要说“调用饮食记录”“扣减库存”或任何工具名称。

### Agent 的计划行为

Agent 应从原话形成一个关联业务请求：

| 含义 | 计划识别结果 |
|---|---|
| 主体 | 当前用户本人 |
| 状态 | 已经发生 |
| 业务方向 | 记录饮食 |
| 食物 | 鸡蛋 |
| 数量 | 1 |
| 单位 | 个 |
| 时间 | 以“刚”结合用户时区解析出的当前近似时间 |
| 附带意图 | 自动尝试库存联动、营养补充和今日进度更新 |

Agent 只提交一次业务请求。它不能先调用饮食记录，再单独调用库存，又重复调用进度查询。

### 后端的计划行为

后端按以下顺序在同一次业务编排中执行：

1. 校验请求结构和幂等键，确认这条消息没有被重复提交。
2. 查询鸡蛋库存及可用批次。
3. 如果存在高可信匹配，按先进先出扣减一个；如果没有库存，不扣减但继续记录饮食。
4. 写入一条“鸡蛋，一个”的饮食事实。
5. 按营养来源优先级生成营养快照。有库存但库存商品缺少营养表时，继续查询商品本地营养表、Skill 通用营养库和互联网来源；采纳的搜索结果保存来源与匹配依据，并沉淀到营养库供后续复用。仍无法取得时才标记未知或待补充，不撤销饮食事实。
6. 重新计算当天累计和已经确认的正式目标进度。
7. 返回一次结构化真实回执。

### 数据变化分支

| 实际状态 | 饮食事实 | 库存 | 营养 | 今日进度 |
|---|---|---|---|---|
| 有鸡蛋库存且有营养来源 | 新增一条 | 扣减一个 | 保存来源快照 | 重新计算 |
| 没有鸡蛋库存但有营养来源 | 新增一条 | 不变化 | 保存来源快照 | 重新计算 |
| 有库存但库存商品营养未知 | 新增一条 | 扣减一个 | 继续检索；采纳结果留档并入营养库，最终无结果才标记未知 | 按最终已知状态重新计算 |
| 同一请求被重放 | 不新增 | 不重复扣减 | 不重复生成 | 返回原提交结果 |
| 用户用新消息再次说“我吃了一个鸡蛋” | 再新增一条 | 再按真实库存扣减 | 为新事实生成快照 | 按总共两次食用重新计算 |

“同一请求”指同一个稳定用户消息身份或同一个业务请求身份因超时、网络重试、Agent 重放而再次到达，不指文字内容相同。系统禁止用原话哈希、食物数量组合或短时间窗口判断重复。

### 用户应该看到的回执

有库存和营养来源时，简洁回执类似：

> 已记录：鸡蛋 1 个。库存已扣 1 个；营养按已匹配来源计算。

没有库存时，目标回执类似：

> 已记录：鸡蛋 1 个。未匹配有效库存；营养按已匹配来源计算。

回执中的数字必须来自后端实际结果；Agent 可以调整说法，但不能自行补数字或宣布未发生的库存变化。以上正文后必须紧接后端冻结的完整六项进度块，营养增量和今日累计不在正文重复展开。

### 验收通过条件

- 普通原话一次成功进入正确业务方向。
- 同一用户消息最多产生一次顶层业务调用。
- 同一消息的技术重试不重复写入；新的用户消息即使原话完全相同，也作为新的真实事件处理。
- 有库存时只扣一次，没有库存时仍能记录饮食。
- 库存商品缺营养时自动继续匹配；采用的联网结果有检索记录并可供后续复用，最终未知时保留饮食事实并明确说明未知。
- 回执中的记录、库存、营养和进度与数据库实际状态一致。
- 只要本次饮食事实最终成功提交，回执末尾必须有且只有一个完整六项进度块；无目标时显示不可用提示和六项累计或未知。
- 在新会话查询时仍能看到本次记录和正确库存余额。

### 验收失败条件

- 要求用户改说固定命令或提供工具名称。
- 同一消息触发多次业务调用或重复写入。
- 因为两条新消息内容相同，就错误吞掉第二次真实饮食。
- 没有库存时拒绝记录已经吃过的鸡蛋。
- 没有真实提交却回复“已经记好了”。
- Agent 依据聊天上下文口算库存或进度。
- 把估算营养说成精确值，或隐藏营养来源未知。
- 饮食已经成功落库，但回执省略六项进度块，或为一个鸡蛋重复输出多个进度块。

## AC-002：一顿包含多种食物和饮品

### 用户原话

> 中午吃了一碗米饭、两个煮鸡蛋，还喝了 300 毫升无糖豆浆。

### Agent 的计划行为

Agent 应保持同一顿饭中项目、数量、单位和修饰词的对应关系：

| 项目 | 数量与单位 | 修饰 | 类型 |
|---|---|---|---|
| 米饭 | 1 碗 | 无 | 食物 |
| 鸡蛋 | 2 个 | 煮 | 食物 |
| 豆浆 | 300 毫升 | 无糖 | 饮品 |

- 主体是当前用户本人，状态是已经发生，时间解析为用户时区的当天中午。
- 三个项目属于同一餐次，Agent 只提交一个包含三个有序项目的业务请求。
- “无糖”和“煮”必须跟随各自项目，不能错误地套到整顿饭或其他食物上。
- 饮品是正常摄入项目，不能因液态被判为“非食物”而忽略。豆浆等含热量饮品同时参与热量、宏量营养和已知水分汇总；白水参与饮水汇总。

### 后端的计划行为

1. 先校验三个项目都能形成合法事实；存在关键结构缺口时不做部分提交，而进入 AC-003 的待补充流程。
2. 结构完整后，在同一个数据库事务中写入一个餐次和三个饮食项目。
3. 分别尝试匹配米饭、鸡蛋和豆浆库存；匹配成功的项目按规则扣减，未匹配项目不阻止整顿饭落库。
4. 分别保存营养来源和快照；饮品与固体食物走同一来源优先级。某一项营养未知时，其他已知项目仍正常计算。
5. 汇总本餐已知营养，并重新计算今日进度。
6. 返回一次包含逐项结果和合计结果的回执。

### 目标回执

> 已记录今天中午这顿：1 碗米饭、2 个煮鸡蛋和 300 毫升无糖豆浆。鸡蛋库存已扣 2 个；米饭和豆浆没有匹配库存，所以未扣。已知部分合计约 500 千卡、蛋白质约 25 克，今天累计和剩余目标已更新。

实际数字、库存变化和未知项必须以后端回执为准。

### 验收通过条件

- 三个项目、数量、单位和修饰词没有串位或遗漏。
- 一条消息只有一次顶层业务调用和一次真实提交。
- 同一餐次的事实不会出现只写入一半的中间状态。
- 库存和营养按项目分别返回，不用一个项目的失败覆盖整顿饭。
- 豆浆等饮品被保存为摄入事实并计入相应营养和水分，不会被当作非食物丢弃。
- 本餐合计等于逐项已知营养之和，未知项被明确排除或标记。
- 三个项目成功提交后，最终回执末尾只输出一次合并后的完整六项进度块。

### 验收失败条件

- Agent 为三种食物分别重复调用，或对同一项目调用多次。
- 把“两个”绑定到米饭、把“300 毫升”绑定到鸡蛋，或丢失“无糖”。
- 一个项目库存不存在导致整顿饭完全失败。
- 把饮品排除在摄入记录之外，或只计水分而漏掉其已知热量和营养。
- 只回复一个合计数字，无法核查每个项目实际记录结果。
- 部分写入后回复整顿饭全部成功。
- 为米饭、鸡蛋和豆浆分别输出三个进度块，或完全不输出进度块。

## AC-003：信息不完整时的最短追问

### 用户原话

> 中午吃了点鸡胸肉和一碗饭。

### Agent 的计划行为

Agent 应识别：米饭有“1 碗”，鸡胸肉数量不明确。鸡胸肉数量会显著影响营养和库存，因此不能静默编造，但也不能要求用户重说整顿饭。

计划追问：

> 鸡胸肉大概吃了多少？可以说克数，也可以说几块；一碗饭我已经保留，不用重说。

### 待补充行为

1. 后端或会话状态保存本次未提交候选：当天中午、鸡胸肉数量待补、一碗米饭已完整。
2. 用户只回答“差不多 150 克”时，Agent 将答案补到鸡胸肉，不把它误绑定给米饭。
3. 补充完成后提交一次完整关联请求，执行逻辑与 AC-002 相同。
4. 用户回答“不知道”时，不继续循环追问；允许记录“鸡胸肉，数量未知”和“一碗米饭”，鸡胸肉不做库存扣减，营养标记为无法可靠计算。
5. 用户说“算了，不记了”时取消整个待补充候选，确保零写入。

### 可以自动处理而不追问的情况

| 表达 | 计划处理 |
|---|---|
| 一杯 250 毫升牛奶 | 使用明确的 250 毫升，不追问 |
| 两个鸡蛋 | 使用 2 个，不追问重量 |
| 刚才吃了一根香蕉 | 用用户时区的当前近似时间，不追问分钟 |
| 包装写着每盒 200 克，我吃了一盒 | 使用已明确的规格换算为 200 克 |

### 必须追问的情况

- “吃了鸡肉”但数量完全缺失，且用户需要营养或库存联动。
- “喝了一杯”但不知道是什么饮品。
- 同一句话存在两个合理主体，无法确认记录给谁。
- “改一下刚才那个”但存在多个同样合理的更正对象。

### 验收通过条件

- 每轮最多提出一个最关键、能直接回答的问题。
- 已经明确的内容被保留，用户无需重新叙述。
- 简短补充能正确合并到原候选，且最终只提交一次。
- 用户不知道或取消时有明确结束路径，不无限追问。
- 待补充期间不提前写入、不扣库存、不宣布成功。

### 验收失败条件

- 一次列出多个表单式问题，要求用户逐项填字段。
- 用户补充“150 克”后仍说不知道是哪种食物。
- 每次追问都丢失前文，要求重新说完整餐食。
- 尚未补全就先写入米饭，再补写鸡胸肉，造成一条消息多次落库。
- 用户取消后仍留下部分饮食或库存流水。

## AC-004：食品入库、批次和先进先出

### 用户原话

> 刚买了两盒纯牛奶，每盒 250 毫升，保质期到下周五，放冰箱冷藏层，一共 12 块钱。

### Agent 的计划行为

Agent 应一次提取并提交：

| 含义 | 计划识别结果 |
|---|---|
| 业务方向 | 食品入库 |
| 商品 | 纯牛奶 |
| 数量 | 2 盒 |
| 包装计数单位 | 盒 |
| 单包装净含量 | 250 毫升/盒 |
| 基础总量 | 500 毫升，可由确定规格计算 |
| 到期时间 | 结合用户时区解析“下周五”为具体日期 |
| 存放位置 | 冰箱冷藏层 |
| 价格 | 总价 12 元；可派生每盒 6 元，但保留总价来源 |

### 后端的计划行为

1. 校验商品、数量和规格；将相对日期解析结果回显在回执中。
2. 查找高可信商品实体；没有时创建“纯牛奶”商品，不与酸奶、调制乳等相似名称合并。
3. 创建独立库存批次，同时保存包装余额 `2 盒`、基础量余额 `500 毫升`、每盒换算关系、入库时间、到期时间、位置和价格来源。
4. 后续消费同一商品时，默认优先扣减更早入库的可用批次；“喝了 1 盒”扣 1 盒和 250 毫升，“喝了 100 毫升”扣 100 毫升并把包装余额表达为 1 盒加 150 毫升，而不是伪造整数盒。
5. 缺少每盒净含量时可按盒管理，但不能按毫升扣减；重量和体积之间没有可靠密度时禁止自动换算。
6. 返回新增批次和当前包装量、基础总量，不用 Agent 自己相加。

### 目标回执

> 已入库：纯牛奶 2 盒，每盒 250 毫升，共 500 毫升；放在冰箱冷藏层。到期日按你的时区记为 8 月 28 日，总价 12 元。当前可用库存为 2 盒。

日期示例必须使用后端实际解析结果，不能照抄本文示例日期。

### 验收通过条件

- 数量、单盒规格、总量、到期日、位置和总价均落在同一批次。
- 相对日期被解析成具体日期并回显，用户可以立即发现误解。
- 同一商品再次购买会形成新批次，不覆盖旧批次的到期日和价格。
- 重放同一请求不重复增加库存。
- 查询库存时可看到总量，也能展开查看各批次来源。
- 后续既能按盒消费，也能按毫升消费，两个余额始终由同一批次换算关系保持一致。

### 验收失败条件

- 同一句话触发多次入库，出现重复批次。
- 把“两盒”误成“两毫升”或忽略每盒规格。
- 只保留总量，导致后续无法按盒消费。
- 只保留盒数，导致用户按毫升饮用时无法扣减；或无规格时擅自猜测盒与毫升、克与毫升之间的换算。
- 新入库覆盖旧批次，丢失历史价格或到期日。
- Agent 回复入库成功，但数据库没有对应库存流水。

## AC-005：消费记录与库存不足

### 前置状态

库存中只有 1 片可用的全麦面包，苹果没有库存记录。

### 用户原话

> 晚饭吃了两片全麦面包和一个苹果。

### Agent 的计划行为

- 理解为已经发生的一顿晚饭，包含全麦面包 2 片和苹果 1 个。
- 只提交一次关联业务请求，不先询问库存够不够，也不把用户说的事实改成计划。

### 后端的计划行为

1. 在同一事务中写入晚饭餐次、2 片全麦面包和 1 个苹果的饮食事实。
2. 全麦面包库存只有 1 片时，扣至 0，并记录还有 1 片没有库存来源。
3. 苹果无库存时不扣减，记录“未匹配有效库存”。
4. 两种食物都按营养来源规则生成快照并更新今日进度。
5. 回执明确区分实际食用数量、实际扣减数量和库存缺口。

### 目标回执

> 已记录晚饭：全麦面包 2 片、苹果 1 个。面包库存仅 1 片，已扣减，当前库存 0；苹果未匹配有效库存。

正文到此结束，随后强制输出一次完整六项进度块。营养、库存缺口和今日累计由进度块及结构化结果表达，不在正文重复铺陈。

### 验收通过条件

- 饮食数量以用户实际表达为准，不被库存余额缩减。
- 库存只扣实际存在的 1 片，不出现负库存或虚构苹果库存。
- 营养按吃了 2 片面包计算，而不是按库存扣了 1 片计算。
- 一次提交后，饮食事实、库存流水和回执相互一致。
- 正文保持简洁，且末尾仍有且只有一个后端冻结的六项进度块。

### 验收失败条件

- 因库存不足拒绝记录晚饭。
- 库存扣成负数，或谎称完整扣了 2 片。
- 只按库存中的 1 片计算营养，改变用户陈述的消费事实。
- 把库存不足误报成食物不存在或用户没有说数量。
- 用冗长正文重复进度块中的营养与累计信息，或为了简短而省略强制进度块。

## AC-006：更正刚才的饮食记录

### 前置状态

最近一条饮食记录为“刚才吃了 1 个鸡蛋”，库存已扣 1 个，营养和进度已更新。

### 用户原话

> 刚才鸡蛋不是一个，是两个。

### Agent 的计划行为

- 识别为更正最近的鸡蛋记录，不是新增一条“2 个鸡蛋”的饮食。
- 从否定和替换表达中提取：原数量 1，新数量 2。
- 最近记录能唯一匹配时直接提交更正；存在多个同样合理的鸡蛋记录时，只追问时间或餐次这一个区分信息。

### 后端的计划行为

1. 找到目标事实及当前版本，验证它仍可更正。
2. 新建数量为 2 的事实版本，并把旧版本保留为历史。
3. 计算差量为增加 1 个鸡蛋，而不是再次增加 2 个。
4. 尝试再扣 1 个库存；库存不足时仍完成事实更正，并记录库存缺口。
5. 重新生成或调整营养快照，重算今日进度。
6. 返回更正前、更正后、库存差量和进度差量。

### 目标回执

> 已把刚才的鸡蛋从 1 个改为 2 个，不是新增一条记录。库存又扣了 1 个；营养和今日进度已按总共 2 个鸡蛋重新计算。

### 验收通过条件

- 更正后只有一个有效饮食事实，数量为 2；旧版本仍可审计。
- 库存总共只扣 2 个，不是先扣 1 个再错误扣 2 个。
- 营养和进度按更正后的总量重算。
- 同一更正请求重放不会再次增加数量或扣库存。

### 验收失败条件

- 新增第二条“2 个鸡蛋”，导致有效总量变成 3 个。
- 删除旧事实而不保留更正历史。
- 更正成功但库存、营养或进度仍停留在旧数量。
- 找不到目标时返回笼统“动作冲突”，不给可理解的区分问题。

## AC-007：撤销与恢复

### 前置状态

AC-006 的更正已经完成，当前有效数量为 2 个鸡蛋。

### 用户原话一

> 把刚才那个修改撤销。

### 撤销的计划行为

1. Agent 将“刚才那个修改”唯一关联到 AC-006 的数量更正。
2. 后端新增撤销事件，把有效版本恢复为 1 个鸡蛋。
3. 退回更正产生的 1 个库存差量；如果原先因库存不足没有扣减，就不能凭空增加库存。
4. 营养和今日进度恢复到 1 个鸡蛋对应的结果。
5. 回执说明撤销的是“数量从 1 改为 2”这次修改，而不是删除整条鸡蛋记录。

### 用户原话二

> 还是恢复吧。

### 恢复的计划行为

1. Agent 将“恢复”关联到刚撤销的更正。
2. 后端新增恢复事件，再次启用数量为 2 的版本。
3. 按真实可用库存重新应用差量，不能只靠旧回执假设库存仍然相同。
4. 再次重算营养和今日进度，返回实际恢复结果。

### 需要确认的范围

- “撤销刚才那个修改”目标唯一且可恢复，可以直接执行。
- “撤销今天所有记录”“清空库存”这类批量操作必须先说明影响范围并获得确认。
- 目标不唯一时先追问最少区分信息，不能随意撤销第一条。

### 验收通过条件

- 撤销和恢复都是新增历史事件，不物理删除审计链。
- 数据、库存、营养和进度跟随有效版本一致变化。
- 重复发送撤销或恢复请求保持幂等，不重复返还或扣减库存。
- 新会话仍能查询完整的原始、更正、撤销和恢复关系。

### 验收失败条件

- “撤销修改”被理解成删除整条饮食。
- 撤销只改聊天回复，数据库仍是 2 个。
- 重复点击导致库存多加或多扣。
- 恢复使用旧库存假设，生成不真实的库存余额。

## AC-008：设置、修改目标和查看进度

### 建档原话

> 我 28 岁，男，身高 175，体重 78 公斤，想三个月减到 72 公斤，平时一周运动三次。

### 建档和推荐的计划行为

1. Agent 理解并提交一次资料与目标意向请求，身高缺少单位但在该上下文中可可靠规范为 175 厘米。
2. 后端保存用户明确提供的资料，计算 BMI 等派生指标时标明计算来源。
3. 后端必须依据资料生成热量、蛋白、脂肪、碳水和纤维五项推荐值；资料足够时同时生成饮水推荐。所有推荐状态均为“待确认”。
4. 未经用户确认，不把推荐值写成正式生效目标，也不在进度回执中伪装成用户目标。
5. 回执分开显示“已保存资料”和“待确认推荐”。

### 确认目标原话

> 热量就按每天 2000 千卡，蛋白质 120 克，水 2 升吧。

后端应在一次目标事务中创建三个正式目标和同一生效时间。Agent 不把三个维度拆成三次互相冲突的新增操作。

### 修改目标原话

> 热量目标改成每天 2100 千卡，其他不变。

计划行为：

- Agent 识别为更新现有热量目标，不是新增第二个并行热量目标。
- 后端结束旧版本的生效区间，创建 2100 千卡的新版本；蛋白质和饮水目标保持原版本。
- 回执说明旧值、新值和生效时间。

### 查询进度原话

> 我今天完成得怎么样？

目标回执必须遵守固定六项顺序：热量、蛋白、脂肪、碳水、纤维、饮水。“蛋白”是强制展示名称，禁止写成“蛋白质”。百分比、10 格条和累计量全部来自后端冻结结果。

当热量、蛋白质和饮水已配置，其他三项未配置时，目标格式类似：

```text
🔥 热量 █████░░░░░ 52%
🔥 1092 kcal / 2100 kcal

🥩 蛋白 ██████░░░░ 58%
🥩 70 g / 120 g

🧈 脂肪 目标未配置
🧈 当前 41 g

🌾 碳水 目标未配置
🌾 当前 126 g

🥬 纤维 目标未配置
🥬 当前 未知

💧 饮水 ███████░░░ 71%
💧 1420ml / 2L
```

单纯查询不得显示本轮增量。存在未知营养或饮品水分时，必须按照“未知”或带 `≥` 的已知下界显示，不能当成 0。Agent 只能调整固定回执之外的引导措辞，不能重新计算或隐藏数据缺口。

### 验收通过条件

- 资料保存与目标生效状态明确区分。
- 确认前至少提供热量、蛋白、脂肪、碳水和纤维五项完整建议；资料足够时同时提供饮水建议。
- 多个目标可以一次确认，不产生动作冲突。
- “改成、调整为、以后每天”能更新目标版本。
- 查询只使用当前生效的正式目标，并能追溯历史版本。
- 未知营养项目会降低进度完整性，而不是被默认为零。
- 固定六项顺序和 10 格条符合进度回执规范；未配置项不显示百分比。
- 单纯查询不显示本轮增量，写入成功回执只显示后端冻结的同次正增量。
- 进度块位于成功回执最后，后面不追加建议或表扬。
- 第二项展示名称严格为“🥩 蛋白”，使用“🥩 蛋白质”即验收失败。

### 验收失败条件

- 建档后静默启用系统推荐值。
- 建档只给热量、蛋白或饮水等零散建议，缺少脂肪、碳水或纤维，且没有说明无法生成的原因。
- 修改目标被当成重复新增并返回冲突。
- 为了设置三个目标调用三次并产生部分成功。
- Agent 根据聊天记录口算累计或沿用已经失效的目标。
- 把 BMI、推荐目标或估算值表达成医疗诊断。
- 把未知纤维或未知饮品水分当成 0，或者使用非 10 格进度条。
- 后端尚未形成终态就显示成功标题和正式进度条。

## AC-009：商品营养表、通用来源、联网检索与估算

营养匹配不依赖库存是否存在。系统按以下优先级选择来源，并为每次饮食保存当时采用的营养快照：

1. 用户为具体商品提供并保存在本地的包装营养表。
2. Skill 本地通用营养库中匹配食物和规格的数据。
3. 带来源、检索时间和匹配依据的互联网查询结果。
4. 无法取得更准确数据时，明确标注的估算数据。

### 分支一：具体商品的本地营养表

用户说：

> 这是小象饼干，一盒 100 克。营养表写每 100 克 480 千卡，蛋白质 6 克，脂肪 20 克，碳水 68 克。

计划行为：

1. Agent 将品牌/商品名、规格和各营养字段绑定为用户提供的包装标签。
2. 后端把营养表保存到用户本地商品库，绑定“小象饼干 + 100 克盒装”的商品身份、规格和版本，不污染通用饼干数据。
3. 用户以后说“吃了半盒小象饼干”时，优先复用该标签并按 50 克换算；库存存在则同步扣减，不存在仍记录饮食。
4. 用户上传新标签或纠正数值时创建营养表新版本，历史饮食保留原快照；只有明确要求重算时才按规则更新受影响记录。

### 分支二：Skill 本地通用营养库

用户说：

> 吃了一个中等大小的苹果。

本地商品标签未命中时，后端可以使用 Skill 通用营养库中带版本和来源标识的标准份量，并在回执中说明“按中等苹果标准份量估算”。这属于有通用来源的标准估算，不表达成称重实测。

### 分支三：联网检索并沉淀

本地商品表和 Skill 通用库都未命中时，系统可以联网搜索。被采用的结果必须保存：查询词、来源名称、可访问地址、检索时间、匹配到的商品或食物、份量换算、置信状态以及是否仍属于估算。

- 高可信、许可证允许缓存且结构完整的数据可以写入营养库，后续相同食物或商品直接复用。
- 来源冲突或匹配不唯一时不能偷偷选一个精确值；应使用清楚标注的估算，或者只追问一个能区分商品的关键信息。
- 联网失败不能抹掉已经发生的饮食事实，也不能伪造已经查到来源。

### 分支四：估算保证流畅使用

用户说：

> 喝了 250 克杂粮粥。

本地与互联网都没有该碗粥的精确配方时，饮食事实仍照常保存。系统可采用合理的通用杂粮粥估算值，回执明确显示：

> 营养来源：估算数据。

估算必须保存假设的份量、参考范围和置信状态。能给出合理单值时可以用于进度，但不能冒充包装实测；连合理范围都无法建立时才显示未知，并按进度规范降低完整性。

### 后续补充或纠错

用户说：

> 小象饼干的标签我看错了，每 100 克其实是 460 千卡。

Agent 应更新“小象饼干”本地营养表版本，不新增饮食。后端保留旧值和来源历史；后续消费使用新版本，已发生记录是否重算由明确的更正请求决定。

### 验收通过条件

- 来源优先级严格符合：用户本地具体商品标签、Skill 通用库、带审计信息的互联网结果、明确估算。
- “小象饼干”等具体商品标签可本地持久化，并在新会话和后续消费中复用。
- 联网采用结果能追溯查询、来源、时间、匹配依据、份量换算和置信状态，并在允许时沉淀复用。
- 250 克杂粮粥等没有精确配方的食物仍能流畅记录，回执清楚标记“营养来源：估算数据”。
- 每个饮食快照保留当时的营养来源和版本；营养未知或联网失败不阻止事实保存。
- 任一饮食事实成功提交后，回执末尾仍有且只有一个后端冻结的六项进度块。

### 验收失败条件

- 用通用库或联网结果静默覆盖用户为具体商品提供的包装标签。
- 用户已经上传“小象饼干”标签，后续仍反复联网搜索或改用普通饼干数据。
- 声称来自互联网却不保存来源和检索记录，或联网失败后伪造结果。
- 把估算数据表达成包装实测值，或为无法建立合理依据的混合食物编造伪精确数据。
- 营养查不到就拒绝保存饮食，或者为了流畅使用把未知营养写成零。
- 修改营养标签时新增一条重复饮食，或回执显示的新进度与实际营养快照版本不一致。

## AC-010：否定、未来、他人和混合主体的零写入边界

### 表达与计划结果

| 用户原话 | Agent 应理解 | 饮食写入 |
|---|---|---|
| 我没吃那个蛋糕 | 否定的已发生事件 | 零写入 |
| 明天准备喝一杯牛奶 | 未来计划，不是已饮用 | 零饮食写入 |
| 如果晚上吃两个鸡蛋会怎样 | 假设和咨询 | 零写入 |
| 我妈吃了两个鸡蛋 | 他人事件 | 当前用户零写入 |
| 我跟我老婆各吃了一个鸡蛋 | 混合主体；本人 1 个、他人 1 个 | 只为当前用户写入 1 个 |
| 本来想吃蛋糕但没吃，后来吃了一个苹果 | 蛋糕被否定，苹果已发生 | 只写入苹果 1 个 |
| 刚才不是我吃的，是我朋友吃的 | 对既有错误归属的更正 | 撤销或更正当前用户记录，不新增他人事实 |

### 未来计划的边界

- “准备、打算、明天、等会儿想吃”不能进入已消费账本。
- 如果用户明确说“帮我做计划”或“提醒我”，可以进入独立计划或提醒能力；计划完成前不得影响已摄入营养和库存。
- 计划到点也不能自动认定用户已经吃了，必须等待用户确认实际发生。

### 混合主体的计划行为

对于“我跟我老婆各吃了一个鸡蛋”：

1. Agent 提取当前用户本人 1 个鸡蛋，另标记存在他人项目。
2. 后端只把本人项目写入个人饮食账本并按本人份额联动库存。
3. 回执说明“已为你记录 1 个；你老婆的 1 个没有写入你的个人饮食”。
4. 除非未来明确支持家庭成员账户，否则不能擅自为他人创建档案或写入事实。

### 验收通过条件

- 否定、假设、咨询和纯未来表达稳定零写入。
- 混合句只保存明确属于当前用户且已经发生的部分。
- 零写入时不扣库存、不更新营养和进度。
- 更正主体时能移除当前用户错误事实及其联动影响。
- 回执清楚说明记录了什么、忽略了什么及原因。

### 验收失败条件

- 看见食物和数量就写入，忽略“没、准备、如果、我妈”等语义。
- 把未来计划提前计入今日热量或扣库存。
- 把他人吃的食物记录到当前用户。
- 混合主体整句拒绝，导致当前用户明确发生的部分也丢失。
- 用聊天便签保存他人事实并声称已经入账。

## AC-011：新会话中的数据复核

### 前置状态

用户在旧会话中已经完成：

- 记录一顿包含米饭、鸡蛋和豆浆的午饭。
- 将鸡蛋数量从 1 个更正为 2 个。
- 入库两盒纯牛奶。
- 确认当前热量、蛋白质和饮水目标。

随后用户新建一个完全没有旧聊天上下文的会话。

### 用户原话

> 我今天都吃了什么？冰箱里还有多少鸡蛋和牛奶？今天目标完成得怎么样？

### Agent 的计划行为

- 识别为一个关联查询，包含今日饮食、当前库存和今日目标进度三个读模型。
- 提交一次组合查询请求，查询范围使用用户身份、用户时区和当前日期。
- 不从聊天记忆复述旧答案，也不因为新会话没有上下文而让用户重新建档。

### 后端的计划行为

1. 从权威账本读取当天当前有效的饮食版本，排除已撤销版本但保留可审计历史。
2. 从库存流水投影当前可用鸡蛋和牛奶，并能展开批次。
3. 从当前生效目标和当天已知营养快照计算进度。
4. 返回统一查询时间、数据版本和营养完整性状态，避免三个结果来自不同时间点。
5. 如果某个投影损坏或暂时不可用，明确返回该部分失败，不用其他部分的旧值冒充。

### 目标回执

> 今天已记录：……。当前库存：鸡蛋 …… 个，纯牛奶 …… 盒。今日热量、蛋白质和饮水进度分别为……。其中家制杂粮粥的营养仍未知，所以热量和蛋白质合计不完整。

所有省略值必须由测试时后端真实数据填入。

### 验收通过条件

- 新会话能完整读取旧会话真实提交的数据。
- 查询结果使用当前有效版本，不把旧版本和更正后版本重复相加。
- 库存余额可由入库、扣减、更正、撤销和恢复流水复算。
- 进度明确说明未知营养对完整性的影响。
- 查询本身不产生饮食、库存或目标写入。

### 验收失败条件

- 新会话说“我不知道，你之前没告诉我”。
- 用旧会话摘要或模型记忆代替数据库查询。
- 把更正前后的鸡蛋同时统计。
- 三个查询分别返回互相矛盾的时间点或库存余额。
- 查询失败时编造一个看起来合理的数字。

## AC-012：弱模型 Agent 的受限交互

### 目标

较低能力模型可以降低语言表达质量或增加一次必要追问，但不能降低数据正确性、真实回执、幂等、事务和零写入边界。

### 输入示例

> 中午我就随便吃了碗饭、俩鸡蛋，豆浆大概三百毫升吧。

### 计划适配方式

1. `SKILL.md` 只提供通用流程和参考路由，弱模型仅按当前场景读取餐食与回执资料。
2. Agent 提交的候选必须通过公共 Schema；后端工具只接受有限动作和明确字段，不接受自由拼接 SQL 或文件操作。
3. 高可信字段直接进入候选；缺少关键字段时，工具返回具体缺口，例如“鸡蛋单位缺失”，不能只返回“动作冲突”。
4. Agent 对一个缺口提出一个自然问题；用户补充后再提交完整请求。
5. 一次用户消息最多允许一次可产生业务变化的提交。纯 Schema 校验失败不得产生任何数据变化，也不能在循环中连续尝试多个猜测。
6. 后端回执已经包含可直接展示的简洁摘要，弱模型可以小幅改写，但不得重算数字或改变成功状态。

### 降级顺序

| Agent 状态 | 计划行为 |
|---|---|
| 能完整提取 | 一次提交并返回真实回执 |
| 只缺一个关键字段 | 保存候选并进行一次最短追问 |
| 多个核心语义互相冲突 | 不写入，说明当前理解并请用户用自己的话补充关键事实 |
| 无法调用工具 | 只说明无法持久化，可整理待提交内容；禁止声称成功 |

### 跨 Agent 一致性要求

- 同一结构化命令在 OpenClaw、MCP 和其他适配器中产生相同核心数据变化。
- 适配器只能转换协议和错误格式，不复制或修改饮食业务规则。
- 同一组口语评测分别在强、中、弱模型运行，比较语义候选、调用次数、真实数据和回执，不只比较回复文案。
- 弱模型可接受的差异是更多一次必要追问；不可接受的差异是漏写、重复写、错误扣库存或假成功。

### 验收通过条件

- 示例原话能够正确绑定一碗饭、两个鸡蛋和约 300 毫升豆浆。
- 解析失败时错误指出具体字段，且数据库零变化。
- 模型不会为了通过 Schema 反复猜测并连续调用。
- 回执中的数字和状态完全来自后端。
- 无工具环境明确降级，不制造持久化假象。

### 验收失败条件

- 要求普通用户改说内部动作名或固定 JSON 格式。
- Schema 失败后仍部分写入，或 Agent 连续七次尝试工具。
- 把数据库冲突猜成某个不存在的食物条目。
- 工具不可用时改用聊天记忆并回复“已经记好了”。
- 为某个 Agent 单独复制一套业务逻辑，导致相同命令结果不同。

## 全场景共同发布门槛

- AC-001 至 AC-012 都必须拥有自动化用例和至少一条普通中文口语人工验收用例。
- 同一场景必须分别核验 Agent 候选、业务调用次数、数据库变化、库存流水、营养来源、目标投影和最终回执。
- 所有 P0/P1 已知问题必须映射到至少一个场景，并先证明旧版失败、再证明 0.3 通过。
- 01、02、03 作为主要模型环境全部通过；低阶模型环境允许按 AC-012 追问降级，但不允许数据安全降级。
- 安装、迁移、回滚和新会话复核通过后，才允许把 0.3 标记为可发布。
