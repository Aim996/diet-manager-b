# 饮食管家 0.3 进度回执规范

> 状态：已确认  
> 版本：0.3 设计基线  
> 用途：冻结饮食目标进度条、进度数据权威边界和开发进度表达规则  
> 来源：继承 0.2.1 已验证的回执与日期契约，并按 0.3 的“Agent 负责语义、后端负责数据”架构修订

## 1. 两种进度必须分开

本项目存在两种含义完全不同的“进度”：

1. **饮食目标进度**：来自用户已经确认的营养和饮水目标，由后端计算并冻结，按照本规范展示六项进度块。
2. **开发工作进度**：来自实际完成并通过验收的工作项，默认只报告状态，不随意估算百分比。

两者不得共用计算公式、数据来源或展示话术。

## 2. 饮食目标的生效条件

- 只有用户主动设置或明确确认的目标，才能参与百分比和进度条计算。
- 系统推荐目标在用户确认前只是建议，不能自动生效。
- 修改目标必须建立新版本，保留旧版本的生效区间。
- 查询和本轮回执只能使用对应日期、对应时刻实际生效的目标版本。
- 目标不存在时，禁止使用系统默认值、推荐值或模型猜测值补齐。

### 2.1 强制触发规则

- 只要后端最终成功产生一条或多条饮食、饮品或白水消费事实，用户回执末尾必须输出一次完整六项进度块。
- 同一请求记录多种食物、同一餐或混合饮食与饮水时，只在最终回执末尾输出一个合并后的六项进度块，不按项目重复输出。
- 更正、撤销或恢复改变了饮食累计时，必须为每个受影响日期输出重新冻结的六项进度块。
- Agent、Skill 和适配器无权因为回复过长、模型能力较弱、营养存在部分未知或认为用户不需要而省略进度块。
- 六项目标全部未配置时，强制输出“目标未配置，进度条不可用。”和六项累计或未知；此时强制的是进度反馈块，不允许伪造进度条和百分比。
- 必要效果尚未终态时遵守第 10 节：不能提前输出成功进度；形成成功冻结终态后才强制输出。

### 2.2 六项目标全部未配置

必须先显示：

```text
目标未配置，进度条不可用。
```

随后仍按固定顺序显示六项当天累计量；未知值显示“未知”。此时不显示百分比、不显示进度条。

```text
🔥 热量 1040 kcal
🥩 蛋白 82 g
🧈 脂肪 41 g
🌾 碳水 126 g
🥬 纤维 未知
💧 饮水 1420ml
```

### 2.3 只配置了部分目标

六项仍然全部出现并保持固定顺序：

- 已配置目标的项目使用正式两行进度格式。
- 未配置目标的项目不显示进度条和百分比；第一行显示“目标未配置”，第二行只显示当前累计或未知。
- 未配置项目不得使用系统推荐值冒充目标。

```text
🔥 热量 █████░░░░░ 52%
🔥 1040 kcal / 2000 kcal｜+320 kcal +16%

🥩 蛋白 目标未配置
🥩 当前 82 g
```

## 3. 固定六项与顺序

顺序、Emoji、展示名称和基础单位固定如下，不允许适配器或模型重新排序或改名：

1. `🔥 热量`：当前、目标和增量使用 `kcal`。
2. `🥩 蛋白`：使用 `g`。六项进度块中必须使用“蛋白”两个字，禁止写成“蛋白质”。
3. `🧈 脂肪`：使用 `g`。
4. `🌾 碳水`：使用 `g`。
5. `🥬 纤维`：使用 `g`。
6. `💧 饮水`：当前量和增量使用 `ml`；目标允许格式化为 `L`。

## 4. 已配置目标的固定两行格式

- 每个已配置项目严格显示两行。
- 两行必须使用相同 Emoji。
- 第一行只包含 Emoji、名称、10 格进度条和百分比。
- 第二行包含当前累计、目标和可选的本轮正增量。
- 进度条必须正好 10 格，只允许使用 `█` 和 `░`。

```text
🔥 热量 █████░░░░░ 52%
🔥 1040 kcal / 2000 kcal｜+320 kcal +16%
```

## 5. 计算规则

```text
percentage = round_half_up(current / target × 100)
filled = clamp(round_half_up(current / target × 10), 0, 10)
increment_percentage = round_half_up(increment / target × 100)
```

约束：

- 必须使用十进制 `round_half_up`，恰好 `.5` 时向远离零的方向取整。
- 0.3 不允许直接使用 JavaScript 二进制浮点数加 `0.5`、PowerShell 默认舍入或 SQLite 默认舍入作为权威算法。
- 计算前必须统一单位。
- `current` 必须大于等于 0；`target` 必须大于 0。
- 超过目标时百分比显示真实值，进度条最多填满 10 格。

| 当前 / 目标 | 百分比 | 进度条 |
|---|---:|---|
| 0 / 100 | 0% | `░░░░░░░░░░` |
| 5 / 100 | 5% | `█░░░░░░░░░` |
| 105 / 100 | 105% | `██████████` |

## 6. 本轮增量

- 只显示同一次最终冻结结果返回的正增量。
- 零增量、负增量和缺失增量不显示在普通进度条回执中。
- 正增量折算后低于 1% 时显示 `+<1%`。
- 单纯查询进度时，不显示“本轮增加”。
- 不允许通过前后两份报告相减、读取旧快照或让 Agent 自行相加来推算增量。
- 跨日更正所需的有符号数据可以保存在后端审计结果中，但普通展示仍遵守“只显示本轮正增量”。

## 7. 未知值不能当成零

每个指标必须具有明确覆盖状态：

- `known`：当前累计完整已知。
- `unknown`：无法形成可靠当前值。
- `known_min`：只知道可靠下界。

禁止把 `unknown` 或缺失值转换成数字 0。

目标已配置但指标未知时，十个 `░` 只是未知状态的版式占位，不表示 0%：

```text
🥬 纤维 ░░░░░░░░░░ 未知
🥬 未知 / 30 g
```

## 8. 饮水进度

```text
饮水已知量 = 白水 + 已知的食物或饮品水分
```

约束：

- 白水与食物、饮品含水量不得重复计算。
- 如果任何相关食物或饮品水分未知，精确饮水总量保持未知。
- 已知部分只作为下界保存和展示，使用 `≥`，不能称作精确总量。
- 下界百分比和进度条仍使用十进制 `round_half_up`。

```text
💧 饮水 ██░░░░░░░░ ≥20%
💧 已知至少 500ml / 2.5L｜另有饮品水分未知
```

本轮存在已知正增量时，可以追加已知增量；未知部分只能说明“本轮另有饮品水分未知”，不得伪造增量。

## 9. 数据权威与成功条件

进度结果必须由后端最终器在同一次原子提交中生成并冻结。后端冻结结果至少包含：

- 对应日期和用户时区。
- 当前生效目标版本。
- 固定六项顺序。
- 已提交有效记录形成的累计量。
- 当前请求实际产生的增量。
- 每项覆盖状态和未知项目来源。
- 饮水已知下界。
- 幂等结果身份和生成时间。

Agent、Skill 和各 Agent 适配器：

- 只能读取后端冻结结果并按规范渲染。
- 不得自行计算百分比、格数、累计量或增量。
- 不得根据聊天记录口算。
- 不得额外查询旧快照后拼接成功回执。
- 不得通过两次查询结果相减重建本轮增量。

累计量只统计 `active + committed` 的有效记录，必须排除：

- 预览。
- 失败和忽略事件。
- 未提交候选。
- 被更正版本取代的旧事实。
- 已撤销事实。

更正、撤销和恢复后必须重新计算受影响日期。

## 10. 未终态时禁止显示成功进度

如果必要的营养、库存联动或最终器仍处于 `pending` 或 `retryable_failed`：

- 不显示成功标题。
- 不显示正式进度块。
- 不声称进度已经更新。
- 同键重试只恢复未完成的效果或最终器，不重复已经成功的事实和效果。

“没有库存”“未匹配库存”等已经被后端确定为稳定业务跳过的结果，不等于技术 `pending`；只要整体已经形成冻结终态，仍可返回真实饮食回执和正式进度块。

## 11. 日期与幂等

- 单日操作只显示一个六项进度块。
- 同日包含多项饮食、饮水或混合操作时，也只显示一次最终进度块。
- 跨日更正、撤销或恢复时，按日期升序分别显示进度块，不得合并。
- 同一幂等请求合法重试，必须返回第一次冻结的原进度结果。
- 即使随后当天累计发生变化，也不能用最新状态重建旧请求回执。
- 新用户消息即使文字相同，也是新业务事件，不使用旧幂等结果。

## 12. 展示位置与禁止项

- 进度块必须位于成功回执最后。
- 成功产生饮食、饮品或白水消费事实时，禁止省略完整六项进度块。
- 不添加“📊 今日进度”等额外标题。
- 进度条之后不追加表扬、警告、健康建议、剩余额度或下一餐推荐。
- 不使用非 10 格进度条。
- 不使用 `█`、`░` 之外的字符替代进度格。
- 不把推荐目标伪装成用户正式目标。
- 不把未知值展示为 0 或 0%。
- 不把饮水已知下界表达成精确总量。
- 六项进度块第二项禁止显示“蛋白质”，必须固定显示“蛋白”。

## 13. 开发进度表达

仓库开发进度默认只使用以下状态：

- **已完成**：功能完成且已经通过约定验收。
- **开发中**：已经开始实现，但尚未完成统一验收。
- **待开发**：尚未实现。
- **阻塞**：依赖环境、授权或外部服务，当前无法完成验收。

在没有冻结工作项和权重前，不随意报告 `80%`、`95%` 等开发完成度。

如果未来确实需要百分比，统一使用：

```text
开发完成度 = 已完成并通过验收的工作项权重 ÷ 全部计划工作项权重 × 100%
```

约束：

- 只写完代码但未验收，不计为已完成。
- 测试数量多不代表功能进度高。
- 文档、部署和真实 Agent 环境验收分别计入。
- 阻塞项目仍属于未完成。
- 新发现缺陷必须调整剩余工作量，不得为了维持百分比而隐瞒。

## 14. 0.3 实现修正要求

0.3 不直接复制 0.2.1 的进度条实现，必须修正以下已确认风险：

1. 当前值的数据类型允许“未知”和“已知下界”，禁止由调用方把空值折算为 0。
2. 权威计算使用确定性十进制算法，不依赖 JavaScript 二进制浮点近似。
3. 后端冻结完整六项进度对象；渲染器不重新计算。
4. 推荐目标与正式目标使用不同状态，只有正式目标参与计算。
5. 自动化测试覆盖未知纤维、饮水下界、本轮增量、部分目标、跨日、幂等冻结、最终器失败和固定排版。

## 15. 发布验收门槛

- 0、5、100、105 百分比边界全部通过十进制 Oracle。
- 六项目标全部未配置、部分配置和全部配置三种模式通过。
- 已知、未知和已知下界三种覆盖状态通过。
- 直接查询无增量、写入回执有正增量、低于 1% 三种情况通过。
- 单日、同日 mixed、跨日更正三种日期结果通过。
- 同键重试返回冻结原结果，新消息相同文字仍产生新事件。
- `pending`、可重试失败和最终器失败均不出现成功进度块。
- 强模型和弱模型得到相同后端进度数据，适配器只允许措辞差异，不允许数值差异。
- 所有正式回执和黄金样本中的第二项名称严格等于“🥩 蛋白”，出现“🥩 蛋白质”即验收失败。
- 每一条终态成功的饮食、饮品和白水写入黄金回执末尾都有且只有一个完整六项进度块；缺失或重复均验收失败。
