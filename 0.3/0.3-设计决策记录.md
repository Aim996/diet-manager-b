## DEC-001：产品定位为“单包安装的工具型 Skill”

- 状态：已确认
- 确认日期：2026-08-21

### 决定

饮食管家对普通用户继续以一个 Skill 的形式提供，并保持单包安装体验；工程内部不采用“只有一份提示词”的纯 Skill 结构，而采用工具型 Skill 结构：

1. 通用 Skill：定义语义、交互、工具使用和回执规则。
2. Agent 语义层：理解用户自然语言并生成结构化业务指令。
3. 饮食核心服务：处理餐食、饮水、库存、营养、目标、进度、更正、撤销和恢复。
4. SQLite 权威账本：保存事实、库存流水、营养快照、目标版本和变更历史。
5. 多 Agent 适配器：OpenClaw 使用本地插件；支持 MCP 或 JSON Tool Calling 的 Agent 使用相应薄适配器。

### 对外体验

- 用户只需安装一个饮食管家包，不需要分别安装和理解内部组件。
- 用户始终通过自然语言与自己的 Agent 交流。
- 不要求用户学习 action、记录 ID、数据库或固定字段格式。

### 兼容边界

- 能读取 Skill 且能调用 Tool、Plugin 或 MCP 的 Agent 可以使用完整能力。
- 完全没有工具调用能力、无法访问本地服务的 Agent 只能理解和临时回答，不能承诺可靠持久化。
- 任何 Agent 的语言能力可以降级，但数据安全、单次提交、幂等和真实回执不能降级。

### 不采用的方案

- 不采用只靠 `SKILL.md` 和提示词管理长期数据的方案。
- 不使用聊天记忆、便签或 Markdown 日志作为第二套权威账本。
- 不为每个 Agent 重写一套饮食、库存和进度业务逻辑。

## DEC-002：Agent 负责语义，后端负责数据执行

- 状态：已确认
- 确认日期：2026-08-21

### 决定

Agent 不是原话传递器。Agent 使用大模型理解用户，并向后端提交“用户原话 + 结构化业务指令”。后端不重复争夺自然语言语义判断权，而按业务指令查询真实状态、执行数据事务、计算营养和进度，并返回实际执行回执。

### Agent 负责

- 判断用户意图及要进入的业务方向。
- 判断本人、他人和混合主体。
- 判断已经发生、未来计划、否定、假设和查询。
- 提取食物、饮品、数量、单位、时间和修饰信息。
- 保持一顿饭中多个项目与各自数量的对应关系。
- 把后端结构化回执简洁地表达给用户。

### 后端负责

- 查询和扣减真实库存。
- 写入饮食和饮水事实。
- 查询营养来源并生成营养快照。
- 计算今日累计、目标百分比和剩余量。
- 执行更正、撤销、恢复和目标版本变更。
- 保证事务、幂等、并发和数据库约束。
- 只依据实际提交结果返回成功、部分成功、未写入或失败。

### 标准流程示例

用户说“我吃了一个鸡蛋”时：

1. Agent 提取“本人、已发生、鸡蛋、一个、当前时间”。
2. Agent 提交结构化餐食指令和原话。
3. 后端查询库存；有鸡蛋则扣一个，没有则不扣但不阻止餐食记录。
4. 后端写入餐食事实，并尝试匹配鸡蛋营养。
5. 后端重新计算当天营养和目标进度。
6. 后端返回餐食、库存影响、营养、今日累计和剩余目标。
7. Agent 只使用该回执回答用户，随后结束本轮。

### 权威边界

- Agent 对“用户表达了什么”负责。
- 后端对“数据实际上执行成什么结果”负责。
- Agent 不得自行宣布数据库提交成功、库存余额、营养来源或目标进度。
- 后端不能把普通语义重新解释成与 Agent 指令无关的另一项业务；发现结构冲突时返回明确缺口或安全错误。

## DEC-003：架构升级版本改为 0.3

- 状态：已确认
- 确认日期：2026-08-21

### 决定

本次升级不再作为 0.2.3 小版本开发，正式改为饮食管家 0.3。发布展示版本使用 `0.3`，符合包管理器要求的工程版本使用 `0.3.0`。

### 原因

- 产品从纯 Skill 预期明确升级为单包安装的工具型 Skill。
- Agent 与后端的职责、公共语义契约和适配器边界会发生架构级变化。
- 将新增或调整多轮候选、库存联动、事务回执、查询投影和跨 Agent 适配能力。
- 当前工作不只是修复若干自然语言规则，不适合继续沿用补丁版本编号。

### 目录与版本处理

- 原计划目录 `0.2.3` 已整体迁移为 `0.3`。
- `0.2.3` 不再作为待发布版本。
- 当前 0.2.2 仍是测试基线；0.3 从其现有能力和数据兼容边界上演进。
- 测试问题编号同步改为 `DM-030-*`，与新版本设计保持一致。

## DEC-004：采用“轻入口、按需参考、单一契约真源、口语评测”结构

- 状态：已确认
- 确认日期：2026-08-21

### 调研依据

本决定参考了高关注度 Agent Skill 项目的实际目录和公开规范，但不以 Star 数量代替工程判断：

- [Anthropic Agent Skills](https://github.com/anthropics/skills) 使用 `SKILL.md` 作为入口，并按需要搭配 `scripts/`、参考文件和评测资源；其 PDF、XLSX 等技能把执行代码与入口说明分开。
- [Vercel Agent Skills](https://github.com/vercel-labs/agent-skills) 将大量细则拆成独立规则文件，再生成 Agent 可读汇总和评测用例，减少人工维护的重复内容。
- [Superpowers](https://github.com/obra/superpowers) 将 Skill 本身也按测试驱动方式验证，强调先记录未加载 Skill 时的失败基线，再验证 Skill 是否真正改变 Agent 行为。
- [Agent Skills 开放规范](https://agentskills.io/specification) 明确要求 `SKILL.md`，推荐使用 `scripts/`、`references/`、`assets/` 和渐进式加载，并建议入口文件少于 500 行、文件引用不要形成深层链路。

### 决定一：`SKILL.md` 只做入口和行为总纲

`skills/diet-manager/SKILL.md` 只保留：

1. 技能触发范围与不触发范围。
2. Agent 与后端的职责边界。
3. 一次消息的标准执行流程。
4. 必须遵守的零写入、一次提交、真实回执规则。
5. 根据当前任务读取哪个参考文件的路由表。
6. 一个覆盖“记录、库存联动、营养、目标进度、回执”的黄金示例。

详细语义词典、动作字段、错误码、回执字段和边界案例不得继续堆进入口。目标不是追求固定行数，而是保证激活 Skill 后不会一次加载整套领域资料。

### 决定二：语义和业务资料按需拆分，保持一层引用

参考资料采用平铺、小主题文件；`SKILL.md` 直接引用所需文件，不让参考文件继续引用第二层、第三层说明：

```text
skills/diet-manager/
├─ SKILL.md
├─ agents/
│  └─ openai.yaml
├─ references/
│  ├─ semantic-extraction.md
│  ├─ meal-and-water.md
│  ├─ inventory.md
│  ├─ goals-and-progress.md
│  ├─ correction-history.md
│  ├─ receipt-and-errors.md
│  └─ safety-boundaries.md
└─ evals/
   └─ evals.json
```

- 每份参考文件只覆盖一个业务主题，并写明何时读取。
- `agents/openai.yaml` 只存客户端展示和发现信息，不复制业务规则。
- 没有实际用途时不创建 `assets/`、空目录或占位文件。

### 决定三：公共契约只有一份机器真源

Agent 指令、后端回执和错误结构以 `contracts/*.schema.json` 为唯一机器真源。TypeScript 类型、工具注册参数、示例片段和契约文档由 Schema 生成或校验，不允许分别手写后长期漂移。

```text
contracts/
├─ agent-command.schema.json
├─ backend-receipt.schema.json
└─ shared-types.schema.json
```

Skill 的参考文件只解释字段的语义和使用时机，不复制完整 Schema。构建和持续集成必须检查：

- Schema 本身有效。
- Agent 示例可通过命令 Schema 校验。
- 后端回执可通过回执 Schema 校验。
- 生成类型和注册定义与 Schema 没有差异。

### 决定四：把真实口语评测作为 Skill 的组成部分

0.3 不只测试函数和数据库，还要测试不同能力 Agent 是否能按普通人说法正确使用 Skill。评测集来源包括本轮五环境人工测试、已知问题回归和新增自然表达变体。

每条评测至少包含：

- 用户自然原话与必要的前置状态。
- 期望语义指令或允许的候选范围。
- 期望写入、库存变化和零写入约束。
- 期望回执必须包含或不得声称的内容。
- 最大业务调用次数。
- 跨新会话复核方式。

评测分为两层：`skills/diet-manager/evals/evals.json` 验证 Agent 激活、理解和调用行为；根目录 `tests/` 验证契约、核心服务、适配器与端到端真实落库。P0/P1 已知问题必须先形成失败用例，再允许修复实现。

### 优化后的单包边界

```text
diet-manager-0.3.0/
├─ package.json
├─ openclaw.plugin.json
├─ README.md
├─ skills/diet-manager/       # 可被兼容 Agent 发现的通用 Skill
├─ contracts/                 # Agent 与后端的唯一公共契约
├─ src/
│  ├─ core/                   # 饮食、库存、营养、目标等确定性业务逻辑
│  ├─ storage/                # SQLite、仓储、事务和查询投影
│  └─ adapters/               # OpenClaw、MCP 等薄适配器
├─ migrations/                # 可升级、可回滚的数据迁移
├─ scripts/                   # 安装探针、校验、迁移和诊断
└─ tests/                     # 契约、核心、适配器和端到端测试
```

### 明确不照搬的做法

- 不因为某仓库 Star 高就复制其全部目录；只引入饮食管家确实需要的文件。
- 不把 Vercel 的几十条规则编译成一个超长入口；饮食管家需要按业务场景读取，而不是一次装入全部知识。
- 不把运行时代码塞进 Skill 文本，也不让 Agent 直接修改 SQLite。
- 不把特定 Agent 的私有前置字段当作公共契约；跨 Agent 能力依赖标准 `SKILL.md` 与统一工具 Schema。

### 预期结果

- 强模型能充分理解普通用户表达，不被大量无关规则挤占上下文。
- 低阶模型只读取当前场景所需规则，减少动作冲突和字段遗漏。
- OpenClaw、MCP 和其他适配器共享同一业务与契约，不产生多套真相。
- 已经测出的重复调用、假成功、目标修改失败、纠错失败和库存幻觉都能转成稳定回归门槛。

## DEC-005：采用七项默认产品行为规则

- 状态：已确认
- 确认日期：2026-08-21
- 决策来源：用户审核 D-01 至 D-07 后，批准全部采用推荐方案

### D-01：信息不完整时采用“可靠自动化，关键缺口单问”

- 能从原话、用户资料、明确上下文或确定单位换算中可靠得到的字段自动补全。
- 缺失字段会明显影响事实含义、营养结果或数据安全时，最多先追问一个最关键问题。
- 追问必须承接当前候选，不要求用户把整句话重新说一遍。
- 不能为了追求一次成功而悄悄编造数量、时间、主体或食物。

### D-02：一句话多件事只提交一次关联业务请求

- Agent 可以一次理解同一句话中的多种食物、饮水、库存联动和进度查询。
- 对同一用户消息只提交一次顶层业务请求，并携带多个有序关联项目。
- 后端在一个业务编排中完成餐食事实、库存影响、营养快照和进度投影。
- 禁止 Agent 为同一消息反复调用同一业务，幂等键必须使重放不产生新事实。
- 幂等键必须绑定稳定的用户消息或业务请求身份，不能使用“原话相同”“食物和数量相同”或短时间窗口作为重复判据。
- 用户用一条新的消息再次说出相同内容时，默认代表一个新的真实事件并新增记录；只有用户表达“刚才重复发了、别重复记”等更正含义时才走纠错流程。
- 餐食或饮水事实是主结果；库存不存在或营养暂时未知时，不应让已经明确发生的事实丢失，回执必须逐项说明联动结果。

### D-03：库存采用高可信自动匹配和先进先出

- 食物与库存能高可信匹配时自动扣减，多个可用批次默认按先进先出处理。
- 库存不存在或数量不足时仍记录已发生的饮食，不能伪造库存扣减。
- 同名商品、规格或单位存在实质歧义时不乱扣；只有该歧义确实影响库存变化时才追问。
- 单位换算只能使用确定换算或已保存的商品规格；不使用模型猜测重量扣库存。
- 回执分别说明“饮食已记录”和“库存扣了什么、未扣什么及原因”。

### D-04：更正、撤销和恢复保留完整版本历史

- 用户明确指向最近记录时直接更正，不强迫使用记录 ID 或固定命令。
- 存在多个合理目标时只追问区分目标所需的最少信息。
- 更正不物理覆盖原事实，而以新版本和变更关系保留历史。
- 撤销后允许恢复；重复撤销或恢复必须幂等。
- 回执只宣布后端实际完成的更正、撤销或恢复，不用聊天记忆冒充成功。

### D-05：营养数据按可信来源分级并暴露不确定性

默认优先级为：

1. 用户已经确认的营养值。
2. 商品包装或标签值。
3. 经过标识的可信营养数据库。
4. 明确标为“估算”的近似值。

- 事实记录与营养补充解耦；营养未知不能阻止明确发生的饮食落库。
- 每个营养快照保存来源、版本、份量换算和是否估算。
- Agent 不把估算值表达成精确测量值，用户后续提供标签时可更正并重算进度。

### D-06：目标只推荐，不在未确认时自动启用

- 建档后可以生成热量、体重、蛋白质、饮水等推荐目标，但推荐值不是正式目标。
- 只有用户明确确认或主动设定后，目标才进入生效状态。
- 用户使用“改成、调整为、以后每天”等自然说法时，应更新现有目标而不是与旧目标冲突。
- 每次修改生成目标版本，保存生效时间；历史进度可以解释当时使用的目标。
- 进度回执区分当前累计、正式目标、剩余量和仅供参考的推荐值。

### D-07：跨 Agent 兼容能力分三级承诺

| 兼容级别 | Agent 能力 | 饮食管家承诺 |
|---|---|---|
| 完整工具型 | 能读取 Skill、提交结构化 Tool/Plugin/MCP 请求并读取回执 | 提供完整记录、库存、营养、目标、进度、更正、撤销和恢复能力 |
| 受限工具型 | 模型理解能力较弱，但仍能调用统一工具 | 使用更严格的参考路由和 Schema 约束；数据正确性标准不降级，必要时增加最短追问 |
| 只读分析型 | 不能调用后端工具或不能持久化 | 只能解释、估算或生成待提交内容；不得声称已保存、已扣库存或已更新进度 |

- 对外“兼容所有 Agent”指 Skill 入口和语义规范可跨 Agent 使用，不代表无工具 Agent 也具备虚假的持久化能力。
- 适配器可以不同，但公共命令、回执、事务、数据安全和验收标准保持一致。

## DEC-006：固定六项进度由后端冻结，展示层不得重算

- 状态：已确认
- 确认日期：2026-08-21
- 完整规范：[0.3-进度回执规范.md](./0.3-进度回执规范.md)

### 决定

饮食目标进度固定包含热量、蛋白、脂肪、碳水、纤维和饮水六项，并保持固定顺序。进度块第二项的展示名称强制为“蛋白”两个字，不得写成“蛋白质”。百分比、10 格进度条、本轮增量、未知状态、饮水下界和跨日结果全部由后端最终器计算并冻结；Agent、Skill 和适配器只负责按照冻结结果渲染，不重新计算。

任何终态成功的饮食、饮品或白水写入回执，都必须在末尾附带一个完整六项进度块；同一请求无论包含多少项目都只显示一次。更正、撤销和恢复改变累计时也必须返回受影响日期的进度块。任何 Agent 或适配器均无权省略。

### 目标状态

- 只有用户主动设置或确认的正式目标参与进度计算。
- 推荐目标未确认时不得生效。
- 六项目标全部未配置时，显示“目标未配置，进度条不可用”，随后只显示六项当前累计或未知。
- 即使六项目标全部未配置，成功饮食回执也不能省略进度反馈块；只是不得显示虚假百分比和条。
- 只配置部分目标时仍显示固定六项；已配置项显示两行进度条，未配置项显示“目标未配置”和当前累计或未知，不显示百分比。

### 数据完整性

- 每项明确区分已知、未知和只知道下界。
- 未知值不得折算为 0。
- 饮水由白水与已知食物、饮品水分组成，不得重复计算；存在未知水分时只显示带 `≥` 的已知下界。
- 只聚合当前有效且已提交的事实，排除预览、失败、忽略、被取代和已撤销记录。

### 终态与幂等

- 必要效果或最终器处于待处理、可重试失败时，不显示成功标题或正式进度块。
- 同一幂等请求重试返回第一次冻结的原进度结果，不用最新累计重建旧回执。
- 相同文字的新用户消息仍是新事件，不命中旧幂等结果。
- 单日只显示一个六项块；跨日修改按日期排序分别显示，不得合并。

### 展示边界

- 进度块位于成功回执最后。
- 成功产生饮食事实而缺少六项进度块，或者同一次请求重复显示多个进度块，均属于发布阻断问题。
- 进度条固定 10 格，只使用 `█` 和 `░`。
- 进度块后不追加表扬、警告、建议或下一餐推荐。
- 超目标显示真实百分比，但条最多填满 10 格。

### 开发进度

开发完成度默认只使用“已完成、开发中、待开发、阻塞”四种状态。在未冻结工作项权重前，不随意报告开发百分比；代码写完但未通过验收不能标记为已完成。

## DEC-007：营养来源沉淀、双单位库存与简洁回执

- 状态：已确认
- 确认日期：2026-08-21
- 完整规范：[0.3-营养来源与库存单位规范.md](./0.3-营养来源与库存单位规范.md)

### 决定

1. Agent 负责识别用户吃了或喝了什么；饮品不能因液态而被排除。含热量饮品同时参与营养与水分汇总，白水参与饮水汇总。
2. 营养匹配与库存匹配是两条独立链路。没有库存时仍记录摄入并显示“未匹配有效库存”；有库存但营养未知时必须继续查找营养来源。
3. 营养来源依次使用：用户为具体商品提供的本地包装营养表、Skill 本地通用营养库、带来源的互联网检索结果、明确标注的估算数据。采用的联网结果必须记录检索来源、时间、匹配依据和置信状态，并沉淀到营养库供后续复用。
4. 具体商品的本地营养表绑定商品身份和规格并保留版本。例如用户上传“小象饼干”的标签后，后续吃同一商品必须优先复用该标签，不退回通用饼干数据。
5. 库存批次同时保存包装数量单位与每包装基础净含量。例如“2 盒、每盒 250 ml”同时保留 `2 盒` 和 `500 ml`，允许以后按盒或按毫升扣减。没有确定规格或密度时禁止猜测换算。
6. 成功回执正文只保留已记录项目和关键库存变化，详细批次、换算、来源与审计信息保存在结构化结果中，需要时再展开；正文之后仍必须强制输出一次完整六项进度块。
7. 建档推荐在用户确认前必须至少生成热量、蛋白、脂肪、碳水和纤维五项目标建议，状态统一为“待确认”。资料足够时同时生成饮水建议；资料不足时明确缺少的信息，不得静默编值，也不得自动启用建议。
