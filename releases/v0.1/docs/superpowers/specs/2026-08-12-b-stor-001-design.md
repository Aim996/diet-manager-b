# B-STOR-001 Storage Bootstrap Design

## Goal

Deliver the first production-shaped B storage bootstrap: built-in `node:sqlite`, one fixed database filename, one mapping-locked initial migration, fail-closed open checks and packaging compatibility. All verification writes only to a unique test-owned temporary root.

This task does not implement meal/water/inventory repositories or expose a writing OpenClaw tool. Those belong to `B-STOR-002` and the later B slice.

## Approved scope

- product route: B only;
- driver: Node.js 24 built-in `node:sqlite`;
- database filename: `diet-manager-b.sqlite3`;
- path authority: an adapter-provided private B runtime root, never a model/user-provided database path;
- schema source: `shared/contracts/storage-mapping.md`, machine block `storage-mapping/v1`;
- mapping block identity: 44461 UTF-8 bytes, SHA-256 `19A74F1FB131CDCC1799653043EE707F6CC765369F4997811E62815ABED99D2F`;
- database identity: `PRAGMA application_id = 0x444D4231` (`1145913905`), `user_version = 1`;
- migration identity: `diet-manager/b-sqlite-migration/0001`, checksum equal to the mapping block SHA-256;
- schema cardinality: 20 tables, 18 indexes and 22 declared foreign keys;
- runtime settings: WAL, foreign keys enabled and 5000 ms busy timeout.

## Architecture

### 1. Trusted root and fixed leaf

The storage module accepts only an existing absolute private runtime root. It rejects a relative root, a non-directory root, a symlink/junction root and an existing database leaf that is not an ordinary file. The caller cannot supply a filename; the module always appends `diet-manager-b.sqlite3` as one direct child.

The production adapter is responsible for obtaining the private runtime root. Natural-language input and tool parameters never carry a filesystem path.

### 2. Candidate-first initial migration

For a fresh install, the module creates a uniquely named candidate beside the fixed final leaf. It configures SQLite and applies migration 0001 under `BEGIN EXCLUSIVE`. Only after the following checks pass may the candidate be renamed to the fixed final leaf:

- exact application ID and user version;
- one exact `schema_migrations` row with the frozen mapping checksum;
- exact table/index/foreign-key counts;
- empty `PRAGMA foreign_key_check`;
- `PRAGMA quick_check` equals `ok`.

An injected or real migration failure closes and removes the unpublished candidate plus its WAL/SHM files. The fixed final leaf remains absent. A retry always starts from a fresh candidate; partial resume is forbidden.

An existing matching v1 database may be opened after the same identity/integrity checks. Upgrade publication and backup/restore of older official databases remain for the later migration/reliability task; B-STOR-001 never mutates an unknown existing database.

### 3. Generated migration with independent cross-check

The migration SQL is a committed generated artifact inside the B package so runtime installation does not depend on repository Markdown. A test-only generator parses the mapping machine block and compares SQLite introspection with every mapped table, column, check, index and foreign key.

The runtime does not parse Markdown, does not import shared acceptance Oracle data and does not self-generate expected test outcomes.

### 4. Failure and logging boundary

Migration code reports a stable technical error code and stage. It does not insert a dietary record or a technical log into the business database. A future separate redacted logger may record the error outside this database. Logger success or failure can never change migration commit/rollback behavior.

Because this task has no repository write API, every business table remains empty after successful initialization and after every failure injection.

## Public/internal API boundary

```ts
export const DIET_DATABASE_FILENAME = "diet-manager-b.sqlite3";

export interface OpenDietDatabaseOptions {
  privateRuntimeRoot: string;
  now?: () => string;
  migrationFault?: "after_schema" | "before_history" | "before_commit";
}

export interface DietDatabaseRuntime {
  readonly databasePath: string;
  readonly database: DatabaseSync;
  close(): void;
}

export function openDietDatabase(options: OpenDietDatabaseOptions): DietDatabaseRuntime;
```

`migrationFault` is private/test-only and must not be exported from the OpenClaw tool or Skill contract. The production wrapper calls a no-fault overload/factory.

## Validation strategy

1. RED: require the fixed path API and migration artifact before they exist.
2. RED: inject all three failure phases and prove no final database, WAL, SHM, business row or partial candidate remains.
3. GREEN: fresh initialization yields exact 20/18/22 mapping structure and zero business rows.
4. Reopen: reject wrong application ID, wrong user version, mapping checksum drift, quick-check/foreign-key failure, root symlink and database-leaf symlink.
5. Package: run focused Vitest, TypeScript, build and local OpenClaw plugin validation without invoking a model.
