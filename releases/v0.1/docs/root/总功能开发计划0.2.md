# 饮食管家总功能开发计划 0.2

> **供执行代理使用：** 实施本计划时，必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`，按唯一任务台账逐项执行；任何任务开始前先编写对应的文件级实施计划，步骤使用 `- [ ]` 复选框追踪。

**目标：** 建成一个以本人日常饮食事实为核心，能够可靠记录饮食与白水、安全关联家庭库存、追溯营养来源、追加纠错并提供日常进度与回顾的饮食管家。

**架构：** 对话层负责理解用户自然语言和组织简洁回执；共同领域层负责事件、商品、库存、营养、异常、纠错与进度语义；A/B/C 三条路线只用于验证不同实现边界，并通过早期决策门淘汰不值得继续的路线。产品约束、任务状态、验证证据和技术决策均在本文件中保持唯一事实来源。

**技术栈：** Windows PowerShell、OpenClaw、Markdown/JSON Schema、A 路线固定 JSONL、B/C 路线 TypeScript + Node.js + 固定 SQLite、共享自然语言验收案例与隔离测试数据。

## 全局约束

- 本文件的文档版本是 `DOC-0.2`；产品目标版本分别为 `PRODUCT-0.1` 与 `PRODUCT-0.2`，两者不得混淆。
- `A/B/C foundation 0.1` 验证通过只代表工程基底可构建、可测试，不代表饮食管家产品已经完成。
- 当前产品不可作为正式饮食管家安装使用；任何安装说明在发布门通过前只能标记为开发验证用途。
- 测试、构建、插件验证和计划校验不得创建或修改正式 JSONL/SQLite 业务数据。
- 只有已经持久化完成的事务才能返回 `committed`；预览、失败、忽略和未提交片段不得进入查询、汇总或进度。
- 已发生且可识别的饮食事实优先保存；库存、营养、数量或关联问题应降级为异常，不得无故丢失事实。
- 用户原话与系统推导必须分开保存；明确事实不能被规范化名称、模板、估算或互联网资料覆盖。
- 未知营养不是零；部分合计不得冒充完整合计。
- 库存不得为负；多商品候选不得擅自选择；同一提交重试不得重复写入或重复扣减。
- 更正、冲销、库存补偿和营养重算必须保留审计链，不得物理覆盖原始业务记录。
- 用户配置的目标只用于进度展示，不构成健康判断、建议、诊断或治疗意见。
- 模拟示例中的目标、克重、容量、保质天数和营养值只用于说明格式，不是系统默认常量。

## 1. 本文件如何成为单一事实来源

### 1.1 信息归属

| 信息类型 | 唯一可写位置 | 其他章节的处理方式 |
| --- | --- | --- |

### 1.2 规范性语言

- **必须：** 不满足即验收失败。
- **不得：** 零容忍禁止行为。
- **应当：** 默认行为，只有存在已登记且生效的例外决定才能偏离。
- **可以：** 可选增强，不得阻塞更高优先级需求。
- **示例：** 用于说明，不自动成为默认常量、默认配方或默认目标。

### 1.3 状态体系

任务状态只允许：

```text
未开始
进行中
阻塞
已完成
已取消
```

需求处置只允许：

```text
0.1 必须
0.2 必须
后续候选
明确排除
已取代
```

路线状态只允许：

```text
实验中
有限对照
暂停
停止
发布候选
已发布
```

这些状态属于不同对象，不得混写成“基底已完成，业务未实现”之类的自由状态。

### 1.4 完成定义

任务只有同时满足以下条件才能标记为 `已完成`：

1. 交付物存在于任务指定路径。
2. 任务关联的正常、边界和失败案例全部通过。
3. 相关回归测试通过。
4. 实际验证发生在相关文件最后一次修改之后。
5. 任务引用至少一个有效 `EV-*` 证据。
6. 验证使用隔离测试数据，业务数据前后扫描符合预期。
7. 没有未登记的范围变化、接口变化或数据迁移。
8. 需要独立复核的任务已经由复核角色确认。

### 1.5 计划维护纪律

- 全局 WIP 上限为一个共享任务；路线试验阶段允许 A/B/C 各一个相互独立的进行中任务。
- 开发前必须确认依赖、预期交付物、验证命令和业务数据路径。
- 开发后只更新唯一任务台账、证据台账、风险/决策台账和变更记录。
- 需求冻结后新增 `0.1 必须`，必须登记变更请求并说明价值、成本、依赖和被推迟工作。
- 被 G1/G2 停止的路线，其后续任务标记 `已取消`，不得删除任务历史或伪装成完成。
- 文档摘要与路线矩阵均为引用视图；发现与任务台账冲突时，以任务台账为准并修正摘要。

## 2. 产品定义、版本与边界

### 2.1 产品使命

饮食管家帮助用户用自然语言低摩擦地记录本人已经发生的饮食、白水和购买事实，并在可靠证据允许时自动完成库存关联、营养计算和日进度更新。系统必须允许用户立即纠错、稍后补充异常，并能够准确回答“我在某天吃了什么、喝了多少水、家庭库存发生了什么变化”。

### 2.2 产品对象

| 需求 ID | 处置 | 约束 |
| --- | --- | --- |
| `REQ-SCOPE-001` | 0.1 必须 | 系统只记录当前用户本人，不建设家庭成员、主体切换、家庭成员归属或多人账户模型。 |
| `REQ-SCOPE-002` | 0.1 必须 | 家庭库存是本人饮食的默认库存来源，不代表多人家庭账户。 |
| `REQ-SCOPE-003` | 0.1 必须 | 用户明确描述非本人饮食时，不得写入本人的饮食账本；不创建他人档案。 |
| `REQ-SCOPE-004` | 明确排除 | 不建设“0.3 非医疗健康管理助手”。 |
| `REQ-SCOPE-005` | 明确排除 | 不提供疾病诊断、治疗方案、用药建议或替代专业医疗意见。 |
| `REQ-SCOPE-006` | 0.1 必须 | 用户目标只用于记录进度；系统不得自行生成目标或用目标评价用户。 |
| `REQ-SCOPE-007` | 后续候选 | 云同步、多人、可穿戴设备、健康平台、图像/条码/发票识别不进入 0.1。 |

### 2.3 产品阶段

| 阶段 | 定位 | 必须形成的用户闭环 |
| --- | --- | --- |
| `PRODUCT-0.1` | 可靠日常饮食账本 | 饮食/白水/购买事实 → 库存与营养安全附加效果 → 简洁成功回执 → 追加纠错 → 当日查询与进度 |
| `PRODUCT-0.2` | 记录与回顾助手 | 0.1 全部能力 + 个人常用模板 + 快速复用 + 日/周回顾 + 批量补录 + 趋势与导出 + 主动临期提醒 |

### 2.4 0.1 必须范围

- 本人饮食、白水、购买和查询意图。
- 一餐多项、餐次、补记、相对时间和时区自然日。
- 精确、近似、范围、模糊、分数和缺失数量。
- 家庭库存默认查询、唯一匹配扣减、多批次分配与异常降级。
- 商品身份、营养资料和库存批次分离。
- 入库包装层级、存放位置、开封状态、保质依据和入库回执。
- 常见食物可信营养资料、精确包装标签、透明菜品模板和历史营养复用。
- 异常中心、快捷回复、自然语言补充和追加式纠错/冲销。
- 白水与食物水分分离，六项固定进度回执。
- 今天、昨天、指定日期/餐次的有效记录和已知营养聚合。
- 幂等、原子性、并发、隐私、备份恢复以及零正式数据污染验证。

### 2.5 0.2 必须范围

- 两次一致的用户明确组成形成个人菜品模板，第三次增强稳定性。
- “和昨天早餐一样”“再来一份”等快速复用。
- 常吃食物、常用餐、命名菜品版本和确认过的默认份量。
- 批量补录、按食物筛选、周/月趋势和记录完整性回顾。
- 主动临期提醒、盘点校正、丢弃、退货、赠送和更完整库存生命周期。
- 营养标签版本管理、数据导出、保留与清除流程。

## 3. 不可突破的业务与数据规则

| 需求 ID | 硬规则 |
| --- | --- |
| `REQ-EVENT-001` | 只有已经发生的饮食、白水或购买事实可以进入正式业务账本。 |
| `REQ-EVENT-002` | 尚未发生的计划/假设、明确否定、取消计划和最终未发生事件必须返回 `ignored`，不得写入；已经写入的记录被用户要求“取消/删除”时必须走追加式 `void_event`，不能按未发生事件忽略。 |
| `REQ-EVENT-003` | 已发生且至少包含一个可识别食物的饮食，应优先保存事实；库存或营养异常不得反向否认摄入。 |
| `REQ-EVENT-004` | 每个正式事件必须保存用户原话、消息来源、接收时间、提交时间、Schema 版本和稳定事件 ID。 |
| `REQ-EVENT-005` | 所有规范化、时间解析、单位换算、模板应用、库存匹配和营养选择必须保留来源及规则版本。 |
| `REQ-EVENT-006` | `preview/committed/ignored/failed` 是命令结果；`active/corrected/voided` 是持久化生命周期，二者不得混用。 |
| `REQ-EVENT-007` | 同一幂等键重试必须返回原结果，不得产生第二个事件或第二次库存影响。 |
| `REQ-EVENT-008` | 语义相似但幂等键不同的两条消息只能提示可能重复，不得自动合并或删除。 |
| `REQ-EVENT-009` | 混合输入按叙述顺序拆为多个领域事件，并按事件逐项原子提交。 |
| `REQ-EVENT-010` | 后一个混合事件失败时，前一个已经独立提交成功的事件不回滚；总回执逐项说明状态。 |
| `REQ-EVENT-011` | 基础验证、构建和测试必须使用临时或隔离数据；正式数据路径不得被测试触碰。 |
| `REQ-EVENT-012` | 存储不可用且事实未持久化时必须返回 `failed`，不得声称已记录。 |

### 3.1 事实优先与附加效果降级

饮食命令采用三层处理：

```text
核心事实：发生时间、餐次、原始食物、原始份量
安全附加效果：库存查询/扣减、营养资料/换算、daily_progress
便利增强：模板学习、异常快捷处理、回顾提示
```

- 核心事实明确时应提交。
- 多候选、库存不足、数量不清或营养未知时，附加效果使用稳定的 `skipped_*`、`partial` 或 `unknown` 状态，并创建异常。
- 若计划执行库存扣减，饮食记录与实际扣减必须在同一可靠事务边界中提交；业务前置条件变化应转换为“饮食提交 + 库存跳过异常”，不得产生负库存。
- 若整个存储不可用，则无法满足“事实已保存”，必须失败并允许幂等重试。

## 4. 核心用户旅程

### 4.1 明确饮食

```text
用户原话
→ 判断确实已经发生
→ 解析时间、餐次和多个食物项
→ 默认查询家庭库存（除非明确外食/不扣）
→ 选择营养来源或透明估算
→ 原子提交事实和可靠附加效果
→ 返回逐菜简洁回执
→ 使用同次结果中的 daily_progress 显示进度
```

### 4.2 模糊数量或库存异常

```text
保存用户原始份量
→ 营养有合理范围时采用合理较大值并标明依据
→ 库存没有可靠换算时跳过扣减
→ 建立异常
→ 必要时提供少量快捷方案
→ 用户可稍后用字母、组合选项或自然语言补充
```

### 4.3 商品入库

```text
解析一个或多个商品
→ 创建/匹配 ProductIdentity
→ 创建新的 InventoryBatch
→ 保存包装层级、数量和单位
→ 关联或复用 NutritionProfile
→ 推断存放位置和可追溯保质状态
→ 单商品详细回执 / 多商品每项一行简洁回执
→ 不完整内容进入异常中心
```

### 4.4 纠错与冲销

```text
定位活动预览或最近明确记录
→ 多候选时显示人类可读选项
→ 追加 CorrectionEvent
→ 原子执行库存补偿与营养重算
→ 更新有效视图和受影响日期的 daily_progress
→ 原始记录保持可审计
```

### 4.5 查询与回顾

```text
按用户时区解析日期范围
→ 一次聚合读取有效饮食、白水和进度
→ 排除预览、失败、忽略、旧纠错版本和已冲销记录
→ 明确完整、部分、估算和未知覆盖情况
→ 不产生写入副作用
```

## 5. 事件、时间、餐次与上下文规范

### 5.1 事件类型

| 类型 | 含义 | 默认写入 |
| --- | --- | --- |
| `meal` | 本人已经发生的有营养摄入 | 是 |
| `water` | 本人已经完成的白水或明确白水等价物 | 是 |
| `purchase` | 已发生的购买、制作或库存入库 | 是 |
| `query` | 查询饮食、白水、库存、异常或进度 | 否 |
| `correction` | 更正、移除单项或冲销既有记录 | 追加事件 |
| `ignore` | 尚未发生的计划/假设、明确否定、取消计划或明确非本人事实 | 否 |
| `mixed` | 输入信封中包含两个或更多有序事件 | 拆分后逐事件处理 |

### 5.2 时间模型

| 需求 ID | 约束 |
| --- | --- |
| `REQ-TIME-001` | 同时保存 `occurred_at_text`、解析结果、`received_at`、`committed_at`、时区和解析依据。 |
| `REQ-TIME-002` | 用户没说时间时可以使用接收时间，但必须标记 `default_received_at`。 |
| `REQ-TIME-003` | “中午”等表达保存为时间范围或餐段，不伪造精确 `12:00`。 |
| `REQ-TIME-004` | “昨晚、凌晨、三天前、上周五”等使用可注入时钟、用户时区和解析锚点。 |
| `REQ-TIME-005` | 日查询采用用户时区下 `[日开始, 次日开始)` 半开区间。 |
| `REQ-TIME-006` | 测试必须固定时钟、时区和 locale，覆盖跨午夜和跨月。 |
| `REQ-TIME-007` | 时间解析规则必须有版本；规则升级不得静默改写历史解析结果。 |

建议结构：

```text
OccurredTime
├─ raw_text
├─ resolved_start
├─ resolved_end
├─ precision: exact | date | meal_period | approximate | unknown
├─ timezone
├─ resolution_basis
├─ resolution_anchor
└─ resolver_version
```

### 5.3 餐次

```text
breakfast   早餐
lunch       午餐
dinner      晚餐
snack       加餐
late_snack  夜宵
unknown     未知
```

| 需求 ID | 约束 |
| --- | --- |
| `REQ-MEAL-001` | 同时保存餐次原文、规范餐次和来源。 |
| `REQ-MEAL-002` | 用户明确餐次优先；系统推断必须标记 `system_inferred`。 |
| `REQ-MEAL-003` | 餐次和发生时间分开；凌晨一点不能自动冒充用户明确说过夜宵。 |
| `REQ-MEAL-004` | 一条饮食事件支持多个有序 `items[]`，共享一个 `meal_event_id`。 |

### 5.4 用餐上下文

系统不要求用户每次说“在家”。上下文仅用于决定库存行为：

```text
home_default
external_explicit
delivery_explicit
skip_inventory_explicit
unknown
```

没有明确非家庭证据时按 `home_default` 尝试库存；底层仍应记录这是默认策略而不是用户明确说“在家”。

## 6. 饮食、份量与菜品处理规范

### 6.1 饮食事件最低要求

| 需求 ID | 最低要求 |
| --- | --- |
| `REQ-MEAL-005` | 能确认摄入已经发生。 |
| `REQ-MEAL-006` | 至少有一个可识别食物或菜品名称。 |
| `REQ-MEAL-007` | 保存用户原话和原始食物名称。 |
| `REQ-MEAL-008` | 保存用户时间或带来源的默认发生时间。 |
| `REQ-MEAL-009` | 数量、库存、营养和餐次允许分别不完整，并具有独立状态。 |

### 6.2 份量模型

```text
Amount
├─ raw_text
├─ kind: exact | approximate | range | vague | missing
├─ value
├─ min_value
├─ max_value
├─ unit_raw
├─ unit_normalized
├─ qualifier
├─ conversion_basis
├─ conversion_formula
├─ conversion_source
└─ evidence_kind
```

系统必须分开保存：

1. 用户实际描述的摄入量。
2. 营养计算采用量。
3. 库存实际扣减量。
4. 商品包装及单件规格。

四者不得默认相同。

### 6.3 模糊和缺失数量

| 需求 ID | 约束 |
| --- | --- |
| `REQ-MEAL-010` | 数量模糊或缺失时仍保存饮食事实并创建异常。 |
| `REQ-MEAL-011` | 营养存在可靠合理范围时，默认采用范围内较大值 `upper_plausible_bound`。 |
| `REQ-MEAL-012` | 较大值必须是合理范围上界，不是理论最大值；保存范围、来源和规则版本。 |
| `REQ-MEAL-013` | 营养采用的估算克重不得自动成为库存扣减克重。 |
| `REQ-MEAL-014` | 无可信范围时保持营养未知，不为了完整回执编造数值。 |
| `REQ-MEAL-015` | 分数、小数、范围和近似表达必须可保留，例如半盒、1.5碗、两三片、约200克。 |

### 6.4 食物分类和组合菜

| 类型 | 示例 | 默认处理 |
| --- | --- | --- |
| 常见单一食物 | 鸡蛋、苹果、米饭、牛肉 | 查可信公共资料；自然单位需要推定可食重量时显示依据 |
| 基础食品 | 鲜牛奶、豆浆、馒头、面条 | 使用匹配生熟/规格的可信资料 |
| 精确包装食品 | 某品牌牛奶、饼干 | 优先精确标签、生产商或历史商品资料 |
| 常见边界明确菜品 | 牛肉面、蛋炒饭、番茄炒蛋 | 使用版本化透明菜品模板自动估算 |
| 高度自定义复合食品 | 奇亚籽牛油果青瓜液体沙拉 | 请求配方、用量或标签；可只保存事实 |
| 内容不明套餐/拼盘 | 肉夹馍套餐、自选盒饭、烧烤拼盘 | 必须询问实际包含内容，不自行假设 |

| 需求 ID | 组合规则 |
| --- | --- |
| `REQ-MEAL-016` | 一道菜可以作为整体条目，也可以按组件计算，但同一营养汇总不得同时计入整体和组件。 |
| `REQ-MEAL-017` | 通用模板必须显示主要组成和采用份量，并保留模板版本与来源。 |
| `REQ-MEAL-018` | 用户纠正模板组成后，当前事件立即重算；历史原估算快照保留。 |
| `REQ-MEAL-019` | 套餐内容未知时先保存“吃了该套餐”的事实，营养保持未知并建立组合内容异常。 |

## 7. 家庭库存匹配与扣减规范

### 7.1 默认行为

| 需求 ID | 约束 |
| --- | --- |
| `REQ-PANTRY-001` | 未出现非家庭证据时，默认读取库存并尝试关联和扣减。 |
| `REQ-PANTRY-002` | 明确外面、餐馆、公司食堂、朋友家、堂食、外卖等非家庭场景时，不读取也不扣减家庭库存。 |
| `REQ-PANTRY-003` | 用户明确说“只记录”“别扣库存”时，跳过库存读取和扣减。 |
| `REQ-PANTRY-004` | 库存跳过原因必须形成稳定状态，不得只存在于回复文字。 |

### 7.2 商品匹配证据

匹配依次使用：

```text
精确 product_id / 条码
→ 规范化名称 + 品牌 + 变体 + 规格
→ 用户确认过的别名
→ 原始名称的唯一历史匹配
→ 当前对话可靠指代
→ 名称相似候选
```

每次匹配保存：

```text
match_status
candidate_product_ids[]
matched_product_id
match_evidence[]
match_rule
match_rule_version
```

置信度只能辅助解释，不能替代证据。

### 7.3 匹配结果与行为

| 状态 | 含义 | 饮食 | 库存 |
| --- | --- | --- | --- |
| `unique` | 唯一可靠商品且单位可处理 | 提交 | 充足时扣减 |
| `multiple` | 多个不同商品身份候选 | 提交 | 跳过并建立 `ambiguous_inventory_match` |
| `none` | 无可靠库存候选 | 提交 | 跳过；可低优先级提示漏记入库 |
| `insufficient` | 商品明确但库存不足 | 提交 | 不产生负数，跳过并建立异常 |
| `unconvertible` | 商品可能明确但单位无法可靠换算 | 提交 | 跳过精确扣减并建立异常 |

对应库存影响状态：

```text
deducted
skipped_external
skipped_by_user
skipped_no_match
skipped_ambiguous
skipped_insufficient
skipped_vague_quantity
skipped_unconvertible_unit
reversed
```

### 7.4 同商品多批次

| 需求 ID | 约束 |
| --- | --- |
| `REQ-PANTRY-005` | 同一商品身份的多个批次不属于 `multiple` 商品歧义。 |
| `REQ-PANTRY-006` | 用户明确指定批次时优先使用该批次。 |
| `REQ-PANTRY-007` | 有可靠到期依据时采用 FEFO；没有可靠到期依据时采用 FIFO。 |
| `REQ-PANTRY-008` | 一次摄入可以跨同一商品的多个批次原子分配。 |
| `REQ-PANTRY-009` | 已过期批次默认不自动选择；用户明确选择时必须提示状态并保留证据。 |
| `REQ-PANTRY-010` | 并发扣减不得共同超扣同一批次。 |

### 7.5 延迟处理

用户稍后处理库存异常时，必须重新检查饮食有效性、异常状态、商品身份、批次剩余量、换算依据和是否已经处理。旧快捷选项不能绕过重新校验。

## 8. 商品入库、批次与生命周期规范

### 8.1 三层实体

```text
ProductIdentity  商品长期身份
NutritionProfile 可版本化营养资料
InventoryBatch   某次实际入库批次
```

库存耗尽只把 `InventoryBatch` 变为 `depleted`；不得删除商品身份、营养资料、别名或历史事件。

### 8.2 商品身份最低字段

| 字段 | 规则 |
| --- | --- |
| `raw_name` | 必须保留用户原始名称 |
| `normalized_name` | 用于检索，不能覆盖原名 |
| `product_type` | 食材、基础食品、包装食品、饮料、复合食品或 `unknown` |
| `brand` | 用户、标签或可靠商品资料提供时保存 |
| `variant` | 口味、脂肪类型、型号或其他变体 |
| `confirmed_aliases[]` | 只有可靠证据或用户确认后长期保存 |
| `packaging_variants[]` | 保存不同包装规格，不与商品身份混为一个批次 |
| `nutrition_profile_ids[]` | 关联一个或多个版本化营养资料 |
| `status` | `active/historical/merged/superseded` |

### 8.3 入库批次最低字段

| 需求 ID | 最低字段 |
| --- | --- |
| `REQ-PANTRY-011` | `batch_id`、`product_id`、`source_text`、购买/制作时间原文、解析时间、接收时间、提交时间。 |
| `REQ-PANTRY-012` | 原始数量、数量类型、外层包装数/单位、内层数量/单位、单件规格、推导总量和公式。 |
| `REQ-PANTRY-013` | 原始入库量和当前剩余量分开；未知剩余量必须为 `unknown`，不得写成 0。 |
| `REQ-PANTRY-014` | 保存数据来源、推导字段、解析/换算规则版本、数据质量和 `issues[]`。 |
| `REQ-PANTRY-015` | 每次购买默认创建新批次；同名商品再次购买不能覆盖旧批次。 |

包装示例的正确存储方式：

```text
2箱 × 12盒/箱 = 24盒
24盒 × 250ml/盒 = 6000ml
```

系统必须同时保留“2箱、每箱12盒、每盒250ml”和推导总量，不能只剩 6000ml。

### 8.4 缺失和异常数量

- “买了牛奶”：商品存在，数量 `missing`，剩余量 `unknown`，建立 `missing_quantity`。
- “买了一袋鸡蛋”：已知 1 袋，不是数量缺失；未知的是袋内个数，建立 `missing_package_content`。
- 包装规格互相冲突：保存可确定事实，对冲突数量使用 `needs_confirmation`，不生成不可靠总量。
- 没有营养资料、品牌或保质期通常不阻止入库。

### 8.5 存放位置

位置判断优先级固定为：

```text
用户明确指定
→ 商品标签
→ 用户确认过的同商品规则
→ 商品类型默认规则
→ unknown
```

| 需求 ID | 约束 |
| --- | --- |
| `REQ-PANTRY-016` | 系统可以推断存放位置，但必须保存来源和规则版本。 |
| `REQ-PANTRY-017` | 入库回执显示实际采用的位置；用户可以自然语言纠正。 |
| `REQ-PANTRY-018` | 正常明确判断不显示位置快捷修改；只有多个合理位置影响保质或库存时才提供选项。 |

### 8.6 开封和保质

开封状态：

```text
sealed
opened
unknown
depleted
```

首次对明确未开封独立包装执行部分取用时，可以按饮食发生时间推断 `opened_at`，但必须标记 `inferred_from_first_partial_consumption`。不知道具体包装、包装层级不明或库存异常时保持未知。

保质依据优先级：

```text
用户明确到期日
→ 商品标签到期日
→ 生产日期 + 明确保质期
→ 开封时间 + 标签开封后期限
→ 购买时间 + 可靠规则
→ 入库时间 + 商品/位置默认规则
→ unknown
```

| 需求 ID | 约束 |
| --- | --- |
| `REQ-PANTRY-019` | 推算到期或剩余天数必须显示“估算/预计”，保存锚点、规则版本、时区和存放条件。 |
| `REQ-PANTRY-020` | 没有足够规则时不得编造天数，应显示最有价值的制作、生产、购买或入库时间锚点。 |
| `REQ-PANTRY-021` | “剩余几天”是查询时动态计算的展示值，不每日改写原始入库记录。 |
| `REQ-PANTRY-022` | 位置或开封状态变化后重新计算有效估算，并保留旧估算审计记录。 |
| `REQ-PANTRY-023` | 临期提示只是库存管理信息，不保证食品安全。 |

### 8.7 入库回执

单商品允许详细回执：

```text
已入库：蒙牛全脂纯牛奶
数量：2箱，共24盒
规格：250ml/盒
存放：冷藏
保质状态：估算剩余3天
营养资料：已关联
```

多商品每项一行：

```text
已入库4项：
蒙牛全脂纯牛奶 24盒/2箱｜250ml/盒（冷藏），估算剩余3天
鸡蛋 1袋（冷藏）｜袋内数量待完善
冷冻水饺 3袋（冷冻）｜估算剩余90天
调理包 2袋（位置待确认）｜9号入库，类别与保质期待确认
```

上述商品、数量和天数均为格式示例，真实回执必须来自实际输入、商品资料和版本化规则。

## 9. 营养资料、互联网来源与计算规范

### 9.1 营养来源优先级

```text
当前包装的精确营养标签
→ 生产商或精确商品资料
→ 已确认的同一商品历史 NutritionProfile
→ 权威公共营养数据库
→ 配置白名单内的可信互联网资料
→ 版本化常见菜品模板
→ 通用估算
→ unknown
```

| 需求 ID | 约束 |
| --- | --- |
| `REQ-NUTR-001` | 高优先级来源存在且适用时，不得用低优先级来源冒充或覆盖。 |
| `REQ-NUTR-002` | 常见原始食材和基础食品应主动查询本地可信缓存、权威数据库或可信来源，不要求用户上传标签。 |
| `REQ-NUTR-003` | 包装食品、精加工食品和高度自定义复合食品优先使用精确商品资料、生产商资料、标签或用户配方。 |
| `REQ-NUTR-004` | 不得把普通牛奶、普通果蔬汁等通用数据套用到配方差异明显的加工饮料。 |
| `REQ-NUTR-005` | 完全没有可靠资料时保存 `unknown`，不得编造来源或把缺失字段补成 0。 |

### 9.2 外部资料获取

外部查询顺序：

```text
本地已确认资料
→ 本地可信缓存
→ 权威公共营养数据库
→ 生产商官方资料
→ 配置白名单内的可信网站
```

每份外部资料至少保存：

```text
source_type
source_name
source_ref_or_url
source_version
retrieved_at
food_or_product_match
applicable_variant
basis_amount
basis_unit
applicable_scope
```

外部请求只能发送完成匹配所需的食物/商品名称、品牌、变体和规格；不得发送整段用户原话、饮食日期、对话内容、库存数量或存放位置。

### 9.3 营养最低字段和基准

0.1 固定支持：

```text
energy_kcal / energy_kj
protein_g
fat_g
carbohydrate_g
fiber_g
sodium_mg（资料存在时）
```

允许基准：

```text
per_100g
per_100ml
per_serving
per_item
per_package
custom
```

每份资料必须明确基准量、基准单位、份名和每包装份数；来源没有某字段时保持缺失。

### 9.4 明确数据、参考数据与估算标签

| 需求 ID | 约束 |
| --- | --- |
| `REQ-NUTR-006` | 用户明确提供的数量、包装标签、确定性单位换算不显示“估算”。 |
| `REQ-NUTR-007` | 精确匹配同一商品版本并沿用历史营养表时，显示“沿用历史营养表”，不显示“估算”。 |
| `REQ-NUTR-008` | 已激活个人菜品模板显示“按个人模板”，不显示“估算”。 |
| `REQ-NUTR-009` | 数量明确且营养密度来自可信公共数据库时，简洁回执不强制显示“估算”；详情必须可追溯为“参考数据库”。 |
| `REQ-NUTR-010` | 根据自然单位、可食部分、密度、出成率或通用菜品模板推定的字段必须显示具体采用值和依据。 |
| `REQ-NUTR-011` | 只有部分字段经过推定时，只标记相应字段，不得笼统把整条记录标为估算。 |

示例：

```text
米饭200g
牛奶1瓶｜250ml
橙子1个｜按可食部分200g估算
牛肉面1碗｜牛肉80g（估算）、面条100g、青菜50g（估算）
```

示例中的数值不是默认份量。

### 9.5 营养快照

每个饮食项目在提交时保存不可变 `NutritionSnapshot`：

```text
snapshot_id
meal_event_id
meal_item_id
profile_id
profile_version
source_type
source_ref
basis_amount
consumed_amount
conversion_formula
raw_values
rounded_values
rounding_rule
estimated_fields[]
known_fields[]
missing_fields[]
coverage_status
created_at
```

历史饮食继续使用提交当时的快照。新标签或新数据库版本不得静默改变历史；用户要求重新计算时必须形成营养更正事件。

### 9.6 计算精度与覆盖

- 内部计算使用稳定精度，展示时统一舍入；展示后的舍入值不得反向参与累计。
- `complete`：要求的核心字段均有可靠结果。
- `partial`：部分字段或部分项目未知。
- `estimated`：关键值来自有依据的估算。
- `unknown`：没有可靠营养结果。
- 只要存在未计入项目，日合计必须说明“已知部分合计”和覆盖范围，不能称为“今日总摄入”。

### 14.3 固定六项格式

目标确认时顺序固定：

| 顺序 | 指标 | 固定 Emoji | 当前/目标单位 |
| ---: | --- | --- | --- |
| 1 | 热量 | `🔥` | kcal / kcal |
| 2 | 蛋白 | `🥩` | g / g |
| 3 | 脂肪 | `🧈` | g / g |
| 4 | 碳水 | `🌾` | g / g |
| 5 | 纤维 | `🥬` | g / g |
| 6 | 饮水 | `💧` | ml / L |

每项严格两行：

```text
Emoji + 名称 + 10格进度条 + 百分比
Emoji + 当前量 / 目标 + 可选本轮增量
```

公式：

```text
percentage = round(current / target * 100)
filled = clamp(round(current / target * 10), 0, 10)
increment_percentage = round(increment / target * 100)
```

| 需求 ID | 约束 |
| --- | --- |
| `REQ-PROGRESS-006` | 进度条恰好10格，只使用 `█` 和 `░`。 |
| `REQ-PROGRESS-007` | 超目标保留真实百分比，进度条最多10格满格。 |
| `REQ-PROGRESS-008` | 只显示同次结果返回的正增量，格式 `+amount unit +percent`；零/缺失省略。 |
| `REQ-PROGRESS-009` | 正增量低于1%显示 `+<1%`，不加括号。 |
| `REQ-PROGRESS-010` | 纤维明确未知时显示“未知”，不得显示为0。 |
| `REQ-PROGRESS-011` | 饮水当前量和增量用 ml，目标用 L；计算前统一单位。 |
| `REQ-PROGRESS-012` | 所有非负进度值统一使用十进制 `round_half_up` 取整；不得让 PowerShell、JavaScript、SQLite 的默认 `.5` 行为产生不同结果。 |
| `REQ-PROGRESS-013` | 没有确认目标时先明确“目标未配置，进度条不可用”，随后只按固定顺序显示已有累计量；不显示百分比、10格条或当前轮百分比。 |
| `REQ-PROGRESS-014` | 饮水存在未知贡献且有目标时，用已知下界计算 `known_min_percentage` 和进度条，并显示 `≥百分比`；第二行写“已知至少…，另有饮品水分未知”。不得把该下界称为精确当前量。 |

每项两行必须重复对应固定 Emoji。纤维当前值明确未知但目标已配置时固定显示：

```text
🥬 纤维 ░░░░░░░░░░ 未知
🥬未知 / 30 g
```

10个 `░` 只是未知值的版式占位，不代表0；实际目标来自用户配置。没有确认目标时固定以：

```text
目标未配置，进度条不可用。
🔥 热量 1874 kcal
🥩 蛋白 82.3 g
……其余已有/未知指标按固定顺序各一行
```

展示；示例值不是默认值，也不得出现百分比或本轮百分比。

饮水贡献部分未知且目标已配置时固定采用：

```text
💧 饮水 ██░░░░░░░░ ≥20%
💧已知至少500ml / 2.5L｜另有饮品水分未知
```

其中 `known_min_percentage = round_half_up(progress_water_known_min_ml / target_ml * 100)`，进度条只表示已知下界。若当前轮还有已知饮水增量，可按原格式追加该已知增量；未知部分只显示“本轮另有饮品水分未知”，不得伪造增量。

格式示例中的目标和数值仅用于验收排版，不得成为新用户默认目标。

## 15. 查询、日回顾与周回顾

### 15.1 0.1 查询

| 需求 ID | 0.1 要求 |

| `REQ-QUERY-002` | 按早餐、午餐、晚餐、加餐、夜宵筛选有效记录。 |
| `REQ-QUERY-003` | 查询原始记录、当前有效结果和纠错历史。 |
| `REQ-QUERY-004` | 查询当日已知营养、未知项目、估算项目和覆盖状态。 |

## 16. 共同领域模型与存储映射

### 16.1 模型清单

| 模型 | 单一职责 |
| --- | --- |
| `EventEnvelope` | 所有事件的稳定 ID、来源、时间、版本和生命周期 |
| `MealEvent` | 一餐及有序摄入项 |
| `MealItem` | 单项原名、规范名、份量、营养快照和库存影响 |
| `WaterEvent` | 白水原始容器、标准容量和估算依据 |
| `ProductIdentity` | 跨批次长期商品身份、别名和包装变体 |
| `InventoryBatch` | 一次入库的数量、包装、位置、开封和保质状态 |
| `InventoryTransaction` | 入库、扣减、返还、盘点、丢弃和退货事件 |
| `NutritionProfile` | 版本化营养资料及适用商品/食物 |
| `NutritionSnapshot` | 某次摄入实际采用的营养计算结果 |
| `HydrationContributionSnapshot` | 饮食液体的实际体积、食物水分来源/公式/估算状态及对进度的单次贡献 |
| `PersonalDishTemplate` | 通用/个人菜品模板、版本和证据 |
| `Issue` | 异常、资料缺口或阻塞问题 |
| `IssueResolutionEvent` | 后续补充和解决结果 |
| `CorrectionEvent` | 追加式更正、删除单项或整条冲销 |
| `DailyProgressSnapshot` | 同次成功提交后的权威日聚合 |
| `IdempotencyRecord` | 请求键、输入摘要和原提交结果引用 |
| `ProvenanceEvidence` | 用户、标签、外部资料、规则和推导的可追溯证据 |

### 16.2 每个模型必须说明

- 字段名称与类型。
- 必填、可空或明确 `unknown`。
- 原始字段、推导字段或聚合字段。
- 来源类型、来源引用和规则版本。
- Schema 版本与迁移策略。
- 生命周期、纠错和保留方式。
- JSONL 与 SQLite 映射。
- 隐私等级和日志脱敏规则。

### 16.3 A 路线 JSONL

- 固定数据目录，普通对话不得指定路径。
- 每行完整合法 JSON 对象。
- 原始事件不可改写；更正和事务状态使用追加事件。
- 必须通过权威事务日志、提交标记或等价机制保证跨对象一致性；读取忽略未提交片段。
- 追加中断不得破坏既有行。
- 若无法证明幂等、原子性、固定路径和损坏恢复，A 在 G1 停止正式写入开发。

### 16.4 B/C 路线 SQLite

- 固定数据库路径，不接受模型提供任意路径。
- 使用外键、唯一约束、检查约束和事务。
- Schema 迁移有版本、前置备份、失败回滚和兼容检查。
- 预览、幂等、业务事件、库存变化和纠错必须在服务端验证。
- C 的状态不能信任调用方自报；提交使用服务端保存的 `preview_id + preview_version/hash`。
- B/C 即使复用共享存储模块，也必须分别完成插件集成和路线验收。

## 17. 非功能、安全、隐私与运维约束

### 17.1 正式写入硬安全线

| 需求 ID | 规则 |
| --- | --- |
| `REQ-SAFE-001` | 只有完整持久化成功后才能返回 `committed`；返回成功而实际未写、只写一半或写到错误位置均为零容忍缺陷。 |
| `REQ-SAFE-002` | 同一 `idempotency_key` 重试必须返回原 `CommitResult`，不得重复记录、扣减、返还、学习模板或累计进度。 |
| `REQ-SAFE-003` | 任意并发、故障和纠错路径都不得产生负库存；库存不足时提交饮食事实、跳过无法完成的库存效果并登记问题。 |
| `REQ-SAFE-004` | 一项业务事件中的事件、实际库存效果、营养快照、问题、幂等结果和最终进度必须位于同一可证明原子边界。 |
| `REQ-SAFE-005` | 普通自然语言不得指定任意读写路径；所有正式数据根由实现固定配置，测试数据根由测试框架隔离注入。 |
| `REQ-SAFE-006` | 损坏 JSONL 尾部、SQLite 事务失败、迁移失败或结果响应丢失必须失败关闭，不得猜测提交成功。 |
| `REQ-SAFE-007` | 查询、进度和回顾只读取有效且已提交的事件视图，不得读取预览、未提交片段或已被纠错替代的旧值。 |
| `REQ-SAFE-008` | 混合输入按叙述顺序逐事件提交；已经完成的前一事件不因后一事件失败而回滚。 |
| `REQ-SAFE-009` | 所有数值必须与单位成组校验；未知使用缺失或显式 `unknown`，不得用 `0`、空字符串或默认一份代替。 |
| `REQ-SAFE-010` | 业务关键数值跨 JSONL/SQLite 使用规范十进制表示或等价精确方案，避免实现路线间的二进制浮点漂移。 |

任何路线只要出现一次未解释的错误正式写入、重复副作用、负库存、半事务或路径越界，就不能靠其他评分补偿，必须留在风险验证阶段或停止正式写入路线。

### 17.2 验证与正式业务数据隔离

| 需求 ID | 规则 |
| --- | --- |
| `REQ-NFR-001` | 测试、构建、插件验证、Schema 校验和计划校验只可写系统临时目录或路线专属测试目录。 |
| `REQ-NFR-002` | 每个工程门都必须记录正式业务数据扫描的路径、文件数、大小、哈希和修改时间；不能只写“未发现异常”。 |
| `REQ-NFR-003` | 验证允许项目中未来已经存在正式数据，但必须证明前后没有新增、修改或删除任何正式 `.jsonl`、`.sqlite`、`.sqlite3` 或 `.db`。 |
| `REQ-NFR-004` | `shared\validate-foundations.ps1` 必须继续使用隔离的 OpenClaw 临时状态，并在退出后恢复调用者环境、清理临时目录。 |
| `REQ-NFR-005` | 故障注入结束后必须验证：无半事务、无负库存、无重复效果、无正式数据污染、重新启动后投影一致。 |
| `REQ-NFR-006` | 禁止测试通过普通环境变量或对话内容把数据根指向正式目录；测试适配器必须显式声明临时根。 |

### 17.3 隐私、联网和日志

默认本地存储，不默认云同步、遥测或跨设备共享。联网营养查询是资料补全能力，不得把用户完整生活记录发送到外部服务。

| 需求 ID | 规则 |
| --- | --- |
| `REQ-PRIV-001` | 外部营养请求只发送匹配所必需的规范化食物名、品牌、变体、包装规格、生熟状态和最小类别。 |
| `REQ-PRIV-002` | 禁止发送完整原话、会话标识、饮食日期/餐次、库存数量、存放位置、购买地点、异常列表、个人模板历史或完整数据库。 |
| `REQ-PRIV-003` | 外部资料必须经过来源登记表；保存来源、版本/抓取时间、匹配条件、允许字段和缓存键。 |
| `REQ-PRIV-004` | 日志默认只写错误码、事件 ID、规则版本和必要技术上下文；不得写完整用户原话、数据库转储、营养图片或访问密钥。 |
| `REQ-PRIV-005` | 访问密钥不得写入 JSONL、SQLite、验收 fixture、日志或版本库；缺少密钥时不得阻止保存饮食事实。 |
| `REQ-PRIV-006` | 备份、导出、整库清除和云端传输必须由用户明确触发；卸载默认不得静默删除业务数据。 |
| `REQ-PRIV-007` | 面向用户的错误信息不得暴露绝对数据路径、SQL、堆栈或内部记录 ID。 |

外部服务不可用时：保存饮食事实，营养标记为缓存命中、暂缺或待补全；不得因为联网失败把已发生饮食降为 `failed`。

### 17.4 备份、恢复、迁移和卸载

| 需求 ID | 规则 |
| --- | --- |
| `REQ-OPS-001` | 每次破坏兼容的数据迁移前自动创建可验证备份；备份清单包含产品版本、Schema 版本、文件哈希、记录数和最后提交时间。 |
| `REQ-OPS-002` | 恢复流程固定为：预检 → 当前数据备份 → 在临时位置恢复 → Schema/哈希/投影校验 → 原子切换。 |
| `REQ-OPS-003` | 恢复默认不静默合并或覆盖；目标已有数据时必须给出清晰选择和后果。 |
| `REQ-OPS-004` | 迁移带版本、校验和、前置条件和失败回滚；失败不得误写新 Schema 版本。 |
| `REQ-OPS-005` | 安装说明必须区分开发基底验证与正式产品安装；只有 `G3` 通过后才能称为正式可安装版本。 |
| `REQ-OPS-006` | 卸载必须分别提供“保留业务数据”和“删除业务数据”路径；删除业务数据需要明确二次确认。 |
| `REQ-OPS-007` | 发布包必须包含受支持环境、依赖、安装、升级、备份、恢复、卸载、回滚、校验和和已知限制。 |
| `REQ-OPS-008` | 兼容版本以发布门实际验证环境为准；当前 foundation 对 Node/OpenClaw 的要求只能作为证据，不得永远固化为产品假设。 |

### 17.5 可维护性与诊断

- 对话层不直接拼 SQL、修改任意路径或计算隐藏累计；它只调用共同业务命令并渲染结构化结果。
- 领域规则不依赖回执中文文本；回执来自 `receipt_data`，不得反向解析回执作为业务事实。
- 规则、来源、菜品模板、Schema 和迁移都必须版本化。
- 每个用户可见异常必须有稳定 `issue_code`；每个技术失败必须有稳定 `error_code`。
- 诊断信息必须足以回答“采用了什么事实、哪条规则、哪个来源、是否提交、影响了哪些日期”，同时遵守隐私最小化。
- 正确性、安全和可追溯性优先于响应速度。联网慢或资料缺失不得阻止事实记录；性能目标只允许在实际基准测量后通过决策记录设定。

## 18. 需求—案例—任务—证据追踪与验收 Oracle

### 18.1 追踪链

每个可发布行为必须形成完整链条：

```text
用户决定/产品规则
→ REQ-* 稳定需求
→ CASE-* 验收场景
→ SH/A/B/C/X 任务
→ 精确交付物
→ 实际测试命令
→ EV-* 证据
→ DEC-* 发布或路线决定
```

需求阶段映射固定如下；`shared\traceability\requirements.json` 仍需为每条需求逐项保存 `stage`、`status`、`source` 和 `contract_version`，不得只依赖前缀猜测：

| 阶段 | 需求前缀/范围 |
| --- | --- |
| `PRODUCT-0.1` | `REQ-EVENT-*`、`REQ-TIME-*`、`REQ-MEAL-*`、`REQ-PANTRY-*`、`REQ-PRODUCT-*`、`REQ-NUTR-*`、`REQ-ISSUE-*`、`REQ-QUICK-*`、`REQ-CORR-*`、`REQ-RECEIPT-*`、`REQ-WATER-*`、`REQ-PROGRESS-*`、`REQ-QUERY-*` |
| `PRODUCT-0.2` | `REQ-TEMPLATE-*`、`REQ-REVIEW-*`、`REQ-LIFE-*`、`REQ-EXPORT-*` |
| 跨阶段硬约束 | `REQ-SAFE-*`、`REQ-NFR-*`、`REQ-PRIV-*`、`REQ-OPS-*` |
| 逐项指定 | `REQ-SCOPE-*` 已在第2节每行标明0.1、0.2、排除或候选，不使用统一前缀阶段。 |

文档中的 `REQ-X-*`、`CASE-X-*` 区间或通配写法只用于阅读压缩；机器追踪表和实际证据必须展开为每个具体 ID。

任一环缺失时，不得把任务标成已完成：

- 需求没有案例：属于不可验证需求。
- 案例没有 Oracle：属于示例，不是验收。
- 任务没有交付物路径：属于愿望，不是任务。
- 完成交付物但没有新鲜证据：属于未验证成果。
- 证据没有关联任务和案例：属于孤立日志。

### 18.3 Oracle 必填项

| 范围 | 必填断言 |
| --- | --- |
| 固定环境 | `clock`、`timezone`、`locale`、`week_start`、来源 fixture 版本。 |
| 上下文 | 先前消息、活动预览/最近事件、库存种子、营养资料、个人模板、目标。 |
| 命令结果 | 意图、`command_status`、稳定原因码、事件数和事件类型。 |
| 时间 | 原始时间文字、解析范围、解析依据、最终日期展示。 |
| 数量 | 原始量、营养采用量、库存请求量、库存实际量及各自证据。 |
| 库存 | 是否读取、匹配候选、批次分配、前后值、跳过原因、不得为负。 |
| 营养 | 来源类型/版本、基准量、公式、已知/未知字段、覆盖率、字段级估算。 |
| 问题 | `issue_code`、类型、状态、可选解决和是否展示快捷选项。 |
| 提交 | 事务 ID、幂等键、重试结果、最终有效视图、禁止副作用。 |
| 回执 | 黄金文本或结构断言、日期格式、逐菜换行、估算标记、自由文本末行。 |
| 进度 | 提交后累计、当前轮增量、目标、未知纤维、水分拆分和最终格式。 |
| 外部请求 | 请求次数、允许字段、缓存结果和禁止泄露字段。 |

故障案例还必须包含：

```text
注入点
预状态哈希
期望错误码
是否应回滚
后状态哈希
重启后状态
同键重试结果
正式业务数据前后差异
```

### 18.4 案例 ID 与维护规则

- 统一使用 `CASE-<领域>-<三位数>`，例如 `CASE-MEAL-001`。
- 已发布 ID 不得改变含义；规则改变时新增案例或升级契约版本。
- 同一行为在 A/B/C 使用同一 Oracle，只允许适配器不同。
- 示例数值必须由 fixture 提供；不得在实现里硬编码案例中的 1900 kcal、200g 橙子或 3 天保质期。

## 21. A/B/C 路线、决策门与里程碑

### 21.1 三条路线的目的

| 路线 | 核心假设 | 必须证明的优势 | 主要风险 |
| --- | --- | --- | --- |
| A：纯 Skill + JSONL | 最少插件代码也能实现可靠本地账本 | 简单、透明、易检查、低安装成本 | 对话驱动写入漂移、跨对象原子性、并发、坏尾恢复。 |
| B：轻量插件 + SQLite | 领域服务和事务数据库能以较低复杂度保证安全 | 正式写入可靠、可维护、安装可控 | Node/OpenClaw/SQLite 驱动兼容与打包。 |
| C：强约束插件 + 状态机 + SQLite | 服务端状态可以进一步减少错误提交 | 陈旧预览、非法跳转和高风险写入更安全 | 状态复杂度、交互迟滞、重复实现。 |

路线不是产品功能分支。三条路线必须服从同一业务契约、数据语义、案例 Oracle 和回执格式；不允许借“路线特色”改变用户规则。

### 21.2 决策门共同规则

- 决策门不保存独立任务状态；执行状态来自第 22 节对应 `X-GATE-*` 任务。
- 每次门结论必须有一条 `DEC-*` 和一组新鲜 `EV-*`。
- 先判硬安全，再评分；硬安全失败的路线没有评分资格。
- 未获准继续的路线必须在决定生效后将条件任务标为“已取消”，并引用决定；不得长期保留为虚假待办。
- 被停止路线中有价值的设计必须通过明确合并任务迁移，不能靠口头记忆。

### 21.3 G0：工程基底与数据卫生门

目的：证明 A/B/C 可以继续进行工程实验，并证明基础验证不会写业务数据。

进入条件：三个路线目录、共享目录、基础入口和 `shared\validate-foundations.ps1` 存在。

必须通过：

1. A 目录、Skill、固定存储边界和基础测试通过。
2. B 测试、TypeScript 构建、插件构建检查和插件验证通过。
3. C 测试、TypeScript 构建、状态机基础检查、插件构建检查和插件验证通过。
4. OpenClaw 临时状态和调用者状态完全隔离。
5. 验证前、验证后和新增 JSONL 业务文件均为 0。
6. 验证前、验证后和新增 SQLite/SQLite3/DB 业务文件均为 0。
7. 临时目录清理，调用者环境恢复，退出码为 0。

当前证据见 `EV-20260809-001` 与 `EV-20260809-002`。G0 通过只代表基底可继续，不代表产品可安装。

### 21.4 G1：存储安全可行性门

执行时点：共同契约、领域模型和安全案例冻结后，任何完整业务路线开发前。

三路线必须执行同一最小存储切片：

1. 创建一个商品和库存批次。
2. 查询批次投影。
3. 提交一条饮食并执行可验证扣减。
4. 使用相同幂等键重试。
5. 在事件准备后、正式提交前注入故障。
6. 在持久化后、返回结果前注入故障。
7. 尝试库存不足扣减。
8. 尝试将数据根指向允许范围之外。
9. 重启后重建查询视图。
10. 再运行 foundation 验证并比较正式业务数据。

路线专项：

- A：安全追加、完整事务包、独占锁/等价互斥、坏尾检测、校验和、幂等、重启投影、多轮稳定性。
- B：驱动兼容、Schema v1、外键/检查/唯一约束、事务回滚、重复迁移、响应丢失重试。
- C：满足 B，并证明服务端预览版本、陈旧预览和非法状态跳转全部拒绝。

硬性指标全部为零：错误正式写入、重复业务副作用、负库存、半事务、路径越界、未处理损坏和 foundation 业务数据污染。高风险案例通过率必须为 100%。

每条路线输出只能是：

- `continue_full`：允许进入共同纵向切片。
- `continue_spike_only`：只允许继续风险验证。
- `read_only_reference`：停止正式写入，只作只读/研究对照。
- `merge_then_stop`：迁移有效设计后停止。
- `stop`：停止投入。

`X-GATE-001` 只有在每条路线的 outcome 和任务处置都写入 `shared\route-gates\g1-task-disposition.json` 后才能完成：

- `continue_full`：激活该路线的 `X-GATE-001:<route>=continue_full` 条件任务，并列出精确任务 ID。
- `continue_spike_only`：把纵向切片保持为“阻塞”，引用对应 `RISK-*`/`Q-*`；同时在第22节创建精确的 `<route>-SPIKE-NNN` 任务，写明风险问题、实验边界、完成证据和重审条件。Spike 完成后必须用 `CHG-YYYYMMDD-NNN` 重新打开 `X-GATE-001` 并以新鲜证据重跑，不能自动升级为 `continue_full`。
- `read_only_reference`：取消该路线所有正式写入和产品任务；若决定要求继续只读研究，必须同时创建精确的 `<route>-REF-NNN` 任务和允许范围，否则该路线没有活动任务。
- `merge_then_stop`：取消除迁移外的后续任务，并在台账创建精确的 `<route>-MERGE-NNN` 任务；迁移完成证据生成后关闭路线。
- `stop`：取消该路线全部条件性后续任务，并让每个取消状态引用本次顺序型 `DEC-NNN`。

任何 outcome 都不得只留一段文字而让分支长期显示“未开始”。新增 Spike/Reference/Merge 任务必须使用下一个未占用 ID，进入同一唯一台账，并在门报告中逐项列出；不得用通配符代替实际任务。

### 21.5 G2：最小纵向切片与投入方向门

共同纵向切片：

```text
购买商品
→ 创建独立批次和营养资料
→ 查询库存
→ 记录在家饮食
→ 默认读取并尝试扣减库存

→ 补偿库存、重算营养和受影响日期进度
```

切片必须同时覆盖：明确量、自然单位、合理上界营养估算、明确外食、多商品候选、库存不足、常见食物资料、包装标签、同商品新批次复用、幂等、故障、逐菜回执、字段级估算、快捷回复和最终进度快照。

先淘汰任何硬安全失败路线，再比较：

| 维度 | 权重 |
| --- | ---: |
| 业务正确性 | 25% |
| 正式写入安全 | 25% |
| 可追溯性 | 15% |
| 可维护性 | 15% |
| 用户交互稳定性 | 10% |
| 安装和运维复杂度 | 10% |

G2 原则上只允许一条路线承担 0.1 完整开发；可以保留一条有限对照路线，但必须在决定里写明允许的任务范围。

G2 必须为每条进入比较的路线给出且只给出一个结果：

- `continue_full`：承担完整 PRODUCT-0.1/0.2 实现。
- `continue_limited`：只执行决定中列出的有限对照或设计迁移任务，不得自行进入 M5。
- `merge_then_stop`：迁移指定设计后停止。
- `stop`：停止后续投入。

8. 没有开放的发布阻断风险或问题。
9. 不可变候选包、版本、校验和、变更记录、已知限制和回滚方法完整；E2E 实际测试的必须是该精确候选包。

输出：`release`、`conditional_release`、`return_to_milestone` 或 `no_release`。`conditional_release` 不得绕过硬安全条件，也**不满足** `X-GATE-003=release` 或 `X-GATE-004=release`，因此不能解锁发布任务。

每次 G3 都必须生成对应的 `g3-*-task-disposition.json`；四种 outcome 的任务处置如下：

- `release`：只激活对应 `X-REL-*`，并绑定候选 manifest 哈希和 promotion target 映射。
- `conditional_release`：表示“候选版本在解决列明的非硬安全条件后可重新审查”。门报告必须为每个条件登记责任任务、适用产品版本、关闭证据和最迟时间；`X-REL-*` 保持阻塞。条件完成后，通过实际 `CHG-YYYYMMDD-NNN` 重新打开同一个 `X-GATE-*`，使用新鲜证据重跑，并产生新的顺序型 `DEC-NNN`（`gate_id` 为当前 G3，`outcome` 为新结果）。
- `return_to_milestone`：必须登记 `target_milestone`、实际 `CHG-YYYYMMDD-NNN`、精确重开任务 ID、失效的 `EV-*`、所需新证据和重审条件；对应 `X-REL-*` 及下游产品任务保持阻塞。完成修复后重新生成候选包，重跑 E2E 和同一个 G3。
- `no_release`：必须登记终止的产品版本/路线范围，并把对应 `X-REL-*` 及所有依赖该发布的下游条件任务改为“已取消”，逐项引用本次顺序型 `DEC-NNN`。如果决定保留未来重审可能，必须同时登记实际 `CHG-*`、精确后继任务和重审条件；否则该版本是终止状态，不能继续保留虚假“未开始”任务。

只有 outcome 为 `release` 才能进入 `X-REL-*`。当前门是否被问题或风险阻断，必须按第24.3/24.4节的“适用范围”和“阻断点”字段机械判断，不能把与 PRODUCT-0.2 有关的问题错误用于阻断 G3-0.1。

`X-PKG-*` 在门前生成不可变候选包，候选清单记录每个文件的 SHA-256，并保存精确 `promotion_targets`（候选源路径、门后目标路径、共同期望哈希）；`SH-E2E-*` 必须按该清单测试精确包和晋级映射。G3 后的 `X-REL-*` 只能把相同字节和相同校验和从候选区晋级到发布区，不得重建、编辑文档或替换依赖。若候选包、晋级源或目标任何字节不匹配，旧 E2E 与门结论立即失效，必须重新执行候选包、E2E 和 G3。

## 22. 唯一任务台账

### 22.1 台账规则

任务 ID：

- `SH-*`：共享契约、模型、案例和验证设施。
- `A-*`、`B-*`、`C-*`：各实现路线。
- `X-*`：治理、路线门、安装比较和发布。
- 格式为 `<命名空间>-<领域>-<三位数>`；创建后永久保留，改名或取消都不得复用。

状态只允许：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚无可验收成果。 |
| 进行中 | 已产生实际工作，但未满足全部完成条件。 |
| 阻塞 | 引用明确 `RISK-*` 或 `Q-*`，并写明解除条件。 |
| 已完成 | 精确交付物、目标案例、回归和实际 `EV-*` 全部存在。 |
| 已取消 | 引用第24.2节已生效的顺序型 `DEC-NNN`，或第25.3节已批准/已验证的实际 `CHG-YYYYMMDD-NNN`。 |

只有本节表格可以保存任务状态。控制台、里程碑、路线报告和进度说明只能引用 ID，不得复制一份状态。

每个任务必须拥有：阶段、依赖、精确交付物、需求/案例、完成证据、实际证据、状态、所有者、复核者和下一动作。所有者默认是执行该任务的代理，复核者不得与高风险任务的实现者相同；实际分配在任务启动时登记。

台账交付物路径均相对于 `E:\codx\skill\饮食管家`。单元格以“A”“B”“C”开头时，其中每个反引号相对路径分别固定解析到 `version-a-skill-only`、`version-b-lite-plugin`、`version-c-strict-plugin`；不允许由执行者另选根目录。使用 `*.json`/`*.txt` 的任务必须在启动时的文件级实施计划中展开为精确文件清单，并写回机器台账后再修改文件。

依赖判定：

- 普通任务依赖只有在上游任务“已完成”时满足；“已取消”不等于完成。
- `X-GATE-*:<route>=<outcome>` 是决策条件，不是虚构任务 ID；只有对应门的生效决定给出完全相同 outcome 时满足。
- “所有获准路线”必须由门报告展开为精确任务 ID 清单，机器台账中禁止保留通配依赖。
- 被门停止的分支从下游必需依赖集合中移除，并将其条件任务改为“已取消”；不得让取消任务阻塞其他路线。
- 存储 spike、故障注入和纵向比较属于“评估任务”：完成含义是预定矩阵全部真实执行、工具本身正常结束且成功/失败结果完整取证，不要求被测路线通过业务案例。业务案例失败会让路线不能通过门，但不会让门永远无法形成 `stop` 决定。
- 普通产品实现任务仍必须满足第1.4节完成定义，不能借“评估任务”例外跳过测试。

## 23. 安装、开发验证与发布使用说明

### 23.1 当前能做什么

当前仓库只能用于：

- 阅读和评审本计划及共同契约。
- 验证 A/B/C foundation 的目录、测试、构建和插件外壳。
- 继续执行第 22 节开发任务。

当前仓库不能用于：

- 正式记录个人饮食、饮水、库存或营养。
- 依赖当前 B/C 空处理器得到业务结果。
- 把 foundation 版本号当成 PRODUCT-0.1。
- 按正式产品安装说明交给日常使用者。

### 23.2 当前开发基底验证

开发者可在项目根执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\shared\validate-foundations.ps1
```

这条命令的成功含义仅限于 G0。当前历史版本的脚本只在“执行前正式业务文件已确认为0”的基线上做执行后存在性扫描，不能证明未来已有业务数据保持不变。G1 前 `SH-SAFE-001` 必须更新或包装该命令，为正式扫描根生成执行前/后清单并比较路径、数量、大小、SHA-256 和 mtime；此后执行者必须查看 OpenClaw 状态隔离与新增/修改/删除差异，退出码为0也不允许省略数据污染检查。

### 23.3 正式安装流程必须达到的形态

G3 通过后的安装入口必须完成：

```text
环境预检
→ 展示产品版本、契约版本、Schema版本和支持环境
→ 检查已有安装与数据
→ 需要时创建升级前备份
→ 安装选中路线的 Skill/插件
→ 初始化或迁移固定数据根
→ 校验插件/Skill加载
→ 在隔离测试根运行冒烟测试
→ 验证正式数据未被测试改写
→ 输出安装结果、版本和回滚入口
```

首次启动必须：

- 让用户配置时区和区域设置；`week_start` 可采用明确产品默认并允许修改。
- 仅在用户主动配置时保存六项目标；不得自动生成健康目标。
- 说明本地数据位置和备份方式，但普通回执不暴露绝对内部路径。
- 不要求先上传所有营养资料；常见食物按来源策略补全。
- 不要求建立家庭成员，因为产品只记录本人。

### 23.4 升级与回滚

- 升级前展示来源版本、目标版本、Schema 变化和预计影响。
- 先在备份副本或临时数据根运行迁移与投影校验，再切换正式数据。
- 失败时保持旧版本可读且版本号不误升。
- 回滚不得让新版本已经提交的事件静默消失；涉及数据格式不兼容时必须使用前置备份和清晰提示。
- 0.1→0.2 必须证明个人模板、提醒、导出等新能力不会改写 0.1 历史营养快照。

### 23.5 卸载

卸载入口必须把“移除程序”和“删除业务数据”分开：

1. 默认移除 Skill/插件，保留业务数据和备份。
2. 只有用户明确选择删除数据并二次确认时才删除业务数据。
3. 删除前给出最后备份选项和目标范围。
4. 删除后报告删除范围和可否从备份恢复。

### 25.3 变更流程

变更 ID 只允许 `CHG-YYYYMMDD-NNN`；同一天使用下一个未占用三位序号。第25.3节下方台账是变更的唯一人类可读落点，`shared\traceability\changes.json` 只由该台账生成/校验，不能独立创建、关闭或改变变更状态。

每条变更必须包含：提出时间与原始来源、级别、问题/目标、受影响 `REQ/CASE/DEC/TASK/SCHEMA/PRODUCT`、所有者、审批者、实施任务、目标证据、状态（提议/批准/实施中/已验证/拒绝/撤销）和关闭证据。重开任务时还要记录旧状态、重开理由及旧证据继续适用的契约版本。

| 级别 | 类型 | 必须动作 |
| --- | --- | --- |
| L0 | 错别字、链接等不改变行为的文字修正 | 更新文档修订记录。 |
| L1 | 对已存在行为补充不改变边界的说明/例子 | 更新相关需求和文档校验。 |
| L2 | 新增兼容行为 | 新需求、案例、任务和证据。 |
| L3 | 改变库存默认、估算、回执等业务契约 | 新 `DEC-*`、契约版本、回归和迁移评估。 |
| L4 | 数据字段、约束、索引或历史转换 | 新 Schema 版本、迁移、备份恢复验证。 |
| L5 | 停止路线、切换实现或改变发布方式 | 路线门/新决定、条件任务取消和发布影响分析。 |

标准顺序：记录用户原始要求 → 分级 → 列影响 → 更新权威需求 → 更新案例 → 创建/重开任务 → 实施 → 测试 → 登记证据 → 更新唯一台账 → 更新控制台/变更日志。

已完成任务因规则变化重新打开时，不删除旧证据；旧证据仍是旧契约版本的历史事实，新契约必须有新证据。

当前变更登记：

| ID/时间 | 来源与级别 | 问题/目标 | 精确影响 | 所有者/审批者 | 状态 | 实施任务/关闭证据 |
| --- | --- | --- | --- | --- | --- | --- |

当前尚无需要单独登记的 `CHG-*`。未来任何任务重开、路线处置改变或已冻结业务规则改变，都必须先在此表新增实际 ID，再同步机器镜像；禁止只在任务单元格中写一个未定义的 `CHG-*`。
