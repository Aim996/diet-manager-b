## 2. 产品是什么

### 2.1 一句话定位

用户对智能体说一句口语（"我吃了两个鸡蛋"），系统把它变成**可靠、可追溯、可恢复**的饮食账本记录。智能体（Skill）只负责理解意图和转发原话；**所有事实判定、写入、回执都由确定性的 B 后端（TypeScript + SQLite）完成**。

### 2.2 分层架构

```
用户原话
  ▼
Skill（SKILL.md 指令层）      —— 只选动作、传原话、复述结果；一条消息至多一次工具调用
  ▼
OpenClaw 插件适配层            —— 只做 Schema 校验、克隆请求、转交 runtime；不重解析
  ▼
Application（编排）            —— parser → 营养解析 → 映射领域操作 → 执行 → 公开结果
  ▼
Parser（纯函数）               —— 原话 → candidate / needs_clarification / ignored
  ▼
Domain + Repository           —— FactCommit → EffectBundle → EnvelopeFinalize 三层事务
  ▼
Storage（node:sqlite + 迁移 + 备份）
```

**核心纪律：数据只能变得更结构化，不能在中途丢失。** Parser 输出的 candidate 是后续所有层的唯一事实来源；application/mapping 不是第二个自然语言解析器。

### 2.3 八条硬不变式（I-1 … I-8，约束力最强的一层）

| 不变式 | 一句话 | 一句话动机 |
|---|---|---|
| I-1 事实优先 | 营养/库存失败只降级，不丢餐次 | 账本底线是"记了就在" |
| I-2 未发生不写入 | 计划/否定零写；撤销走追加 void | 防"我没吃"变成记录 |
| I-3 未知 ≠ 0 | unknown 存 null，展示"未知" | 假 0 污染统计 |
| I-4 库存非负+唯一匹配 | 多候选不自动扣 | 宁可问不可猜 |
| I-5 原话保留 | raw_text 与派生字段分列 | 原话是最终证据 |
| I-6 幂等 | 业务语义生成幂等键 | 重试/重发不重复记录 |
| I-7 有界原子 | 事实+必要效果同事务 | 不追求全局分布式 |
| I-8 可追溯 | 事实↔效果↔来源全链引用 | 每个数字能回答"从哪来" |

## 3. 开发思路（为什么这样设计）

### 3.1 用「机器可校验的不变式」取代「功能列表」

传统功能列表在 AI 参与开发时容易被悄悄绕过。本项目把最强约束落到 8 条不变式（§2.3），**每条都有测试断言，违反即 Red**——让"约束"从 prompt 自觉变成工具强制。

### 3.2 三层事务「有界启用」（DEC-023）

- **FactCommit**：单层 `BEGIN IMMEDIATE`，写事实 + effect outbox + 幂等 checkpoint。纯查询、白水、单条营养标注只用这层。
- **EffectBundle**：事实的**必要**附加效果（库存扣减、营养快照、Issue、进度贡献）整体成功/回滚；技术失败保留事实和 pending outbox，重启可恢复。
- **EnvelopeFinalize**：聚合当日累计、冻结回执、写终态；重放同 token 返回原冻结结果。

**取舍**：能用单层就用单层。EnvelopeFinalize 是最后手段，进入前必须有一条新 DEC 说明必要性。

失败语义精确分工（回执真值的基础）：`committed`（全完成）/ `committed_with_issues`（效果降级，**不可重复提交**）/ `needs_clarification`（零写入+追问）/ `ignored`（零写入）/ `failed`（技术失败零业务写入）。

### 3.3 营养白名单（DEC-029）：AI 不许编数字

营养数值只能来自白名单来源（权威数据库 → 用户自建 → 标签 OCR），解析不到一律 `unknown`。LLM 对营养有"常识"，但这些数字不可追溯、会静默漂移。实现上是**只读引用硬编码**，AI/Skill 层无写入营养数值的口径——结构性防御而非约定防御。

### 3.4 冻结契约（contract + version + sha256）

Skill 与后端之间的公开契约以 `contract_id + version + sha256` 三元组冻结，SKILL.md 写死校验值。任一侧漂移时 Skill 视结果为"未确认成功"。这是最后防线，因为智能体平台的工具 Schema 更新往往不受我们控制。

### 3.5 已付学费的三条铁律（MIXED-LIQUID-001 教训）

1. **「识别到」和「可提交」是两个独立状态**：类别已识别但数量未知必须显式表达（`self_unquantified_count`），而不是不产生证据。
2. **Fail-closed 分支必须覆盖"证据缺失"的输入组合**。
3. 修复方式是让 parser 返回 `needs_clarification` 零写，**而不是让下游"聪明地"补救**——下游没有第二次解析的权利。

其他检验过的规则：并发测试必须真 worker + 独立连接 + 启动屏障；重放零写入要用全业务表规范快照 SHA 比较（行数抓不到 UPDATE/DELETE）；`Number(null) === 0` 所有 nullable 数量显式分支；测试 fixture 的营养来源要与生产权威一致（修 fixture，不放宽生产校验）。

## 4. 0.2.0 首个增量做了什么

三个 DEC，共享同一次 `contract v2 → v3`。公开动作从 8 个增至 **11 个**：`record_meal` / `record_water` / `add_inventory` / `query_inventory` / `query_meals` / `query_daily_summary` / `correct_record` / `undo_record` + 新增 `set_profile` / `set_goal` / `restore_record`。

### 4.1 DEC-030：个人档案 + 六项目标 + 进度条

- 新增 `user_profiles` 表（身高/体重/年龄/性别/减脂增肌状态），`set_profile` 显式触发派生。
- 六项参考目标**全部派生**，公式公开可检验（非 AI 编造），回执标注"参考目标（公式估算，可覆盖）"+"非医疗建议"：

| 维度 | 公式 |
|---|---|
| 基础代谢 BMR | Mifflin-St Jeor：`10×kg + 6.25×cm − 5×age + 性别项`（男 +5 / 女 −161 / 未填 −78；未填年龄默认 30） |
| 🔥热量 | `BMR × 1.2 × 状态系数`（维持 1.0 / 减脂 0.85 / 增肌 1.10） |
| 🥩蛋白质 | 维持 1.6 g/kg；减脂/增肌 2.0 g/kg |
| 🧈脂肪 | 1.0 g/kg |
| 🍚碳水 | `max(0, (热量 − 蛋白×4 − 脂肪×9) / 4)` |
| 🥦膳食纤维 | 14 g / 1000 kcal |
| 💧饮水 | 35 ml/kg |

- `set_goal` 可覆盖/清除任意子集（置 `null` 即清除该维度），手动覆盖优先于派生值。
- `query_daily_summary` 输出 `configured_goals` + `progress`（10 格 `█/░`，`percentage=round_half_up(current/target×100)`，超目标显示真实百分比、满格）。

### 4.2 DEC-031：撤销后恢复 `restore_record`

- `undo_record` 撤销后现在**可反悔**：`restore_record` 把已 void 记录翻回 active，重算营养/白水/进度。
- **库存返还边界**（关键）：restore 需重新扣减；批次不足时不造负库存（I-4），该效果标 `skipped_inventory`，营养/白水/进度照常恢复，回执如实说明。
- 幂等：对非 void 记录返回 already_active，不新建事实；恢复不删除 void 痕迹，`correction_events` 链完整可追溯。

### 4.3 DEC-032：离线营养数据集（去网络/代理依赖）

**背景**：开源项目不能假设所有环境都有代理。原生产营养解析唯一来源是 USDA FDC HTTP（需网络 + `env:FDC_API_KEY`），无 key/无网络一律降级 `unknown`——整套验收语义绑定网络。

**决策**：把封闭词表 12 项的 USDA FDC 权威营养值**固化进源码**（构建期下载 + 转写），离线解析链无条件接通，网络 FDC 降级为可选增强。

- 数据源：USDA FDC（Foundation / SR Legacy），美国政府公有领域作品，可合法分发。每条记录带 `fdcId` / `dataType` / `publicationDate` / `source_ref`。
- **离线 10 项权威**（`source_type=authoritative_public_database`，rank 4，network:false，始终启用）fdcId 闭合集：牛奶 `171265`、鸡蛋 `171287`、苹果 `171688`、香蕉 `173944`、面包 `174924`、米饭 `168930`、鸡肉 `171477`、咖啡 `171890`、茶 `173227`、豆浆 `172446`。
- **复合菜 2 项**（`fried_rice` 炒饭、`soup` 汤）无单一权威源 → 保留 `versioned_common_dish_template`（rank 6）。
- 解析链：离线 bundle（4）→ 版本化通用模板（6）→ 通用估计（7）→ unknown（8）。
- 修掉 `chicken_breast`→`chicken` 等键名与解析器 `LEXICON` 的对齐问题。

## 5. 测试思路

### 5.1 铁律：TDD 先红后绿

1. **先写失败测试（RED）**，跑它，**确认失败原因是"行为缺失"**，不是编译/导入/环境错误——错误的 RED 什么都证明不了。
2. 写**最小实现**到 GREEN，禁止顺手重构。
3. 定向测试 → 邻接回归 → `tsc --noEmit` → `git diff --check`。
4. **绝对禁止**把测试改成适配错误行为。

### 5.2 三层测试金字塔

| 层 | 内容 | 门禁 |
|---|---|---|
| 单元/定向 | 各 DEC 切片先证 RED 再 GREEN | 定向 vitest |
| 全量回归 | B 包全量 vitest（基线 959+ 例，约 3 分钟，`--maxWorkers=1`） | 阶段出口 |
| 真实验收 | 7 网关 Docker 容器逐场景回放，SQLite 只读白名单断言 | `run-real-acceptance-docker.py` |

### 5.3 真实验收方法论（0.2.0 的关键新增）

- **执行器** `shared/real-acceptance/run-real-acceptance-docker.py` 跑在宿主机 `bome`（`cz@192.168.100.10`，Debian 12），用 `docker exec` 直接驱动 7 个容器 `openclaw-gateway-01..07`（镜像 `ghcr.io/openclaw/openclaw:2026.7.1-2`）。
- 每台 `--reset` 建全新空库后逐场景独立会话回放 `setup + input`，对官方数据根 SQLite 做只读白名单断言（`expect_delta` 是相对 input 前的净增量）。
- **「公式不变、内容变」**（用户明确要求）：断言结构（表/where/delta/状态）7 台完全一致，输入内容（身高体重/热量/饮水/食物）逐台不同——证明能力跨内容/跨设备泛化，而非 7 台复读同一句。由 `generate-smoke-variants.py` 生成 7 份 `scenarios-0.2.0-smoke-gw0X.json`。
- 场景目录：`scenarios-0.2.0-smoke.json`（8 场景精简子集）+ `scenarios-0.2.0.json`（16 场景全量）。

### 5.4 证据链（EV）

- 每个 EV 指向**不可变产物**（commit SHA / 测试输出精确数字 / 文件 SHA-256），不复制"已通过"结论。ID 一旦分配永不重命名、永不复用。
- 0.2.0 关键证据：`EV-20260819-040`（candidate-009 build）、`EV-20260819-041`（DEC-032 离线营养）、`EV-20260820-042`（7 网关 × 8 场景 56/56 全绿）。
