# 0.1.1 真实环境验收执行手册

本文描述 0.1.1 在真实 OpenClaw 网关 + 真实 USDA 数据源上的产品验收执行方式。验收资产与执行器位于 `shared/real-acceptance/`：

- `scenarios.json` —— 38 个验收场景（8 类），每场景带独立会话、受测输入、前置 setup 与 SQLite 白名单断言。
- `evidence.schema.json` —— 证据结构（绑定候选字节、脱敏、`secret_value_count` 恒为 0）。
- `run-real-acceptance.ps1` —— 预检 + 逐场景执行 + 只读断言 + 原子写证据的执行器。
- `shared/tests/validate-real-acceptance-assets.mjs` —— 资产静态验证器（含变异自检）。

## 何时运行

本手册对应**阶段 4 的 Task 18**：不可变候选（Task 17 产出）构建完成后，用真实 `FDC_API_KEY` 与签收进行最终验收。Task 16 只交付资产与执行器，不实际跑真机。真机执行前必须满足：

1. 候选压缩包已由 Task 17 产出，其 SHA-256 已绑定。
2. 用户提供真实 `FDC_API_KEY`（只进入网关进程环境，绝不写入仓库、日志或证据）。
3. 用户在验收结束后签收。

## 安全边界（强制）

- **FDC_API_KEY**：只以环境变量注入网关进程；执行器只记录「存在 / 不存在」，绝不回显或写入其值。证据 `secret_value_count` 必须为 0。
- **authority secret / 备份口令**：不进参数、环境清单、日志、Git 或证据。
- **专用根**：`OfficialDataRoot` 与 `OpenClawStateRoot` 必须是绝对路径且落在 `E:\codx\skill\饮食管家\.tmp\real-acceptance\0.1.1` 之下；执行器拒绝其它位置。
- **只读断言**：SQLite 检查只允许白名单表与列（与 `validate-real-acceptance-assets.mjs` 一致），任何越界表/列都被拒绝，防止退化为任意 SQL 读取。
- **不改产品代码 / 防火墙**：断网与超时通过注入式 HTTP 传输或仅绑定到验收进程的测试代理实现，不得改产品代码或系统防火墙。

## 前置环境

- PowerShell 7（`pwsh`），Node 24.15.x，OpenClaw CLI（`openclaw`）。
- 一个**专用、隔离**的 OpenClaw 网关（独立 state root + 端口），由 `openclaw daemon` 管理以便执行器安全停启。
- 网关内已安装 0.1.1 候选插件；`FDC_API_KEY` 已注入网关进程环境。

## 执行

```powershell
pwsh -NoProfile -File shared/real-acceptance/run-real-acceptance.ps1 `
  -OfficialDataRoot E:\codx\skill\饮食管家\.tmp\real-acceptance\0.1.1\data `
  -OpenClawStateRoot E:\codx\skill\饮食管家\.tmp\real-acceptance\0.1.1\openclaw-state `
  -CandidateZip E:\codx\skill\饮食管家\.tmp\release-candidate\0.1.1\candidate-001\artifacts\diet-manager-b-0.1.1.zip `
  -SourceCommit <40-hex> -PackageVersion 0.1.1 `
  -EvidencePath E:\codx\skill\饮食管家\.tmp\real-acceptance\0.1.1\evidence.json `
  -GatewayStopCommand "openclaw daemon stop" `
  -GatewayStartCommand "openclaw daemon start"
```

执行器依次：

1. 预检根目录、候选哈希、网关 health、业务数据（已存在则拒绝，除非 `-Resume` 且哈希一致）。
2. 逐场景：回放 `setup` 消息 → 执行 `input`（会话键 `agent:main:diet-manager-real-0.1.1-<id>`）→ 捕获结构化工具事件与最终回复 → 停网关 → 只读断言 → 重启网关。
3. 生成证据并校验 schema，原子写入 `EvidencePath`。

## 场景类别与特殊控制

| 类别 | 场景 | 说明 |
|---|---|---|
| meal | single / multi / natural-unit / gram | 餐食主链 |
| zero_write | plan / negation / non-self / advice / not-occurred | 五种表述零写入 |
| nutrition | hit / no-result / missing-key / offline / timeout | `hit` 需 `requires_fdc_key`，无 key 时跳过 |
| inventory | unique / multiple / package / multi-purchase / insufficient / location | 采购、扣减、位置纠正 |
| correction | amount / time / water / undo / repeat-undo | 纠正与撤销 |
| query | meals / inventory / progress | `snapshot_equality`：同一查询执行两次要求输出一致 |
| reliability | duplicate / gateway-restart / plugin-reload / same-root-restore / portable-restore | 幂等与持久 |
| reply | committed / committed_with_issues / clarification / ignored / failed | 五种回执真值 |

### nutrition 五态与 FDC_API_KEY

- 有 key：`nutrition-hit` 期望 `coverage_status != unknown`（USDA 命中）。
- 无 key 或断网/超时：`nutrition-snapshots` 的 `coverage_status` 为 `unknown`（降级，`source_ref = nutrition-source-registry:terminal.unknown`）。
- `nutrition-missing-key` 通过在验收进程内不注入 key 验证；`offline`/`timeout` 通过测试代理（不落地产品代码）注入断网/超时，控制仅对验收进程生效。

### 恢复场景（Task 18 接线）

`same_root` 用 `dist/admin/cli.js backup` + `restore` 完成；`portable` 用 `backup-portable` + 离线 `restore-portable`，后者需操作者在真实终端逐键输入口令（不回显、不经管道）。执行器在这些场景停网关、完成恢复、再重启并继续。当前执行器对这两类恢复保留 `REAL_ACCEPTANCE_RESTORE_NOT_WIRED` 占位，Task 18 用候选字节的实际产物命令替换。

## 结果判定

- 每场景 `passed` = 观察到 `expected_outcome_status` 一致，且全部 SQLite 白名单断言通过。
- 全场景通过且 `secret_value_count = 0` 时，候选具备晋级资格（阶段 5）。
- 证据 JSON 由执行器输出到 `EvidencePath`，并可作为阶段 4 门禁证据归档。

## 已知约束

- `reliability-duplicate` 依赖网关在重放相同 `source_message_id` 时走幂等键；若 `openclaw agent` 无法透传相同幂等标识，该场景在证据中记录为「由单元测试覆盖」并跳过，不误报产品缺陷。
- 断言中的 `expect_delta` 是「相对本场景开始前的净增量」，天然对场景顺序鲁棒；个别绝对计数若与真实行为不符，属断言修正而非产品缺陷。
