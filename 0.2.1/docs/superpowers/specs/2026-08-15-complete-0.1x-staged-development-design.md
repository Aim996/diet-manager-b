# 饮食管家完整 0.1.x 分段开发设计

日期：2026-08-15

状态：设计已批准，等待实施计划

目标版本：`0.1.1`

现行权威：仓库根 `饮食管家-开发约束与需求-v1.0.md`

## 1. 目标

从已经冻结的 `releases/v0.1` 和当前 B 路线代码出发，以最少重复开发补齐 v1.0 的完整 0.1 范围，最终交付一个经过真实 OpenClaw、真实用户自管数据根、USDA 在线与离线降级验证的不可变 `0.1.1` 安装包。

完成状态不以“代码存在”或“单元测试通过”判定，而以以下结果同时成立为准：

1. v1.0 的 `SLICE-0` 至 `SLICE-7` 均有实现、测试和可追溯证据；
2. `I-1` 至 `I-8` 在正常、故障、重放、重启和恢复路径中均保持成立；
3. 用户可通过一个公开安装入口完成全新安装和升级；
4. 同根恢复与跨机器加密恢复均通过；
5. 真实 OpenClaw 对话、真实 USDA key、断网和缺 key 场景通过；
6. 最终发布字节与完成验收的候选字节完全相同。

## 2. 当前基线

本设计采用以下已经在 2026-08-15 重新核对的事实作为起点：

- `releases/v0.1` 是 464 个文件组成的冻结快照；安装 ZIP 的 SHA-256 与清单一致；
- 发布源码有 66 个 TypeScript 模块，冻结 `dist` 有 66 个对应 JavaScript 模块；
- 当前开发工作区的插件源码与 v0.1 发布源码相同；
- 在 Node `24.19.0`、正确包含系统 PowerShell 安全模块的环境中，31 个测试文件、959 条测试全部通过；
- TypeScript `--noEmit` 类型检查通过；
- 餐食、白水、明确采购、唯一库存匹配扣减、营养白名单、只读查询、幂等、同根备份恢复和 OpenClaw Skill 已有工作代码；
- `undo_record`、部分包装采购、多商品澄清、日常位置纠正、跨机器安全恢复和真实部署验收仍未形成完整发布闭环。

`releases/v0.1` 永久保持只读。所有后续开发继续发生在项目根 `version-b-lite-plugin`、`shared` 和 `docs`，最终形成新的 `releases/v0.1.1`。

## 3. 权威关系与范围

### 3.1 唯一需求源

`饮食管家-开发约束与需求-v1.0.md` 是唯一产品需求源。`总功能开发计划.md`、`总功能开发计划0.2.md`、`总功能开发计划0.3.md` 和 `总功能开发计划0.4.md` 只保留为历史材料，不能决定新任务的范围或完成状态。

本设计和后续实施计划属于执行层文件，只解释如何完成 v1.0，不得覆盖或暗改 v1.0。若执行中发现确实需要改变需求，只能先新增符合 v1.0 治理规则的 `DEC-*` 和 `CHG-*`，经批准后再修改计划。

### 3.2 0.1.0 声明纠正

v1.0 把 `SLICE-1` 纳入 0.1.0，同时 `SLICE-1` 包含 `REQ-CORE-004` 追加式撤销。因此，在撤销闭环完成前，只能表述为“v0.1 主链候选已通过自动化验证”，不得表述为“严格满足 v1.0 的完整 0.1.0 DoD”。

本轮不通过缩小需求解决矛盾，而是把追加式撤销作为阶段 1 的发布阻断项实现。

### 3.3 本轮范围

本轮包含：

- v1.0 `SLICE-0` 至 `SLICE-7`；
- 当前 v0.1 已知用户可见缺口；
- 安装、升级、备份、同根恢复、跨机器加密恢复；
- OpenClaw 和 USDA 真实环境验收；
- `0.1.1` 不可变候选与正式发布。

本轮不包含：

- PRODUCT-0.2 的营养研究流水线、Watchlist、跨周期回顾和个人模板；
- 健康诊断、减重建议或医疗营养决策；
- 默认定时提醒、主动推送和未获授权的后台任务；
- A/C 路线重新开发；
- 与 0.1 发布无关的架构重写。

## 4. 分段原则

采用“缺口优先”而不是重新实现全部 SLICE：

1. 已通过的能力先冻结成回归基线；
2. 每个阶段只处理一组彼此强相关的缺口；
3. 每个阶段都有独立可验收产物和退出门；
4. 上一阶段未通过，不启动下一阶段；
5. 全局 `WIP=1`，同一时间只有一个正式任务处于 `IN_PROGRESS`；
6. 所有功能变更测试先行，先观察目标失败，再写最小实现；
7. 阶段内运行定向测试，阶段出口运行完整回归；
8. 正式发布只晋级已完成真实环境验收的同一组候选字节。

### 阶段 0：权威统一与可重复基线

#### 目的

消除当前文档对权威计划、可安装性和 0.1.0 完成状态的互相矛盾，并把 959 条测试变成可重复的正式起点。

#### 工作边界

- 固化 Node 版本门和 Windows `PSModulePath` 预检，避免把 ACL 环境故障误判为产品回归；
- 建立一条机器可运行的基线命令，覆盖类型检查、959 条测试、敏感文件扫描和正式数据零污染检查；

#### 退出门

- 所有活动文档只引用 v1.0；

- 基线命令在干净工作树上通过；
- 执行前后 Git 状态和受保护数据清单无意外变化；
- 撤销缺口被登记为阶段 1 阻断项。

### 阶段 1：0.1.0 合规闭环

#### 目的

补齐 v1.0 首发子集当前最明确的缺口，使“0.1.0 主链完成”第一次与权威 DoD 一致。

#### 工作边界

- 公开接通 `undo_record`；
- 使用追加式 `void_event`，原事实、原话、来源和历史链永久保留；
- 对已经产生的库存扣减追加补偿事件，不直接修改旧流水；
- 撤销后的营养和日进度从有效视图重算，历史 Nutrition Snapshot 不改写；
- 同一撤销请求重放只生效一次；并发撤销只能有一个成功状态转换；
- 已撤销记录再次撤销返回稳定无变化结果，不伪称新提交；
- 无目标、多候选目标或跨主体目标只返回最少澄清，不写业务数据；
- 回执明确区分“事实已撤销”“无需变化”“尚未撤销”和“技术失败”。

#### 退出门

- `REQ-CORE-004`、`I-2`、`I-6`、`I-7`、`I-8` 有直接自动化断言；
- 正常、重放、并发、故障、重启和库存补偿用例全部通过；
- 查询只显示当前有效视图，同时仍可追溯原事实与撤销链；
- 完整测试、类型检查和数据零污染门通过。

### 阶段 2：完整 0.1 业务补齐

#### 目的

在不重写已稳定主链的前提下，关闭完整 0.1 的日常业务和公开交互缺口。

#### 工作边界

- 稳定支持“2盒牛奶，每盒250ml”等单层包装采购；
- 多商品采购逐项解析、统一澄清，并在确认后原子提交；
- 对规格、数量或候选身份不完整的采购返回具体 `needs_clarification.question`；
- 公开接通自然语言库存位置纠正，并保留位置来源与纠正事件；
- 完成 `correct_record` 的餐食、时间、数量、白水分类和库存补偿路径；
- 保持白水与营养饮品严格分离；混合输入不得静默丢项；
- 补齐查询当前有效记录、历史链、库存、当天六域进度；所有查询保持零写入；
- 收紧 Skill 回复边界：失败不得说已记录，不起名、不推销能力、不建议原样重试、不主动创建提醒。

#### 退出门

- v1.0 `SLICE-6` 的白水、购买和纠正全部完成；
- `REQ-WATER`、`REQ-PURCHASE`、`REQ-CORRECTION`、`REQ-QUERY` 的 Given/When/Then 均有自动化覆盖；
- 包装采购、多商品、位置纠正、混合饮品和澄清代表场景通过；
- 每个公开写动作均能证明提交、未提交和失败回执真实；
- 完整测试、类型检查、OpenClaw 插件校验和数据零污染门通过。

### 阶段 3：安装、升级与灾备闭环

#### 目的

完成 v1.0 `SLICE-7` 的运维能力，使普通用户可以安全安装、升级、备份和恢复。

#### 工作边界

- 保留一个公开安装入口，安装前执行 Node、OpenClaw、路径、权限和配置预检；
- 全新安装只创建固定数据库、固定私有 secret 和必要元数据；
- 升级前自动备份，迁移失败恢复旧数据库和旧插件状态；
- 同根备份继续使用在线 SQLite backup、SHA-256 和恢复回滚；
- 新增跨机器加密恢复包：数据库和 authority secret 必须加密封装，认证加密失败即拒绝恢复；
- 加密口令或密钥只能从终端交互或受保护的外部引用进入，禁止出现在聊天、插件配置、日志和普通清单中；
- 恢复后重新验证 schema、foreign keys、quick check、事实签名、库存非负和全部有效视图；
- 卸载插件与删除业务数据保持两个独立操作，任何删除均要求精确根确认。

#### 退出门

- 全新安装、原地升级、失败回滚、同根恢复、跨机器恢复均有隔离 E2E；
- 篡改包、错误口令、错误目标根、旧版本不兼容和恢复中断均 fail closed；
- 恢复后 `I-1` 至 `I-8` 全部复验；
- 安装包和日志扫描不包含 API key、authority secret、Gateway 凭据或真实饮食数据；
- 完整测试、构建和插件校验通过。

### 阶段 4：真实环境产品验收

#### 目的

证明自动化环境之外的真实 OpenClaw、网络、会话和持久数据行为满足发布承诺。

#### 验收环境

- 用户控制的专用验收数据根，不使用已有正式饮食数据；
- 实际 OpenClaw Gateway 和正式插件加载方式；
- 用户自己的 `FDC_API_KEY`，只存在于启动服务进程环境；
- 可控制的在线、断网、缺 key、超时和重启条件；
- 至少一次全新安装和一次从 v0.1 升级。

#### 场景集

- 餐食：单项、多项、克重、自然单位、晚饭/刚吃等省略表达；
- 零写：计划、否定、非本人、健康建议和未发生事件；
- 营养：USDA 命中、无结果、缺 key、断网和超时均不编造数值；
- 库存：唯一扣减、多候选不扣、库存不足、包装采购、多商品和位置纠正；
- 纠正：餐食、时间、数量、白水分类、撤销和重复撤销；
- 查询：餐食、库存、当天六域进度，查询前后数据库业务快照一致；
- 可靠性：重复消息、Gateway 重启、插件重载、备份、同根恢复和跨机器恢复；
- 回复：成功、带问题成功、澄清、忽略和失败五类结果均如实表达。

#### 退出门

- 所有场景保留输入、结构化工具结果、数据库断言和用户可见回复；
- 没有 P0/P1 缺陷；P2 只有明确不影响 v1.0 承诺且已登记偿还条件时才可保留；
- USDA 在线命中和所有离线降级场景均通过；
- 用户明确确认安装、日常记录、查询、纠正和恢复体验可接受；
- 任一修复导致候选字节变化时，本阶段必须针对新候选重新执行受影响场景和完整出口门。

### 阶段 5：不可变候选与正式发布

#### 目的

把已验收代码生成一次不可变候选，并证明最终发布包就是被验收的同一字节序列。

## 6. 组件边界

后续实现维持现有分层，不因补缺口重新设计整套系统：

| 边界 | 责任 | 禁止事项 |
|---|---|---|
| Skill / OpenClaw 适配 | 保留原话、选择一次动作、如实呈现结果 | 不解释或重写业务事实；不做失败兜底存储 |
| Parser | 从原话形成候选命令与澄清原因 | 不直接访问数据库或营养网络 |
| Application | 协调解析、事实提交、效果和公开结果 | 不在展示阶段重新计算权威数据 |
| FactCommit | 追加事实和必要库存效果的原子事务 | 不调用外部网络；不修改历史事实 |
| Effect / Projection | 营养、进度、问题、补偿和有效视图 | 不让非必要效果失败抹掉已允许独立存在的事实 |
| Nutrition | 白名单来源、unknown、来源追溯和不可变 Snapshot | 不接受 AI 常识生成的数值 |
| Storage / Authority | 固定根、SQLite、迁移、签名、锁和恢复 | 不接受模型传入路径、secret 或 revision |
| Admin / Release | 安装、升级、备份、恢复、清单和候选晋级 | 不接触聊天内容；不把 secret 放入普通包 |

阶段 1 至阶段 3 可以增加小型专责文件，但不得把撤销、迁移或加密恢复继续堆入已经过大的领域文件。实施计划必须先给出准确文件责任图，再决定新增或修改路径。

## 7. 数据流与失败处理

### 7.1 写入数据流

```text
OpenClaw 入站元数据 + 原始 source_text
→ 单次 diet_manager 调用
→ Parser 产生命令、忽略或最少澄清
→ 服务端冻结身份、幂等键和必要效果计划
→ FactCommit 原子追加事实与必要库存效果
→ 非必要营养/进度/问题投影
→ 从提交后权威读回构造公开回执
```

任何步骤失败都必须返回稳定状态，且不得通过 Memory、便签、提醒或第二次工具调用补写。

### 7.2 撤销与纠正数据流

```text
用户目标描述
→ 权威记录定位
→ 唯一目标或最少澄清
→ 追加 void/correction 事实
→ 追加库存补偿与进度差额
→ 重算当前有效视图
→ 返回原事实、变更事实和当前状态标识
```

旧行、旧营养快照和旧库存流水不可物理删除或就地改写。

### 7.3 运维失败处理

- 安装预检失败：零安装写入；
- 迁移失败：恢复旧数据库与旧插件状态；
- 备份校验失败：不发布备份文件；
- 恢复候选失败：恢复旧数据库；
- 加密包认证失败：不写目标根；
- USDA 失败：事实按业务规则继续提交，营养为 `unknown`；
- 回执生成失败：不得把未确认结果说成已记录。

## 8. 验证策略

### 8.1 开发循环

每个正式任务采用同一顺序：

1. 新增一个能准确证明缺口的失败测试；
2. 运行该测试并确认失败原因是目标能力缺失；
3. 写最小实现；
4. 运行目标测试和直接相邻测试；
5. 运行类型检查；
6. 更新证据与状态；
7. 单任务提交。

### 8.2 阶段出口

阶段出口至少包含：

- 完整 Vitest；
- TypeScript `--noEmit`；
- 构建和 `src/dist` 覆盖检查；
- OpenClaw metadata check 与 plugin validate；
- 数据库、secret、临时根和敏感文本扫描；
- 正式数据根执行前后清单零差异；
- 本阶段专属故障、重放、重启或恢复测试。

Windows 测试预检必须确认 `Microsoft.PowerShell.Security` 可加载。该环境门失败时应报告 `ENVIRONMENT_BLOCKED`，不得把随后的 `CORE_RUNTIME_SECRET_INVALID` 连锁失败统计为独立产品缺陷。

### 8.3 证据规则

- 自动化输出保存命令、Node/OpenClaw 版本、提交 SHA、退出码和测试计数；
- 真实环境证据保存脱敏输入、工具结果、用户可见回复和数据库断言；
- EV 只引用不可变日志或提交，不用可编辑报告代替测试产物；
- 证据不得包含 API key、authority secret、Gateway 凭据或真实饮食隐私数据。

## 9. 阶段依赖与状态推进

```text
阶段 0 权威与基线
→ 阶段 1 0.1.0 合规
→ 阶段 2 完整 0.1 业务
→ 阶段 3 安装与灾备
→ 阶段 4 真实环境验收
→ 阶段 5 不可变发布
```

任务状态推进规则：

- `NOT_STARTED → IN_PROGRESS`：依赖和测试入口齐全，且当前无其他 WIP；
- `IN_PROGRESS → DONE`：代码、测试、证据、文档和独立复核全部满足；
- `IN_PROGRESS → BLOCKED`：仅用于真实外部依赖不可获得，且已经记录继续条件；
- 需求、Schema、公开契约、迁移或候选字节变化时，所有受影响的下游阶段必须重开。

## 10. 主要风险与控制

| 风险 | 控制 |
|---|---|
| 历史计划继续覆盖 v1.0 | 阶段 0 统一入口并增加禁止历史引用检查 |
| 把现有通过测试误当成全部需求完成 | 每项 v1.0 REQ/I 映射到具体任务与断言 |
| 撤销破坏追加式事实链 | 只追加 void/correction/compensation，不更新旧事实 |
| 多商品采购出现部分提交 | 冻结整单计划后在单一事务提交或整单零写 |
| 跨机器恢复泄露 authority secret | 认证加密、终端密钥输入、日志与配置零明文 |
| ACL 测试环境造成假回归 | 阶段 0 加入 PowerShell 模块预检和环境分类 |
| 真实 USDA 不稳定 | 在线命中只作为来源能力验收；失败必须稳定降级 unknown |
| 修复后沿用旧候选证据 | 任一候选字节变化使真实验收与发布门重新绑定新哈希 |
| OpenClaw 上层回复夸大结果 | Skill 单调用终止规则和五类结果逐类验收 |

## 11. 设计完成标准

后续实施计划必须满足：

- 每个阶段拆成可独立审查的任务；
- 每个任务列出准确文件、接口、失败测试、实现步骤、验证命令和提交边界；
- 每个 v1.0 REQ 和不变式都能定位到至少一个负责任务；
- 不保留占位条目、模糊延期表述或未定义接口；
- 不把 PRODUCT-0.2 混入 0.1.1；
- 最终任务明确生成 `releases/v0.1.1`，且只晋级通过真实环境门的候选字节。
