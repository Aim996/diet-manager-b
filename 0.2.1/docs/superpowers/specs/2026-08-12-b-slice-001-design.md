# B-SLICE-001：B 路线首条纵向业务闭环设计

> 状态：高层方案已获用户确认；本文等待书面规格复核后进入实施计划
> 日期：2026-08-12（Asia/Shanghai）
> 权威目标：仓库根目录《总功能开发计划0.3》§26.5、§31.5 的 `B-SLICE-001`
> 前置门：`X-GATE-001=pass_b_safety`，证据 `EV-20260812-030`

## 1. 目标

本任务只完成 B 唯一产品主线的第一条真实业务闭环：

```text
购买入库
→ 商品/批次/营养资料
→ 库存查询
→ 在家饮食记录
→ 默认关联并扣减家庭库存
→ 营养快照与当日进度
→ 冻结回执
→ 追加纠正或撤销
→ 库存补偿、营养重算和进度重算
→ 查询当前有效视图
```

完成后，B 后端应能够用结构化输入在测试数据库中跑通这条闭环，并由共同案例适配器验证。用户看到的最终产品仍是“饮食管家 Skill”；SQLite、仓储和领域服务只是 Skill 的确定性执行后端，不是独立产品。

## 2. 控制范围

### 2.1 本任务必须完成

- 结构化购买/入库，生成商品、批次、库存入账和可追溯营养资料。
- 库存查询，返回批次当前有效数量和状态。
- 结构化在家饮食记录，按计划规则尝试默认关联家庭库存。
- 明确外食时不读取、不扣减家庭库存。
- 候选不唯一或库存不足时，饮食事实照常提交，库存不擅自扣减、不出现负数，并产生可处理 Issue。
- 明确数量、自然单位和计划允许的合理上界估算之间保持分离；营养估算量不得冒充库存扣量。
- 生成不可变营养快照、同一信封最终日进度和结构化回执。
- 追加式纠正、撤销和恢复；原事实不改写、不删除，库存通过补偿交易调整，营养和进度按当前有效视图重算。
- 查询今日饮食、库存和当日汇总时只返回当前有效视图。
- 同幂等键同输入重试返回冻结原结果；同键不同输入拒绝。
- 任一写入失败都不得在饮食/库存等正式业务表中形成半条记录；允许产生独立、脱敏、无原始业务内容的技术失败日志。

### 2.2 本任务明确不做

- 不接入 MCP；当前产品形态仍是 Skill 加确定性 B 插件后端。
- 不开放 OpenClaw `diet_manager` 工具的真实写入。`src/index.ts` 继续返回非写入 foundation 结果，直到 `B-FAULT-001` 与 `X-GATE-002=bind_b_ready` 完成路径和契约绑定。
- 不创建 `shared/selected-route-map.json`，不宣称 G2/G3、安装、发布或产品可用。
- 不实现自由文本模型解析、联网营养检索、丰富周回顾、模板学习或医疗/家庭成员功能。
- `record_water` 留给计划中的 `SEL-WATER-001`；本任务只处理 G2 固定 17 案所需的饮食、库存、营养、纠正、查询、回执和进度。
- 不继续扩展 Windows 安全底座；只有会导致业务数据污染、路径越界、命令逃逸、秘密泄漏或部署不可用的问题才重开。
- 不修改 SQLite migration v1。若现有表或约束不足以表达闭环，停止实现并重开上游模型/映射任务，不在纵切中静默改库结构。

## 3. 已有基础与缺口

现有 B 实现已经提供：

- 服务端权威 preview/token、`input_digest + data_revision` 绑定和非法状态拒绝；
- `FactCommit`：先提交不可变事实、meal items 和 effect outbox；
- 库存 add/deduct 事务、非负投影与 pending-effect 恢复；
- `EnvelopeFinalize`：效果稳定后冻结一次终态结果；
- SQLite migration v1 中的商品、批次、库存交易、营养、进度、Issue、纠正、outbox 和最终器表；
- 幂等、并发、响应丢失、崩溃和失败日志的 B 存储安全证据。

本任务不重做这些能力。缺口是一个领域编排层：把结构化业务命令确定性地准备为事实、效果和最终结果，并提供有效视图查询。

## 4. 设计选择

### 4.0 比较过的三种推进方式

| 推进方式 | 好处 | 代价与风险 | 结论 |
|---|---|---|---|
| 先把公开 OpenClaw 工具接成真实写入 | 很快能看到聊天入口 | 路径绑定和故障门尚未完成，会把平台问题、模型解析和业务事务混在一起 | 不采用 |
| 先完成内部单条纵向闭环 | 直接验证 Skill 的核心用途，同时复用已通过安全门的仓储能力 | 公开入口暂时仍显示 foundation 状态 | **采用** |
| 继续加固通用安全底座或先做 MCP | 可增加基础设施覆盖 | 偏离计划 0.3 的当前唯一任务，延迟真实饮食功能 | 不采用 |

采用中间方案后，业务规则只实现一次；后续 OpenClaw 或其他智能体宿主都复用同一服务，而不是各自复制写入逻辑。

### 4.1 选择：内部领域服务，而不是先接公开工具

新增一个只接受已结构化、已归一化命令的内部 `DietDomainService`。共同案例适配器和 B 测试直接调用该服务；公开 OpenClaw 工具暂不调用它。

原因：

- 先验证业务和存储语义，不把模型解析、平台会话或安装问题混入纵切；
- 避免在 `selected-route-map` 尚未生成时让公开入口写真实数据；
- 同一内部服务以后可由 OpenClaw、CLI 或其他智能体宿主调用，保持多宿主选择。

### 4.2 结构化信封

服务接收一个信封，包含稳定的 `operation_id`、subject scope、固定时钟、会话/消息标识和一个或多个有序子操作。首版子操作限定为：

- `add_inventory`
- `record_meal`
- `query_inventory`
- `query_meals`
- `query_daily_summary`
- `correct_record`
- `undo_record`

混合信封按叙述顺序执行；例如“买一箱牛奶又喝一盒”先入库，再允许本轮饮食关联新批次。每个子操作有独立 operation identity 和结果，信封只在全部已提交子操作的效果稳定后冻结一次合计进度与回执。后项业务失败不回滚已成功前项。

### 4.3 确定性标识与时间

- 所有 event、item、effect、batch、snapshot、progress、receipt、issue 和 correction 标识均由信封/操作标识、主体和序号确定性派生。
- 测试必须注入固定时钟与测试自有 SQLite 路径。
- 运行时禁止以随机值或当前系统时间重建已存在的幂等结果。
- 同键重试只读取或恢复既有 pending stage，不重新解释当前库存或当前营养版本后改写原结果。

## 5. 组件边界

### 5.1 `src/domain/service.ts`

领域入口和信封编排：

- 冻结并验证结构化输入；
- 取得/验证服务端 preview；
- 按顺序准备每个子操作；
- 调用现有 `FactCommit`；
- 驱动 EffectBundle；
- 全部子操作结束后调用 `EnvelopeFinalize`；
- 对 query 命令只运行只读投影，不创建业务行；
- 返回纯数据 DTO，不渲染平台专用文本。

### 5.2 `src/domain/effect-bundle.ts`

只处理 FactCommit 之后的附加效果，并以每个 operation 为事务边界：

- 商品/批次建立和库存入账；
- 在家饮食库存扣减或明确业务跳过；
- 营养 profile/snapshot 写入；
- Issue 写入；
- 纠正的库存补偿、营养替换和受影响日期进度重算；
- effect outbox 状态与 `effect_bundle_commits` 一致更新。

任何技术失败回滚本次 EffectBundle，保留已提交事实和 pending outbox；不得写伪进度或成功回执。

### 5.3 `src/domain/read-model.ts`

用单次一致性读取构造：

- 库存当前有效投影；
- 今日饮食当前有效视图；
- 某日营养/进度汇总；
- 纠正/撤销链的审计信息。

有效视图以追加纠正链为权威，不物理更新原 `event_records`。查询不得产生业务写入。

### 5.4 `src/domain/receipt.ts`

从已冻结领域结果生成结构化 `ReceiptData`：

- 标题单行；
- 每菜/食物/饮品一行，菜内组件同一行；
- 仅推定字段带估算标记；
- Issue 提供 2–4 个稳定快捷项，末项允许自由文本；
- 同一信封只附一个最终进度块；
- 技术 pending 不冒充成功。

本模块只生成结构化 DTO；文本逐字符渲染继续由既有黄金回执契约负责。

### 5.5 现有 repository 模块

- 复用并按最小需要扩展 `repository/fact-commit.ts`、`inventory-effects.ts`、`envelope-finalize.ts`、`query.ts`。
- 扩展必须保持现有公开契约和 69 项 B 回归通过。
- repository 不做自然语言解释，不自行选择营养来源或库存候选。

## 6. 三段可审查实现

### 阶段一：购买、批次和库存查询

实现结构化 `add_inventory` 与 `query_inventory`：建立商品和批次、写入库存入账、绑定标签营养 profile，并验证幂等重试和查询投影。

阶段出口：购买后可查到正确批次数量；失败前零业务写，FactCommit 后效果失败保持 pending；旧 69 项测试全部通过。

### 阶段二：饮食、库存扣减、营养、进度和回执

实现 `record_meal`、`query_meals`、`query_daily_summary`，包括外食、默认库存、多候选、库存不足、明确量/推定量、公共库 fixture、营养版本和同信封最终进度。

阶段出口：饮食事实、库存、营养快照、进度和回执形成完整闭环；混合“先买再喝”按顺序通过；技术效果失败不产生伪成功。

### 阶段三：追加纠正、撤销和有效视图

实现 `correct_record` 与 `undo_record`：追加 correction event，生成库存补偿交易，替换营养有效快照，重算受影响日期，查询只显示当前有效视图，同时保留旧事实审计链。

阶段出口：2 个鸡蛋改为 3 个时，只增加新事件和差量效果；原事件仍可审计；重试、撤销和恢复均确定性。

三阶段是同一个 `B-SLICE-001` 的内部实施顺序，不是新路线、替代方案或新增门。

## 7. 关键业务规则

### 7.1 库存关联

- 明确外食：不读取家庭库存。
- 在家且唯一可信候选、单位可换算、数量足够：扣减。
- 多候选、单位不可换算或库存不足：饮食事实提交，整项不扣，库存保持非负，并创建 Issue。
- 营养采用量、可食估算量、库存扣量和模板参考量是四个独立值，不互相冒充。
- 同一信封先入库后饮食时，饮食可关联本轮已成功入库批次。

### 7.2 营养

- 精确包装标签优先，保存原值、解析值、版本和适用商品。
- 无标签时只使用测试中冻结的公共资料 fixture；本任务不发真实网络请求。
- 每次饮食保存不可变 nutrition snapshot；营养 profile 升级只影响新记录。
- unknown/partial 必须保留并披露，不能以零替代未知。

### 7.3 纠正和撤销

- 原事件、原库存交易、原营养快照不更新、不删除。
- 纠正通过 `correction_events` 和新 EffectBundle 表达。
- 库存只写补偿交易；营养和进度生成新有效结果。
- 跨日纠正分别重算原日期与新日期；本切片至少保证数据结构支持，完整跨日黄金回执由后继任务继续覆盖。

### 7.4 失败与日志

- `FactCommit` 前失败：正式业务表零新增。
- `FactCommit` 内失败：事务全回滚，正式业务表零半写。
- `FactCommit` 后 EffectBundle 技术失败：事实保留，效果事务全回滚，outbox 保持可重试，终态不得写成功。
- `EnvelopeFinalize` 失败：最终器全回滚，不产生半条终态或回执。
- 技术失败日志只能包含阶段、稳定错误码、trace id 和 input digest 等脱敏字段；不得包含原话、食物明细、库存明细、密钥、SQL 或本机路径。

## 8. 固定 17 案责任

| 案例 | 本设计的证明点 |
|---|---|
| `CASE-MIXED-001` | 同信封先买牛奶，再让饮食关联本轮入库批次 |
| `CASE-CORR-001` | 2 个鸡蛋改 3 个，追加纠正、库存差量、营养重算、旧事实可审计 |
| `CASE-QUERY-001` | 今天吃了什么按用户自然日返回当前有效视图 |
| `CASE-EFFECT-001` | 营养效果失败时事实保留、效果回滚、outbox pending、无伪进度 |
| `CASE-MEAL-006` | 明确克重不标估算，营养来源可追溯 |
| `CASE-NUTR-008` | 一个橙子的可食克重只落推定字段 |
| `CASE-MEAL-003` | 半碗米饭用可靠范围上界估算营养，但不拿该克重扣库存 |
| `CASE-MEAL-004` | 明确公司进食不读、不扣家庭库存 |
| `CASE-INVENTORY-003` | 多候选时提交饮食、跳过扣减、不擅选 |
| `CASE-INVENTORY-004` | 库存不足时提交饮食、整项不扣、库存不负 |
| `CASE-NUTR-001` | 包装标签优先并保存版本与适用商品 |
| `CASE-NUTR-002` | 无标签时使用冻结公共资料，不要求上传 |
| `CASE-NUTR-005` | 新记录用 profile v2，历史 snapshot 保留 v1 |
| `CASE-STORAGE-001` | 同幂等键重试不增加事件、库存或终态，并返回冻结原结果 |
| `CASE-RECEIPT-001` | 一餐多菜保持标题单行、逐菜/食物行、菜内同一行 |
| `CASE-RECEIPT-003` | Issue 快捷项为 2–4 项且支持末行自由文本 |
| `CASE-PROGRESS-010` | 多子操作同日只冻结一个信封级合计增量 |

这 17 案必须全部由 B 当前候选的新鲜执行证据承担，不能借用 A/C 历史结果，也不能只做静态断言。

## 9. 测试与证据

### 9.1 测试层次

1. 领域单元测试：数量分离、候选选择、营养版本、纠正差量、ReceiptData。
2. SQLite 集成测试：每个阶段使用新临时数据库，验证真实表行、事务、外键、非负和重放。
3. 共同案例适配：把 G2 固定 17 案映射到 `DietDomainService`，逐案比较冻结 expected/forbidden。
4. 故障定点：本任务只跑 `CASE-EFFECT-001` 必需故障；完整字段故障矩阵留给 `B-FAULT-001`。
5. 回归：69 项既有 B 测试、TypeScript build、共享 trace/gate 校验和 OpenClaw build/validate 的无模型门。

### 9.2 测试约束

- 不读取、改写或把受保护契约/Schema/fixture/validator 文件作为本任务输入。
- 共同案例只通过已获准的公共适配器和冻结目录消费；不得从被测结果反推 expected。
- 每次测试冻结数据库/正式根前后差量；失败后业务候选和临时 fixture 必须为零残留。
- 不调用真实 Node 以外的模型服务，不消耗 OpenClaw 测试平台大模型。
- OpenClaw 只运行本地插件构建/校验和必要的独立只读复核。

### 9.3 完成证据

`B-SLICE-001` 只有同时满足以下条件才能标记完成：

- 固定 17 案全部 PASS 且 ID 唯一；
- 既有 69 项 B 测试无回归；
- TypeScript、plugin build/validate、trace/gate 校验通过；
- 技术失败日志与业务零半写边界有真实断言；
- 正式根前后无业务污染，临时数据库/fixture 清零；
- 独立复核 P0=0、P1=0；
- 生成新鲜 `E-STOR+E-CASE` 证据并更新《总功能开发计划0.3》和《开发进度》；
- 候选 commit SHA 与证据、复核、GitHub 分支完全一致。

## 10. 停止和重开条件

出现以下任一情况时停止当前实现，不用“顺手扩功能”掩盖问题：

- migration v1 无法表达固定 17 案；
- 需要改变共同契约、模型或案例 expected；
- 需要提前开放 OpenClaw 写入或创建 selected-route-map；
- 发现安全问题会造成业务数据错误、半写、路径/命令逃逸或秘密泄漏；
- 需要真实联网营养服务才能让固定案例通过；
- 实现开始承担 `SEL-*` 的完整 0.1/0.2 功能，而不是 G2 最小纵切。

届时应在计划 0.3 中重开对应上游任务或风险项，并取得明确批准后再继续。

## 11. 实施后的唯一后继

本设计通过并完成实现后，只解锁 `B-FAULT-001`。`X-GATE-002`仍需等待 `B-FAULT-001`、冻结 CONTRACT-v2 版本/hash 和路径清单齐全；在此之前不安装、不发布、不让公开 Skill 写真实数据。
