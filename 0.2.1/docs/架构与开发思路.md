# 饮食管家 B：架构与开发思路

> 初版：2026-08-16（0.1.1 开发期）。本文档解释"为什么这样设计"，供人和后续 AI 会话快速建立心智模型。
> 需求权威始终是仓库根《饮食管家-开发约束与需求-v1.0.md》；两者冲突时以权威文档为准。

## 1. 一句话定位

用户对智能体说一句口语（"我吃了两个鸡蛋"），系统把它变成**可靠、可追溯、可恢复**的饮食账本记录。智能体（Skill）只负责理解意图和转发原话；所有事实判定、写入和回执都由确定性的 B 后端（TypeScript + SQLite）完成。

## 2. 分层架构

```
用户原话
  │
  ▼
Skill（SKILL.md 指令层，运行在智能体上）
  │  只做：选动作、传原话、复述结果；一条消息至多一次工具调用
  ▼
OpenClaw 插件适配层（src/openclaw/plugin.ts）
  │  只做：Schema 校验、克隆请求、转交 runtime；不重解析、不补业务
  ▼
Application（src/application/：core-runtime、mapping、outcome）
  │  编排：调 parser → 解析营养 → 映射领域操作 → 执行 → 构造公开结果
  ▼
Parser（src/parser/：meal、liquid、purchase、time、subject…）
  │  纯函数：原话 → candidate（可提交）/ needs_clarification / ignored
  ▼
Domain + Repository（src/domain/、src/repository/）
  │  FactCommit → EffectBundle → EnvelopeFinalize 三层事务
  ▼
Storage（src/storage/：node:sqlite、迁移、备份）
```

**核心纪律：数据只能变得更结构化，不能在中途丢失。** Parser 输出的 candidate 是后续所有层的唯一事实来源；application/mapping 不是第二个自然语言解析器，发现不了 parser 遗漏的实体。这就是 MIXED-LIQUID-001 缺陷的教训（见 §7）。

## 3. 为什么是 8 条硬不变式

传统"功能列表"式需求在 AI 参与开发时容易被悄悄绕过；v1.0 改用**机器可校验的不变式**做最强约束层：

| 不变式 | 一句话 | 设计动机 |
|---|---|---|
| I-1 事实优先 | 营养/库存失败只降级，不丢餐次 | 账本的底线是"记了就在" |
| I-2 未发生不写入 | 计划/否定零写；撤销走追加 void | 防止"我没吃"变成一条记录 |
| I-3 未知 ≠ 0 | unknown 存 null，展示"未知" | 假 0 会污染营养统计 |
| I-4 库存非负+唯一匹配 | 多候选不自动扣 | 宁可问，不可猜 |
| I-5 原话保留 | raw_text 与派生字段分列 | 原话是可审计的最终证据 |
| I-6 幂等 | 业务语义生成幂等键 | 重试/重发不产生重复记录 |
| I-7 有界原子 | 事实+必要效果同事务 | 不追求全局分布式事务 |
| I-8 可追溯 | 事实↔效果↔来源全链引用 | 每个数字都能回答"从哪来" |

每条不变式都有对应测试断言；违反即 Red。这让"约束"从 prompt 自觉变成工具强制。

## 4. 三层事务模型（DEC-023：有界启用）

- **FactCommit**：单层 SQLite `BEGIN IMMEDIATE` 事务，写事实行 + effect outbox + 幂等 checkpoint。纯查询、白水这类简单场景只用这一层。
- **EffectBundle**：事实的必要附加效果（库存扣减、营养快照、Issue、进度贡献）在一个事务里整体成功或整体回滚；技术失败保留事实和 pending outbox，重启可恢复。
- **EnvelopeFinalize**：聚合当日累计、冻结回执、写终态；重放同 token 返回原冻结结果。

**取舍**：能用单层就用单层。EffectBundle 只服务于"事实+必要效果"的原子性；EnvelopeFinalize 是最后手段。这个"有界"决定来自早期教训——全场景启用三层会让简单路径背上不必要的复杂度和故障面。

失败语义的精确分工（这是回执真值的基础）：

- `committed`：事实已提交，效果全部完成。
- `committed_with_issues`：事实已提交，某些效果降级（如库存 skipped）。**不能重复提交**。
- `needs_clarification`：最小安全事实无法确定，**零写入**，附一个具体追问。
- `ignored`：计划/否定/只读，零写入。
- `failed`：技术失败，零业务写入（可有脱敏技术日志）。

## 5. 营养白名单（DEC-029）：为什么 AI 不许编数字

营养数值只能来自：权威数据库（USDA FDC，已接入生产 HTTP transport；CFCT 规划中）→ 用户自建 → 标签 OCR。解析不到一律 `unknown`。

动机：LLM 对食物营养有"常识"，但这些数字不可追溯、不可复现、会静默漂移。账本产品的可信度建立在"每个数字有出处"上，宁可显示"未知"。实现上白名单是**只读引用**硬编码，AI/Skill 层没有写入营养数值的口径，属于结构性防御而非约定防御。

## 6. 冻结契约 contract-v2

Skill 与后端之间的公开契约（字段、状态语义、reason_code）以 `contract_id + version + sha256` 三元组冻结，SKILL.md 里写死校验值。任何一侧漂移时 Skill 视结果为"未确认成功"。这防止了适配层和后端独立演化造成的静默语义错位——智能体平台的工具 Schema 更新往往不受我们控制，契约哈希是最后防线。

## 7. 已付学费的经验教训

### MIXED-LIQUID-001：解析边界吞事实

"喝了豆浆和白水"只记了豆浆。根因：白水扫描器把"可识别为白水"和"有可提交的 ml 数量"合并成同一条件，无数量白水在 parser 边界直接消失；后续层看到的 candidate 已经是截断的，无法发现遗漏。

教训（已固化为规则）：
1. **识别与可提交是两个独立状态**。"类别已识别但数量未知"必须显式表达（`self_unquantified_count`），而不是不产生证据。
2. **Fail-closed 分支必须覆盖"证据缺失"的输入组合**，不能只在证据完整时可达。
3. 修复方式是让 parser 返回 `needs_clarification` 零写，而不是让下游"聪明地"补救——下游没有第二次解析的权利。

### 冻结例句 → 有界语法的演进

早期 purchase parser 是整句正则匹配的冻结例句（只认"买了两箱牛奶，每箱12盒，每盒250ml"这样的精确句式）。这在验收驱动阶段是正确的——先证明链路，再泛化语法。0.1.1 阶段 2 把它替换为有界组合语法（1–64 件、整数量词、显式单位），仍拒绝开放式推断。原则：**语法的每一次放宽都必须带着"拒绝清单"**（小数、超界、歧义→澄清），否则放宽就是造数。

### 其他检验过的规则

- 并发测试必须是真 worker + 独立连接 + 启动屏障，顺序调用冒充的并发一文不值。
- 重放零写入的证明要对全部业务表做规范快照 SHA 比较，行数统计抓不到 UPDATE/DELETE。
- `Number(null) === 0`：所有 nullable 数量必须显式分支，这是 I-3 在 JS 里的具体形态。
- 测试 fixture 的营养来源要和生产权威一致，靠放宽生产校验让测试通过是禁手。

## 8. 目录职责速查

| 路径 | 职责 |
|---|---|
| `version-b-lite-plugin/src/parser/` | 原话 → candidate；纯函数，不碰数据库 |
| `src/application/` | 编排与公开 outcome；`core-runtime.ts` 是入口 |
| `src/domain/` | 业务规则、效果包、读模型 |
| `src/repository/` | 三层事务的 SQL 实现、幂等、重放 |
| `src/storage/` | 数据库生命周期、迁移、备份 |
| `src/nutrition/` | 白名单来源适配器、解析、Doctor |
| `skills/diet-manager-b/SKILL.md` | Skill 指令层（与 contract-v2 绑定） |
| `shared/contracts/`、`shared/tests/` | 跨版本契约与门禁验证器 |
| `docs/work-items/`、`docs/evidence/` | 任务台账、报告、不可变证据 |
| `releases/` | 冻结发布快照（只读） |

## 9. 0.1.1 的四个新增边界

按批准设计，0.1.1 只新增四个专责边界，其余全部复用现有分层：

1. `src/parser/correction.ts`：撤销/纠正目标的候选解析（不访问数据库）。
2. `src/repository/correction-target.ts`：认证的同会话目标定位（服务端权威）。
3. `src/repository/purchase-envelope-commit.ts`：多商品采购的单一事务边界。
4. `src/storage/portable-backup.ts`：AES-256-GCM + scrypt 便携加密备份。

设计约束：撤销目标由**服务端**解析和认证（调用方只提供引用如"刚才那条"），因为客户端提交的 event_id 可能属于别的会话；二次撤销不映射为 restore（防止 undo 语义漂移为 toggle）。
