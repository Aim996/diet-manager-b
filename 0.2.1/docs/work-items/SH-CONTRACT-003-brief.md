## 2. 目标

建立一份三路线共同消费、可机器校验的来源注册表，明确：

1. 营养资料的不可颠倒优先级和适用边界；
2. 第一批真正可用或明确禁用的来源，以及每个来源的官方依据、许可状态和使用限制；
3. 外部请求字段白名单、绝对禁止字段、日志最小化和密钥边界；
4. 来源版本、抓取时间、匹配条件、缓存键、缓存内容、失效和撤销规则；
5. 外部来源不可用、无密钥、许可不明、匹配不精确或字段缺失时的 fact-first 降级；
6. 明确数据、公共参考数据、历史档案、个人模板和逐字段推定的证据标签。

注册表只能登记经官方/第一方文档核验的网络来源。许可、接口或缓存权利不明确时必须标记为不可自动调用或待复核，不得靠推测启用。

## 3. 16 条需求逐项口径

| 需求 | 必须冻结的行为 |
| --- | --- |
| `REQ-NUTR-001` | 固定优先级：当前精确包装标签 → 生产商或精确商品资料 → 已确认同商品历史档案 → 权威公共数据库 → 白名单可信互联网 → 版本化常见菜模板 → 通用估算 → `unknown`；适用高优先级不得被低优先级覆盖。 |
| `REQ-NUTR-002` | 常见原始食材和基础食品主动使用本地已确认资料、本地可信缓存、权威数据库或可信来源，不要求用户上传标签。 |
| `REQ-NUTR-003` | 包装/精加工/高度自定义复合食品优先精确商品、生产商、标签或用户配方；精确匹配失败不得伪装为精确资料。 |
| `REQ-NUTR-004` | 普通牛奶、普通果蔬汁等通用资料不得套用到配方差异明显的加工饮料。 |
| `REQ-NUTR-005` | 无可靠资料或来源缺字段时保持 `unknown`/缺失，绝不补 0 或编造来源。 |
| `REQ-NUTR-006` | 用户明确数量、包装标签和确定性换算属于明确证据，不标“估算”。 |
| `REQ-NUTR-007` | 只有精确匹配同一商品版本时才可沿用历史 NutritionProfile，并标“沿用历史营养表”。 |
| `REQ-NUTR-008` | 已激活个人模板标“按个人模板”；模板本身不冒充公共数据库或精确标签。 |
| `REQ-NUTR-009` | 明确数量配可信公共库时，简洁回执可不标估算，但详情必须追溯为“参考数据库”。 |
| `REQ-NUTR-010` | 自然单位、可食部分、密度、出成率或通用模板的推定必须记录具体采用值、依据、来源和规则版本。 |
| `REQ-NUTR-011` | 估算证据逐字段保存；只有部分字段推定时不得给整条记录统一贴“估算”。 |
| `REQ-PRIV-001` | 外部请求采用严格 allowlist，只可含规范化食物名、品牌、变体、包装规格、生熟状态和最小类别；每个来源还能进一步收窄。 |
| `REQ-PRIV-002` | 完整原话、会话标识、饮食日期/餐次、库存数量、位置、购买地点、异常、个人模板历史和完整数据库列入 denylist，任何来源都不可放宽。 |
| `REQ-PRIV-003` | 所有外部资料必须命中生效注册项，并保存来源、来源/抓取版本、抓取时间、匹配条件、允许字段和确定性缓存键。 |
| `REQ-PRIV-004` | 默认日志只含错误码、事件 ID、规则版本和必要技术上下文；禁止完整原话、数据库转储、营养图片和密钥。 |
| `REQ-PRIV-005` | 密钥只通过运行时秘密引用；不得进入 JSONL、SQLite、fixture、日志、注册表或版本库；缺密钥只降级营养，不能阻止饮食事实。 |

## 4. JSON 最低结构

交付物必须是无注释的有效 UTF-8 JSON，并至少包含下列可校验结构；字段名可细化，但不得丢失语义：

- `schema_version`、`registry_version`、`effective_at`、`status_source`、`upstream_contract`；
- `priority_policy`：有序来源层级、适用判定、禁止降级冒充、`unknown != 0`；
- `nutrition_field_policy`：能量、蛋白质、脂肪、碳水、纤维、可选钠，以及允许的计量基准；
- `evidence_label_policy`：明确、历史沿用、个人模板、公共参考、逐字段推定；
- `external_request_policy`：全局 allowlist、denylist、每来源再收窄、无原话和生活上下文；
- `credential_policy`、`logging_policy`；
- `cache_policy`：规范化缓存键组成、内容寻址或等价完整性字段、TTL/复核时间、离线可用、不得静默改写历史；
- `failure_policy`：超时、限流、无密钥、许可不明、来源撤销、无结果、匹配不足、字段缺失；
- `sources[]`：稳定 ID、类型/优先级、状态、官方名称与官方 URL、接口/下载方式、许可依据与复核时间、允许用途、缓存/再分发边界、请求字段、匹配范围、版本策略、字段映射能力、质量限制、失败降级；
- `traceability[]`：16 条需求各且仅一次映射到 JSON Pointer 或等价稳定路径。

## 5. 来源选择规则

- `current_label`、`manufacturer_exact`、`confirmed_history`、`personal_template`、`generic_template` 和 `generic_estimate` 可以作为本地来源类别/策略项；不得虚构成统一公网 API。
- 权威公共数据库和可信互联网来源必须保存官方文档 URL 与许可/条款 URL。
- 生产商资料只允许已验证的生产商官方域名或用户提供的标签；搜索结果摘要、聚合转载页和模型记忆不是来源。
- 中国官方食物成分资料若没有可核验的开放接口与机器使用许可，应登记为 `disabled_pending_license` 或仅人工参考，不得声称已经可自动查询。
- 社区型食品数据库必须低于权威公共库和生产商精确资料，并披露自报/社区维护的数据质量限制。
- 网络抓取不得绕过登录、验证码、robots、付费墙、访问频率或条款；条款不允许缓存/再分发时必须在注册项中禁用相应能力。

## 6. 缓存、版本与匹配硬约束

- 缓存键不得包含用户、会话、日期、餐次、库存或位置；只由来源 ID/版本、规范化匹配字段、查询类别和响应语言等非个人字段确定。
- 每次采用的资料必须保留来源返回的稳定标识、来源版本或抓取时间、原始计量基准、匹配输入、匹配强度和响应完整性摘要。
- 新来源版本或缓存刷新只影响未来解析；已经提交的 NutritionSnapshot 不得静默更新。
- 精确商品复用必须至少校验品牌、规范名、变体和包装/标签版本；任一实质字段冲突时不得精确复用。
- 公共食材资料只能在食物类别、生熟/加工状态和可食部分适用时使用；加工饮料和内容不明套餐不得退化套用通用食材资料。
- 来源撤销、许可变化或完整性失败后，现有历史快照继续保留审计，但不得用于新的自动匹配，除非登记的可继续使用条件仍成立。

## 7. 失败降级

任何外部失败都不得使已发生且可识别的饮食事实失败。按可用证据顺序：本地已确认资料 → 合规且未失效缓存 → 下一个适用且已启用来源 → 有依据模板/估算 → `unknown`。每次降级必须记录稳定原因，不得把低层结果伪装成高层来源。

建议稳定原因至少覆盖：`source_unavailable`、`rate_limited`、`credential_missing`、`license_unverified`、`source_disabled`、`cache_miss`、`cache_stale`、`no_match`、`ambiguous_match`、`variant_mismatch`、`required_field_missing`、`integrity_failed`。

实施者必须提交：

3. 有效 JSON 解析、16/16 追踪、优先级、隐私白/黑名单、来源官方依据、缓存、版本、失败降级和旧行为禁用的只读检查；

独立复核至少检查：来源真实性与许可陈述、优先级适用边界、精确商品匹配、逐字段估算、隐私最小化、密钥、缓存历史一致性、失败 fact-first，以及 16 条追踪是否存在“有 ID 无语义”的空映射。

## 9. 明确禁止

- 不得把任意互联网搜索结果、摘要或模型记忆登记为可信来源。
- 不得把 Open Food Facts 等社区数据描述成生产商官方标签或权威政府数据库。
- 不得把许可未知解释为允许缓存、训练、再分发或批量抓取。
- 不得在注册表写任何真实 API key、token、用户数据、样例完整原话或业务记录。
- 不得创建或修改任何正式 JSONL/SQLite 业务数据。
- 不得提前把任务状态写成已完成；通过独立复审和证据落账后才能由主协调者更新总计划。
