# DEC-030：个人档案 + 六项目标 + 进度条

> 状态：**已批准（用户拍板 2026-08-19）** · 关联版本线 0.2.0
> 权威性：本 DEC 是对「进度条不必手动设目标、可由个人信息派生」这一用户诉求的正式决策记录。按 v1.0 §0 与路线图 §7，先写 DEC 再改方向，不静默偏离。

---

## 1. 背景与问题定位（已核实）

用户诉求分两层：

1. **「进度条的显示必须设置目标才会显示，这一部分需要优化；可以模拟身高体重然后生成进度条。」**
2. **用户进一步明确（2026-08-19 口头确认）**：进度条本质上就是「目标」；这个技能应当有一个**专门的「个人档案」存储位置**，存放一个人的身高、体重、年龄、性别，以及热量/蛋白质/脂肪/碳水/膳食纤维/饮水六项目标。每个人的目标不一样；同一人身高体重年龄能推出一套目标，但**处于减脂/增肌/维持等不同状态时目标会变**，所以这套个人信息需要有个地方存、且能随状态更新。

核实结论（证据一致）：

- 权威需求 v1.0 里**没有**「六项目标 + 进度条」。`REQ-PROGRESS-001 六项日进度` 定义的是**六个领域**的当日汇总（餐次/白水/营养/库存/购买/纠正），是 0.1.1 已实现并验收通过的 `DailyProgressView`（无目标、无进度条、无百分比）。
- 用户记忆中的「进度条」来自已归档 `archive/legacy-plans/总功能开发计划0.4.md` §17（「六项目标」= 热量/蛋白质/脂肪/碳水/膳食纤维/饮水 + 10 格进度条）。该 §17 已被归档、不具约束力。
- **存储已就绪但未接线**：`migration-v1.ts` 已建 `goal_versions` 表（`:17`）与 `daily_progress_snapshots.goal_version_id` 外键（`:18`），但**无 `set_goal`/`set_profile` 写入口、`query_daily_summary` 也不读目标**——即「schema 建了、公开动作没接」的半成品。
- PRODUCT-0.2「记录与回顾助手」在 v1.0 §1.3 标注「仅占位，本版不实现」。

因此本诉求 = 从已归档 0.4 计划召回「六项目标 + 进度条」，并新增「个人档案」存储概念，打开 0.2 版本线。

## 2. 决策

**DEC-030：新增「个人档案 + 六项目标 + 进度条」为 0.2.0 首个增量，开放 0.2 版本线。**

- 范围：个人档案（`set_profile`）+ 六项目标（`set_goal`）+ `query_daily_summary` 进度条可视化。
- 版本：0.2.0 独立候选，与已冻结/待签收的 0.1.1（candidate-008）**互不影响**。0.1.1 仍等用户提供 FDC_API_KEY 与签收后关闭阶段 4/5。
- 契约：与 DEC-031（撤销恢复）共享同一次 `contract v2 → v3` bump，避免重复多文件大改。

## 3. 对 §17.10 冲突的裁决（关键）

归档稿 §17.10：「没有确认目标 → 不生成进度条；不根据人口统计或常见推荐值自动创建目标；明确说明尚未配置目标。」

用户诉求「由个人信息派生目标」与之表面冲突。裁决如下（**派生是用户显式触发，非静默**）：

1. **`set_profile` 是用户主动提供个人信息触发的显式结果**，回执明示「参考目标（公式估算，可覆盖）」与「非医疗建议」。
2. **六项目标全部派生**（用户已明确要求「身高体重年龄也能得出一套目标」，且目标会随状态变化），公式全部采用**可检验的公开参考公式**（非 AI 编造），见 §4。
3. **状态系数**：`goal_state` ∈ `减脂 cut / 维持 maintain / 增肌 bulk`（缺省 `maintain`），改变状态即重算一套目标并落新版本。
4. **`set_goal` 可显式覆盖/清除任意子集**（六项目标均可选，置 `null` 即清除该维度目标）。手动覆盖优先于派生值。

## 4. 个人档案存储与派生公式

**专门的「个人档案」存储位置**：新增 `user_profiles` 表（用户要求的「专门个人文件指定位置」），字段：

```
profile_id / user_id / schema_version / height_cm / weight_kg / sex / age /
goal_state(cut|maintain|bulk) / effective_from / effective_to / created_at / payload_json
```

目标快照继续复用既有 `goal_versions`（追加式版本化，`effective_from/effective_to`），只读重算遵守 `REQ-PROGRESS-002`。

**六项参考目标派生公式**（单位：热量 kcal、其余 g/ml，全部 round_half_up）：

| 维度 | 公式 |
|---|---|
| 基础代谢 BMR | Mifflin-St Jeor：`10×体重kg + 6.25×身高cm − 5×年龄 + 性别项`；男 `+5`、女 `−161`、未填性别 `−78`；未填年龄默认 `30` |
| 🔥热量 | `BMR × 1.2 × 状态系数`；状态系数：维持 `1.0`、减脂 `0.85`、增肌 `1.10` |
| 🥩蛋白质 | 维持 `1.6 g/kg`；减脂/增肌 `2.0 g/kg` |
| 🧈脂肪 | `1.0 g/kg` |
| 🍚碳水 | `max(0, (热量 − 蛋白×4 − 脂肪×9) / 4)` |
| 🥦膳食纤维 | `14 g / 1000 kcal`（≈ `热量/1000 × 14`） |
| 💧饮水 | `35 ml/kg` |

所有派生值回执标注「参考目标（公式估算，可覆盖）」「非医疗建议」；可被 `set_goal` 覆盖。

## 5. 契约变更（contract v2 → v3，与 DEC-031 共享）

- **新增动作**：
  - `set_profile`：`{ height_cm, weight_kg, sex?, age?, goal_state? }` → 落 `user_profiles` + 派生六项目标落 `goal_versions`。
  - `set_goal`：六项目标任意子集（`energy_kcal` / `protein_g` / `fat_g` / `carbohydrate_g` / `fiber_g` / `water_ml`，均可选，`null` 清除）→ 落 `goal_versions`。
- **扩展 `query_daily_summary` 输出**（`DailyProgressView`）：
  - `configured_goals`：六项目标，每项 `number | null`（null = 未配置）。
  - `progress`：对每个**已配置**目标，给出 `{ current, target, percentage, filled_cells, bar_text }`；未配置维度不出现进度条，仅标注「尚未配置目标」。
- **进度条计算（对齐归档 §17.6，唯一权威渲染规则）**：
  - `percentage = round_half_up(current/target×100)`；
  - `filled_cells = clamp(round_half_up(current/target×10), 0, 10)`；
  - `bar_text = "█".repeat(filled) + "░".repeat(10−filled)`；
  - 超出目标显示真实百分比（可 >100），进度条满格。
- **固定顺序与两行格式（对齐归档 §17.5）**：`🔥热量 🥩蛋白质 🧈脂肪 🍚碳水 🥦膳食纤维 💧饮水`；每项两行 `Emoji 名称 ██████████ 103%` / `Emoji 当前量/目标 单位`。
