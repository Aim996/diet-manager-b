# 饮食管家 0.1 三版本基底设计

日期：2026-08-08  
状态：基底范围已获用户授权，完整业务设计仍待审阅

## 目的

让用户像平时说话一样描述“吃了什么”或“买了什么”。系统理解口语、检查家庭库存、选择营养资料，并将正式结果保存到唯一指定的数据源。用户不需要学习固定输入格式。

## 0.1 业务范围

正式写入事件只有两类：

1. 饮食摄入：保存实际吃下的食物；存在唯一可靠库存匹配时关联并扣减，没有可靠匹配时只记录摄入。
2. 商品入库：保存商品、数量、规格、购买日期以及用户实际提供的保质信息；不同购买批次分别保存。

支撑能力仅包括库存查询、饮食记录查询和营养资料读取。0.1 不做体重、饮水目标、菜谱、健康诊断、推荐、撤销重做或复杂报表。

## 共同原则

- 口语理解可以灵活，正式数据边界必须明确。
- 用户营养资料优先；不存在时才能使用通用估算。
- 未知营养保持未知，不能写成 0。
- 估算必须保存来源和估算标记。
- 库存存在多个相似候选时，不得自动扣减。
- 未发生、计划、假设或明确否定的摄入不得写入。
- 三个版本使用独立测试数据，不共用可写数据库。
- 三个版本使用同一批验收口语和同一评分口径。

## 三个版本

### A：纯 Skill

只使用 OpenClaw Skill 指导智能体完成分类、匹配和固定目录持久化。采用追加式 JSONL，验证纯提示词方案的能力上限及漂移风险。

### B：极简混合插件

Skill 理解口语；一个 `diet_manager` 工具负责校验、库存匹配、营养选择和 SQLite 事务。公开接口保持极小，验证最少程序约束是否足够。

### C：强约束插件

Skill 只分类和提取原始事实；插件通过显式命令、验证结果和预览/提交状态处理同样的两类事件。验证更强约束是否带来足够收益。

## 基底完成条件

- 每个版本有独立目录和说明入口。
- 每个版本有一份短小的 `SKILL.md`。
- A 明确固定 JSONL 存储边界；B、C 明确固定 SQLite 存储边界。
- B、C 有最小 OpenClaw 插件清单、TypeScript 入口和测试命令。
- B、C 使用 OpenClaw `defineToolPlugin` 原生入口；清单通过 `contracts.tools` 声明工具所有权，包通过 `openclaw.extensions` 声明编译入口。
- B、C 必须通过 OpenClaw 插件验证，不能只证明 Node 能导入普通模块。
- C 的状态边界可在类型和测试中看见，但不提前实现全部业务。
- 每个版本的结构测试可以在其目录独立运行。
- 基底文件中不出现体重、菜谱、目标、偏好等范围外业务实现。

## OpenClaw 原生插件边界

B、C 统一遵守当前 OpenClaw 工具插件契约：

- `src/index.ts` 默认导出 `defineToolPlugin(...)` 的结果。
- `openclaw.plugin.json` 包含严格空配置 Schema，并通过 `contracts.tools` 声明唯一工具。
- `package.json` 的 `openclaw.extensions` 固定指向 `./dist/index.js`。
- `typebox` 是运行时依赖，`openclaw >=2026.5.17` 是 peer dependency。
- 构建后运行 `openclaw plugins validate --root . --entry ./dist/index.js`。
