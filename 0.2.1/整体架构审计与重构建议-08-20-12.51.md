# 饮食管家整体架构审计与重构建议

- 审计时间：08-20-12.51（Asia/Shanghai）
- 审计对象：仓库主线 `version-b-lite-plugin`、Skill/OpenClaw 入口、共享契约、安装器与真实验收框架
- 审计方式：源码与依赖图只读检查，结合 01–05 真机测试和二号深度根因报告
- 边界：本文件只给出架构判断和实施顺序，不修改产品逻辑

## 一、结论

**有必要重构，但不应推倒重写。**

项目的数据可信基础是好的：SQLite 是唯一业务后端，事实、效果、回执分层，幂等、追溯、失败语义、权威营养、备份恢复和大量测试都已有真实实现。重写这些部分会丢失经过验证的不变式，风险大于收益。

需要重构的是不断累积在这些可靠基础之上的入口与编排结构：

1. 模型先选一次 action，确定性 parser 又从原话独立选一次 action，形成双重意图权威；自然口语覆盖不足时被统一包装成 `ACTION_CONFLICT`。
2. `core-runtime.ts` 同时负责运行根安全、secret 生命周期、请求校验、意图编排、查询、营养补充和公开结果，职责过多。
3. `domain/service.ts` 名为领域服务，实际直接编排 repository、storage、preview 和事务；目录名与依赖方向不一致。
4. `domain/effect-bundle.ts` 把采购、餐食、饮水、纠正、档案和目标六条垂直链放在同一文件中，已经成为五千行级变更热点。
5. 领域、仓储、存储之间存在源码级循环依赖，说明分层只存在于目录命名，没有形成可强制的边界。
6. Skill、工具 Schema、运行时契约、共享 v2/v3 文档和版本号存在多处人工同步点，已出现 0.1.1 与 0.2.0 同时作为“当前版本”的治理漂移。
7. 测试数量很多，但巨型测试文件、Windows 专用门禁混入通用套件、setup 不参与真实验收判定，使“覆盖率高”没有完全转化为“用户链路可信”。

建议把 **0.2.1 定位为结构修复版**，在关闭 P0 架构债之前暂停增加业务功能。

## 二、已验证的结构事实

### 2.1 代码规模与热点

- 主线源码：76 个 TypeScript 文件，约 35,858 行。
- 测试：67 个 TypeScript/MJS 文件，约 34,140 行，测试/源码行数约 0.95。
- 最大实现文件：
  - `src/domain/effect-bundle.ts`：5,080 行。
  - `src/domain/service.ts`：3,042 行。
  - `src/application/core-runtime.ts`：2,247 行。
  - `src/repository/fact-commit.ts`：1,819 行。
  - `src/repository/inventory-effects.ts`：1,712 行。
  - `src/repository/envelope-finalize.ts`：1,423 行。
- 最大测试文件：`vertical-slice.test.ts` 4,902 行，`fault-matrix.test.ts` 2,925 行，`pantry-purchase.test.ts` 2,560 行。

这不是单纯的文件风格问题。一个自然语言动作的修改会横跨巨型 parser、runtime、domain service、effect bundle、repository 和巨型测试，回归面难以局部判断。

### 2.2 真实依赖方向

源码依赖图发现 8 条循环依赖，核心环路集中于：

`domain/effect-bundle → repository/fact-commit → storage/inventory-repository → domain/inventory-service / domain/receipt → domain/effect-bundle`

同时存在这些反向依赖：

- domain 直接导入 repository 和 storage；
- storage 导入 application 常量；
- storage 导入 repository 的准备对象和 authority；
- repository 再导入 domain 的验证、身份和回执。

因此当前 `domain / repository / storage` 不是单向分层，而是一个互相知道实现细节的事务团块。

### 2.3 真机故障与架构的对应关系

- 01–03 的大量 `ACTION_CONFLICT` 已证明是“模型请求 action”与“parser 回退 action”不一致，不是数据库冲突。
- 04 证明模型还可能完全绕过业务工具，口头声称目标已处理，数据库却保持零写入。
- 牛奶本人识别失败来自主体词表和确认回合缺少受信上下文，不是营养数据源失败。
- 进度场景假绿来自 runner 只断言 input 阶段，不断言 setup。
- 05 的 GitHub 安装暴露开发 link、临时路径、容器持久化、跨平台测试和总超时缺少统一安装状态机。

这些问题分布在不同目录，却共享同一个结构原因：入口、权威、状态和可观测性没有集中到单一边界。

## 三、应保留的核心，不要重写

1. SQLite 单一业务后端和现有 schema/迁移纪律。
2. FactCommit → EffectBundle → EnvelopeFinalize 的业务语义。
3. 幂等记录、事件追加、撤销/恢复不覆盖历史的设计。
4. 营养来源白名单和“unknown 不等于 0”。
5. authority secret、可移植加密备份和失败回滚原则。
6. 冻结候选、哈希、SBOM 和不可变证据链。
7. parser 继续保持确定性和 fail-closed；不要把业务事实判断重新交给 LLM。

## 四、必须重构的五个边界

### P0-A：单一命令路由边界

建立 `CommandRouter`，输入只包含用户原话、宿主注入的权威元数据和可选的模型 `intent_hint`。

- 模型 action 降级为提示，不再与 parser 形成两个同等级权威。
- router 先选择 action-specific parser；每个 parser 只回答 `candidate / needs_clarification / ignored / not_applicable`。
- 明确矛盾才返回 action mismatch，并在安全诊断中记录 requested、parsed、disposition 和 reason。
- 不允许“目标 parser 没命中后静默回退 meal，再包装成冲突”。

建议目录：

```text
src/parser/
  command-router.ts
  lexicon.ts
  subject.ts
  actions/
    profile.ts
    goal.ts
    meal.ts
    water.ts
    inventory.ts
    correction.ts
```

### P0-B：权威消息上下文与澄清状态

- `conversation_id`、`source_message_id`、`received_at`、`operation_id` 必须由宿主或插件生成，不能作为 LLM 可自由编造的普通文本。
- 为需要澄清的命令保存最小、受信、可过期的 pending candidate；用户说“是我自己喝的”“对，覆盖”时，只补充上一轮明确缺失的字段。
- pending candidate 必须绑定 conversation、原消息和动作，跨会话、多候选或过期时继续拒绝。
- 不接受模型拼接的任意 `prior_context`。

### P0-C：按用例拆分应用和效果处理

把 `core-runtime.ts` 拆为：

- runtime root / secret bootstrap；
- request metadata 与输入校验；
- command router；
- 每个 action 的 handler；
- query handlers；
- nutrition supplement handler；
- public outcome mapper。

把 `effect-bundle.ts` 按现有天然分段机械拆成 `meal-effects`、`water-effects`、`inventory-effects`、`correction-effects`、`profile-effects`、`goal-effects`。第一阶段只移动代码和保留导出，不改变行为。

### P0-D：用 ports 打断 domain/repository/storage 循环

- domain 只依赖领域类型和抽象 port，不直接 import SQLite、repository 或 storage。
- application 负责事务用例编排。
- infrastructure/sqlite 实现 repository、unit of work、迁移和查询。
- repository 不再回调 domain 巨型 bundle；需要的验证器下沉为无数据库依赖的 domain policy。
- storage 不得 import application 常量；共享文件名、版本和 schema 标识移到稳定的 kernel/contracts 模块。

目标依赖方向：

```text
OpenClaw adapter → application use cases → domain policies/ports
                                      ↑
                         infrastructure/sqlite implements ports
```

### P1-E：安装、验证和发布分层

- 普通用户安装与开发 `--link` 完全分开。
- 增加跨平台 Node 安装入口；PowerShell 只保留 Windows 包装层。
- 默认验证只跑 portable/build/plugin validate/有界冒烟；全量测试显式开启。
- `test:portable`、`test:windows`、`test:integration`、`test:real-acceptance` 分开，并在 Windows/Linux CI 矩阵中分别汇报。
- real-acceptance 的每个 setup 步骤拥有自己的状态、DB 增量和 payload 断言；setup 失败时标记 `blocked_by_setup`，不得继续报 PASS。

## 五、版本与契约治理重构

当前仓库根入口仍称 0.1.1 为当前版本，package/plugin 已是 0.2.0，Skill 使用 contract-v3，而多个共享验证器和伴随契约仍写 contract-v2。建议：

1. 新增唯一机器权威 `product.manifest.json`，包含 product version、plugin version、contract id/version/hash、candidate 和支持平台。
2. package、plugin manifest、Skill 契约段、安装器版本、候选清单和测试期望全部由该 manifest 生成或验证。
3. `START-HERE.md` 与 README 只读取/引用机器权威，不再各自声明当前版本。
4. 历史 A/C 路线和冻结 source snapshot 保留，但默认搜索、测试和安装命令明确排除，避免后续智能体误入历史代码。

## 六、实施顺序

### 阶段 0：先建立安全网

1. 把 01–04 的真实自然原文加入 characterization tests。
2. 修复 setup 假绿和回复/数据库一致性断言。
3. 添加依赖环、平台分组和版本一致性门禁。
4. 暂停发布和新增功能。

### 阶段 1：修入口权威

1. 引入 CommandRouter 和 action-specific parser 结果。
2. 宿主生成消息元数据。
3. 增加受信澄清状态。
4. 在该结构上修复 profile、goal、subject、water、inventory、undo 的自然口语覆盖。

### 阶段 2：行为不变地拆巨型模块

1. 先拆 `core-runtime.ts`。
2. 再按动作拆 `effect-bundle.ts`。
3. 将 `domain/service.ts` 的事务编排移到 application/use-cases。
4. 用 ports 打断 8 条循环依赖。

### 阶段 3：整理工程与发布

1. 单一版本/契约 manifest。
2. 跨平台安装器与 CI 矩阵。
3. 拆分巨型测试文件，建立 unit/integration/e2e/real-acceptance 分层。
4. 用 01–04 做业务回归，用 05 做干净 GitHub 安装回归。

## 七、重构完成标准

- 源码依赖环为 0。
- domain 不导入 repository、storage、application 或 OpenClaw。
- 单个 action 的业务修改不需要编辑巨型总入口和无关动作测试。
- 模型不再生成权威消息标识；确认回合有后端绑定的最小上下文。
- 自然原话触发正确 action，明确他人主体仍保持零写入。
- 工具结果、SQLite 事实、用户回复和验收报告四者一致。
- setup 失败绝不显示通过。
- Linux portable 测试全绿，Windows-only 测试在 Windows 单独全绿。
- Docker 容器重建后插件与数据都仍位于持久卷。
- 0.2.1 发布前，一至四号业务回归和五号干净安装回归全部通过。

## 八、不建议做的事

- 不要整库重写或替换 SQLite。
- 不要为了自然语言通过而删除 action mismatch 安全守卫。
- 不要改成让 LLM直接提交结构化营养、库存或撤销目标。
- 不要在同一个提交中同时迁移数据库 schema、拆模块和改变业务语义。
- 不要用更多冻结例句掩盖路由设计问题。
- 不要把高测试数量当成真实验收已经可靠；先修假绿和平台分层。

## 九、最终判断

项目不是“底层不行”，而是**可靠内核被快速增长的入口与编排层包住了**。最合理的策略是保留内核、重构边界，并让 0.2.1 成为一次受 characterization tests 保护的渐进式架构整理。若继续在当前结构上直接补正则、加动作和堆验收场景，短期能修一个句式，长期会让冲突、循环依赖和发布不确定性继续扩大。
