# 二号实例 16 场景失败深度根因与修复建议

- 审计时间：2026-08-20 12:46:22 +08:00（Asia/Shanghai）
- 受测实例：OpenClaw 网关 02
- 版本：diet-manager `0.2.0`；OpenClaw `2026.7.1`；Node.js `v24.16.0`
- 审计方式：只读检查原始 session/trajectory、只读 SQLite 状态、候选包本地 parser 重放与空目录最小复现
- 边界：未修改产品源码，未重置或写入二号实例，本文不包含凭据、Gateway Token 或模型供应商配置

## 一、结论

二号的主要失败不是 SQLite 冲突，也不是已有档案或目标版本与新写入冲突，而是**模型选择的工具 `action` 与确定性 parser 从同一条自然语言推导出的 `action` 不一致**。

完整链路如下：

1. 模型能理解“设档案、设目标、喝水、入库存、撤销”等自然表达，因此以相应 `action` 调用 `diet_manager`。
2. 插件把原始 `source_text` 再交给确定性 parser；专用语法未覆盖这些日常说法时，解析流程继续落入餐食 parser。
3. 餐食 parser 多数返回 `action=record_meal, disposition=ignored, reason_code=non_self_subject`。
4. `core-runtime.ts` 检测到 `parsed.action !== request.action`，统一改写成 `failed/ACTION_CONFLICT`。
5. 该分支在数据库写入之前发生，因而错误名称容易被误读成“数据库状态冲突”。

牛奶场景是同一根因的另一种外观：模型请求本来就是 `record_meal`，没有 action 不一致，因此运行时直接返回 parser 的 `ignored/non_self_subject`，而不是 `ACTION_CONFLICT`。

此外，进度条场景存在独立的测试基础设施缺陷：设置饮水目标和记录饮水两个 setup 都已失败，但执行器只验证正式输入没有新增 `event_records`，因此场景可显示通过；实际查询仍是 `0/2275 ml`，不是期望的 `600/1200 ml`。

## 二、证据链与排除项

### 2.1 运行时分支

`version-b-lite-plugin/src/application/core-runtime.ts:1284` 先调用 `parseCoreCommand`。在 `:1290` 和 `:1308`，只要非候选结果或候选命令的 `action` 与请求 `action` 不同，就返回 `ACTION_CONFLICT`。该分支位于具体 action 的数据库执行之前。

因此本次 `ACTION_CONFLICT` 的严格含义是“模型请求 action 与 parser action 冲突”，不能据此推断为唯一键、版本或已有数据冲突。

## 三、各故障族的具体根因

### 3.1 空库 profile-set

`src/parser/profile.ts:13` 的身高模式要求字面量“身高”紧邻数值，`175高` 不匹配；入口在 `:67` 又要求文本至少包含“身高”或“体重”。首轮虽含“65公斤”，但没有“体重”二字，专用 parser 完全不介入。

即使用户说“我的身高是175，体重差不多65公斤”，现有模式也不接受“是”和“差不多”这类常见连接词，只能返回 `profile_incomplete`。补成规范句“身高175厘米，体重65公斤”后立即成功，进一步证明不是空库冲突。

### 3.2 goal-set-calorie 与 goal-clear-protein

`src/parser/goal.ts:71` 只有出现字面量“目标”才介入；设置模式在 `:49` 只接受近似“热量目标 1900”，清除模式在 `:47–48` 只接受清除词紧邻“维度+目标”。因此以下真实表达均超出语法：

- “每天热量按1900大卡算”
- “覆盖成每天1900大卡”
- “蛋白质这一栏暂时不用给我定”
- “先清掉再改成1900”这类同维度混合命令

clear-protein 还暴露对话层问题：模型没有调用工具，却用自然语言表示“未作更改”；若只看回复，不查版本增量，容易把没有执行误当作成功处理。

### 3.3 牛奶 `non_self_subject`

`src/parser/subject.ts:89` 的省略主语白名单包含“刚刚/刚”，不包含“刚才/这会儿”；`:88` 的显式“我”后修饰词包含“刚才”，不包含“这会儿”。因此：

- “刚才喝了……”省略主语路径失败；
- “这会儿喝了……”省略主语路径失败；
- “我这会儿喝了……”显式 self 路径仍失败；
- “是我自己喝的……”不以当前显式 self 结构开头，确认回合仍失败。

这也解释了为何“我刚才吃了一个香蕉”成功，而几种牛奶说法连续失败。问题是边界词表缺口，不是营养查询键缺失、离线或超时路径本身。

### 3.4 撤销与恢复链 `ACTION_CONFLICT`

`src/parser/correction.ts:7–10` 只接受高度规范的“撤销刚才那条饮食记录”“撤销记录 <id>”或少量需澄清形式；`:97` 还要求命令以“撤销”开头。“取消”“去掉”“前面鸡蛋那次算错了”等用户常用说法不会进入撤销 parser，最后回退为 meal/non-self，再触发 action mismatch。

餐食提交本身成功，证明待撤销记录确实存在；撤销在解析阶段失败，故不是找不到记录、重复撤销或生命周期冲突。

### 3.5 库存 `ACTION_CONFLICT`

`src/parser/purchase.ts:111` 的通用入口只认“（我）买了”，其余仅有少数冻结句型。“今天带回来一盒鸡蛋，先放进库存”虽然意图和数量都明确，但不满足入口，回退成 `record_meal`，再与请求的 `add_inventory` 冲突。

### 3.6 进度 setup 假绿

场景先后要求设水目标 1200 ml、记录 600 ml，两步均已失败。查询 action 在 runtime 中走只读分支，不依赖 parser 对该问句返回 candidate，所以仍能返回摘要，但实际为 `0/2275 ml`（2275 来自已有档案的派生目标）。

`shared/real-acceptance/run-real-acceptance-docker.py:357` 执行 setup，但场景的主要快照与断言围绕正式 input；对普通场景，快照在 setup 后、input 前。现有断言只看到查询没有增加 `event_records`，于是误判为通过。它验证了“查询只读”，没有验证“此前 setup 成功”或“返回进度正确”。

## 四、标识符与对话上下文审计

### 4.1 观察结果

- 每个用户回合的 `operation_id` 和 `source_message_id` 都变化；同一 session 内 `conversation_id` 保持稳定。
- 不同场景的 `conversation_id` 格式不一致：部分为 session UUID，部分为完整 session key。
- trajectory 中模型明确表示拿不到权威 source message id，随后生成时间戳形式的标识符。
- `src/openclaw/plugin.ts:226` 固定传入 `prior_context: []`，所以“对，覆盖”“是我自己喝的”这类确认回合不能通过 parser 的受信上下文恢复上一轮事实。

### 4.2 对当前失败的归因

这些标识符问题是重要的架构风险，但**不是本次 `ACTION_CONFLICT` 的直接原因**：原始请求已通过输入克隆/校验；若标识符格式非法，应得到 `INVALID_REQUEST`；而当前错误发生在 action mismatch 分支。空库复现使用全新唯一标识符仍得到相同结果。

不过，它会破坏幂等、同会话 latest-record 定位与确认回合安全性。模型不应负责制造权威审计标识符。

## 五、产品修复建议

### P0：扩展确定性 parser，但保留双重 action 校验

不要删除 `ACTION_CONFLICT` 守卫，也不要无条件信任模型传入的 action。应在以下文件扩充**有界**自然表达，并增加正反例：

1. `src/parser/profile.ts`
   - 接受“175高/175厘米高”“身高是175”“体重差不多65公斤/65公斤左右”。
   - 仍要求身高、体重二者齐全且落在保守区间，避免把餐食数量误识别成档案。

2. `src/parser/goal.ts`
   - 接受“每天热量按 N 大卡/千卡”“每天喝水按 N 毫升”。
   - 接受“蛋白质这一栏先不设/不用定/去掉”。
   - 对同一维度同时出现“清除+设置”明确规则：推荐拒绝并给出单一、可执行的澄清问题；不要让助手反复建议 parser 自己仍不支持的混合句式。

3. `src/parser/subject.ts` 与 `src/parser/predicate-frame.ts`
   - 有界加入“刚才”“这会儿”，以及“是我自己/本人喝的”确认结构。
   - 必须保留并新增“孩子/同事/家人喝了”等明确 non-self 反例；不能为了通过牛奶场景而全面放宽省略主语。

4. `src/parser/correction.ts`
   - 有界支持“刚才鸡蛋那条先取消”“前面鸡蛋那次算错了，帮我去掉”等指向最近餐食的口语。
   - 仅当同一权威 conversation 中存在唯一、active 的 latest meal 时自动绑定；多候选时继续澄清。

5. `src/parser/purchase.ts`
   - 有界支持“买回/带回来 + 明确数量/包装 + 商品 + 放进库存”。
   - 不把泛化的“带回来东西”直接入库；数量或商品不清楚时必须澄清。

6. `src/parser/parse-command.ts`
   - 增加 intent 路由回归，保证上述明确 profile/goal/water/inventory/correction 句式在 meal fallback 之前被专用 parser 接住。

### P0：补足精确回归测试

把本次二号实际原文作为 parser 和 application 两层测试，不要只保留规范句：

- `set-profile-application.test.ts`：至少覆盖“175高，65公斤”“身高是175，体重差不多65公斤”及缺一项反例。
- `core-goal-parser.test.ts`、`set-goal-application.test.ts`：覆盖“每天热量按1900大卡”“每天喝水按1200毫升”“蛋白质这一栏暂时不用定”，以及同维度清除+设置的明确策略。
- `query-goal-progress.test.ts`：使用 1200 ml setup + 600 ml 矿泉水，断言 `current=600`、`target=1200`、`percentage=50` 和 10 格进度中 5 格完成。
- correction/restore 测试：覆盖“取消/去掉”口语、同会话唯一 latest、跨会话及多候选拒绝。
- purchase 测试：覆盖“今天带回来一盒鸡蛋，先放进库存”及缺数量反例。
- subject 测试：覆盖“刚才/这会儿/我这会儿/是我自己喝的”与明确他人主体反例。

### P1：修正错误可观测性

`ACTION_CONFLICT` 对运维人员过于像数据库错误。建议保留稳定顶层 reason code，同时在安全的结构化 detail 或诊断日志中给出：

- `requested_action`
- `parsed_action`
- `parsed_disposition`
- `parsed_reason_code`

不要包含原始敏感文本。这样能直接区分 action mismatch、parser 澄清和真正的持久化冲突。

### P1：让宿主生成权威标识和上下文

`src/openclaw/plugin.ts` 应优先从 `ToolPluginExecutionContext` 或 OpenClaw session 元数据取得 `conversation_id`、`source_message_id`、`received_at`；`operation_id` 由宿主生成或基于权威消息 id 确定性派生。模型 schema 不应让这些字段成为可自由编造的普通文本。

同时不要固定 `prior_context: []`。若 SDK 可提供受信前序事实，传入经过白名单和来源校验的 context；若不可提供，则确认回合必须由插件自己的 session/DB 状态机解析，不能靠模型拼接上一轮文本。实施前需先确认当前 OpenClaw SDK 的上下文字段及生命周期。

## 六、验收基础设施修复建议

### P0：setup 失败必须阻断或显式降级

修改 `shared/real-acceptance/run-real-acceptance-docker.py`：

1. setup 每一步都声明并校验期望的工具 action、disposition/status 和关键数据库增量。
2. 任一必要 setup 失败时，正式 input 不得计为通过；标记 `blocked_by_setup`，并保留 setup 的回复、工具结果和 DB 差异。
3. 若场景验收的是整条业务链，基线快照必须在 setup 前；若只验正式 input，则 setup 仍需独立断言。
4. 查询进度不能只断言“无写入”，必须同时断言返回 payload 的目标、当前值、百分比和进度条。

### P0：自然变体生成增加 parser 契约预检

`shared/real-acceptance/generate-full-variants.py` 生成了真实自然句，但沿用了规范句的预期，未检查候选包能否识别。应增加 route matrix 或 dry-parse gate：凡预期写入的输入，必须在生成/发布时验证为正确 `action/candidate`；预期澄清的输入必须验证具体 reason code。

这项 gate 用来发现产品语法缺口，**不应把自然句自动改回规范句以求通过**。自然验收的价值正是暴露用户语言与 parser 契约之间的差距。

## 七、建议实施顺序与完成标准

1. 先补上述二号原文的失败测试，锁定现状。
2. 修 profile、goal、subject/water、correction、purchase 的有界语法；保持 action mismatch 守卫。
3. 修 setup 断言与进度 payload 断言，消除假绿。
4. 增加安全诊断 detail。
5. 研究并改造 OpenClaw 权威标识/上下文注入。
6. 在全新数据目录复跑 16 场景，再在二号测试实例复跑；要求 setup 无静默失败、所有写入均有正确 DB 增量、查询 payload 与数据库一致。

完成标准不应只看“16 个场景全绿”，还应满足：

- 自然口语触发正确的确定性 action；
- 明确他人主体仍不入账；
- 必要 setup 失败时不会显示通过；
- 工具回复、SQLite 事实和验收报告三者一致；
- 相同消息重放保持幂等，不同消息不复用 operation/source 标识；
- 撤销只作用于同一权威 conversation 内唯一、可撤销的 active 记录。
