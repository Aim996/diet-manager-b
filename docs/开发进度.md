## 1. 这个项目现在是什么

这是一个给智能体使用的饮食记录 Skill。最终形态分为两层：

1. Skill/适配层理解用户意图并调用固定业务命令；OpenClaw、Docker、MCP 或其他智能体平台都只接薄适配器。
2. B 后端保存权威数据并负责事务、幂等、库存、营养、纠正、进度、查询和回执。

目前仍是开发版本，不能安装给真实用户，也不能写真实饮食数据。底层仓储、购买入库和第一段餐食闭环已可执行，但回执、Issue 交互、纠正、饮水、Skill 指令层与安装发布仍未完成。

- 未知库、漂移库、reparse/hard-link 等身份异常在返回可写连接前拒绝。

### 3.3 B 服务端预览与状态权威（`B-MERGE-C-001`）

- 服务端创建并保存 preview，调用方不能自报状态。
- 签名 token 绑定 preview、输入 digest、主体、命令、预览内容和数据 revision。
- 同 key 完全相同请求返回原 preview；任一身份变化稳定冲突且零新写入。
- forged、stale、ghost、篡改、非法状态转换和 migration/schema 漂移都在业务写入前拒绝。
- 证据：`EV-20260812-028`。

### 3.4 B 原子 repository（`B-STOR-002`）

#### FactCommit

- 严格 prepared DTO；动态 getter、自定义原型、多余字段和非 canonical payload 在 SQL 前拒绝。
- `BEGIN IMMEDIATE` 内重新验证 migration、签名 preview 和服务器当前 repository revision。
- event、meal items、effect outbox、两次 envelope 状态转换和 idempotency checkpoint 一次提交。
- 每一个写点都有故障注入；提交前失败后完整表快照不变。
- 技术失败日志可以在回滚后单独写入，但只含阶段、稳定错误码、trace ID 和 input digest；不进入饮食表。
- 日志写入自身失败不会覆盖主错误，也不会产生业务数据。

#### EffectBundle 与库存

- 重启后可枚举 `pending/retryable_failed` 库存效果。
- 入库原子创建/校验 product、batch、inventory transaction 和唯一当前 projection。
- 扣减要求产品、批次、单位一致且数量足够，绝不写成负数。
- 库存不足时保留已提交事实，但不写 inventory transaction、不改变 projection。
- 响应丢失或并发重试从原始 transaction payload 重放，不用后来变化的当前投影伪造旧结果。

#### EnvelopeFinalize

- 只接受 effects 已稳定的预计算终态。
- finalization、envelope 终态和冻结 idempotency 结果一次提交。
- 任一写点失败只回滚最终器，不删除已提交事实/效果。
- 提交后响应丢失或后来有其他请求，仍返回原冻结结果。

#### 并发、崩溃与备份

- 真实 worker threads、独立 SQLite 连接和启动屏障，不是假并发。
- 相同事实并发：一份物理事实，两次同一权威结果。
- 同 authority 不同事实：一成功、一稳定冲突。
- 相同 effect 并发：一份 inventory mutation。
- 进程在未提交事务中退出后，重开数据库看到 0 条未提交 event。
- `quick_check`、外键检查、migration 身份和 `node:sqlite` backup 打开验证都通过。

4. 新增 `CASE-EFFECT-001` 对应故障回归：FactCommit 成功后注入营养写入失败，餐食事实保留，所有派生表为零、outbox 仍 pending、技术日志脱敏且无伪进度。
5. 新增中文食物名称回归；先复现 `DOMAIN_IDENTITY_INVALID:idempotency_key`，再改用规范摘要作为内部 ID 种子。
6. 新增操作贡献持久化断言；进度贡献现在进入 `effect_bundle_commits.payload_json` 的 `daily_progress_contribution` 效果项。
7. 新增非法自然日回归；`2026-02-31` 不再被 `Date.parse` 静默滚动到 3 月。
8. 新增营养基准与整数换算：例如每 100g 营养值按 150g 摄入换算为 1.5 倍，同时库存仍可只扣半碗；原始基准、摄入量、公式和结果同时留证。
9. 新增未知量回归：`null` 营养采用量产出未知营养，不产出伪 0；`null` 库存扣减量跳过 transaction 并生成稳定 Issue。
10. 新增旧版本兼容：旧 pending label intent 继续执行；旧 product nutrition profile 不被改写，新餐食快照仍保存本次 basis。
11. 新增严格 checkpoint/CAS：篡改 authority、漏 effect 或竞争更新都会 fail closed，不能形成“bundle 已成功、outbox 仍 pending”的半终态。
12. 新增同日累计：EffectBundle 只提交本操作贡献，EnvelopeFinalize 在写事务中形成累计快照；两餐各 100000 后，第二餐回执与查询均为 200000。
13. 新增真实跨 effect 回滚：第一项已写营养和库存后注入失败，所有派生表/projection 一起回滚，餐食事实和 pending outbox 保留。
14. 新增冻结重放：同一已完成餐食再次执行返回深冻结原结果、核对终态权威且零新行。
15. 新增进度贡献权威绑定：最终器逐项核对 bundle 与 outbox，阻止把 contribution 搬到营养或库存 effect 后伪造终态。
16. 新增乱序完成保护：请求接收时间早晚不再决定“最新”累计，较晚最终化的快照一定排在已提交快照之后。

## 5. 发现问题与处理

| 发现 | 处理 |
|---|---|
| 初版只比较 token/调用参数中的 revision，未再次计算数据库当前 revision | 在 FactCommit 事务内计算服务器当前 revision；先 RED 后 GREEN |
| 初版 repository revision 漏掉 product/batch 主数据 | 新增独立 RED；把两类权威行纳入 revision |
| 只会执行指定 outbox，不足以证明重启恢复能发现 pending work | 新增确定性 pending/retryable 枚举与 reopen 测试 |
| 故障测试只覆盖事务末尾会漏掉中间半写 | 扩展到 FactCommit 7 个、Effect 5 个、Finalize 4 个逐写点 fault matrix |
| response loss 可能错误返回后来变化的当前投影 | replay 从原 inventory transaction payload 重建原结果 |
| 测试并发可能只是顺序调用 | 使用 worker threads、独立连接和共享启动屏障 |
| 运行环境自带 Node 24.14 低于当前 OpenClaw 要求 | 最终证据使用已核 SHA 的 Node 24.15；不修改系统环境 |
| 首版餐食用例只覆盖英文名称，中文食物名进入 ASCII 幂等键后失败 | 新增中文 RED；仅食物型营养档案改用 canonical SHA-256 种子，商品档案兼容公式不变 |
| 首版 EffectBundle 终态只有效果 ID/状态，未保存本操作进度贡献 | 新增精确 RED；把冻结贡献放入 `daily_progress_contribution` 效果项 |
| JavaScript 会把 2 月 31 日自动滚动到 3 月 | 查询前先做 UTC 自然日 roundtrip 校验 |
| 最初测试种子中的商品标签来源与餐食来源不一致，触发了正确的档案冲突 | 修正测试 fixture，不放宽生产冲突检查 |
| 同一固定时钟下连续餐食会碰撞进度生成时间唯一索引 | 在同一事务内选择第一个未占用毫秒，保持确定性和唯一性 |
| 营养来源保存的是每 100g/份原始值，初版却直接当成实际摄入 | 新增 basis 字段和 BigInt `round_half_up` 换算，快照同时保存 source/converted 两组数值与公式 |
| JavaScript `Number(null)` 会把未知采用量/扣减量变成 0 | 所有 nullable 数量显式分支；营养未知保持六项 `null`，扣减未知不写 transaction |
| 来源营养六项完整但本次采用量未知时，快照覆盖状态仍会误写成 `complete` | 新增精确 RED；营养档案继续按来源完整度，餐食快照改按换算后的实际营养值计算并写成 `partial` |
| Task 3 的旧 pending intent/旧 nutrition profile 不含 basis | 使用两套精确 shape 解析而非放宽任意字段；旧档案原样保留，新档案写 basis |
| 第二餐终态回执只包含本次 contribution | EffectBundle 只写 contribution；EnvelopeFinalize 在同一事务聚合前一累计快照并发布新累计终态 |
| finalized 餐食重放直接 `JSON.parse`，对象可变且未交叉核验终态 | 重放统一调用 repository finalizer replay，核对两份终态并递归冻结 |
| 餐食 checkpoint 只比较 `data_revision`，篡改/漏更新可能制造半终态 | 精确校验 checkpoint/outbox 全集合、终态 state 与每个 UPDATE 的 `changes()===1` |
| 单项故障用例未证明前序 inventory/Issue 写入会回滚 | 新增两项目晚故障 seam；已完成第一项派生写入后失败，整包表快照和 projection 恢复 |
| 最终器只比较“任意 effect 中的 contribution”，未绑定专用进度 outbox | 新增搬移贡献篡改 RED；按唯一 operation 的 outbox 全量核对 effect ID/kind/state/exact shape，仅成功的 `daily_progress_contribution` 可携带贡献 |
| 较早接收的请求若较晚完成，累计快照时间可能倒退并被查询层隐匿 | 新增乱序 finalize RED；新快照时间至少为 `max(finalizedAt, previous.generated_at + 1ms)`，再处理唯一值碰撞 |
