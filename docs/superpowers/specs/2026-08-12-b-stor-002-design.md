# B-STOR-002 Repository Design

## Goal

Build the smallest B repository that can prove durable fact commit, exactly-once inventory effects, restart recovery and zero dietary rows on a failed write. The design consumes the B-MERGE-C-001 server preview; it does not trust a caller/model to report current state.

## Considered approaches

### A. Three explicit transaction stages — selected

Keep `FactCommit`, `EffectBundle` and later `EnvelopeFinalize` separate. Facts become durable before retryable side effects, while no terminal success is stored until all required effects become stable. This matches the frozen business contract and gives response-loss/recovery an authoritative checkpoint.

### B. One transaction for fact, inventory, nutrition, progress and receipt — rejected

It makes slow or retryable effects erase a valid user fact and cannot represent “fact saved, effects pending”. It also expands B-STOR-002 into the whole product slice.

### C. Independent transactions for every inserted row — rejected

It can leave half a meal, duplicate effects and a terminal idempotency result without its fact.

## Repository boundary

The repository accepts a strict `PreparedFactCommit` created by a future domain service. IDs, timestamps, canonical payloads and effect intentions are already resolved; the repository still validates exact DTO shape, scalar limits, uniqueness and canonical JSON before SQL.

Raw user text is retained only inside the event payload when the future domain contract explicitly supplies it. Tests use synthetic neutral content. Technical diagnostics never receive the event payload or item names.

The repository does not export an OpenClaw tool. `index.ts` remains non-writing until B-SLICE-001.

## FactCommit algorithm

1. Strictly freeze the input and secret in memory. Reject getters, symbols, custom prototypes, duplicate IDs/orders/effects, invalid hashes/timestamps/actions and noncanonical payloads before `BEGIN`.
2. Execute `BEGIN IMMEDIATE` and re-check migration identity.
3. Read the idempotency/envelope authority.
4. If state is `received/preview_ready`, verify the signed token, stored binding and request/revision inside this transaction.
5. If state is `effects_pending/facts_committed_effects_pending`, verify the same binding and reconstruct the committed result from the one authoritative event, items and outbox rows. Return it after `ROLLBACK` as an exact replay.
6. Any other state or changed identity fails closed.
7. Insert `event_records`, ordered `meal_items` and deterministic `effect_outbox` rows.
8. Compare-and-set envelope `received → facts_committed`, then `facts_committed → effects_pending`; update the idempotency row to the same nonterminal checkpoint and keep terminal result null.
9. Before commit, execute only the test-owned fault observer if present. A fault rolls back all steps.
10. `COMMIT`, then optionally execute a response observer. Response-loss simulation may throw here; retry follows step 5 and cannot duplicate data.

The stored preview payload remains immutable. Replay uses its original server binding plus the deterministic fact rows, avoiding a second authority format in the same control field.

## Failure diagnostics

`RepositoryFailureSink` is an optional synchronous boundary invoked only after a transaction has rolled back or before any transaction opened. Its frozen entry contains exactly:

- `phase`
- `error_code`
- `trace_id`
- `input_digest`

No source text, item, quantity, token, secret, database path or stack is included. Sink exceptions are swallowed so the original repository failure remains primary. A successful commit is never logged as a failure, including the deliberate post-commit response-loss observer.

## EffectBundle algorithm

Effect processing starts a new `BEGIN IMMEDIATE`, reloads the outbox row and derives its immutable effect input from the committed event/item canonical payload.

- `pending → processing` is a compare-and-set transition.
- inventory-add validates or creates the product/batch, inserts a unique inventory transaction and replaces the projection with a nonnegative canonical quantity.
- inventory-deduct reads the current projection, requires matching unit and sufficient quantity, inserts one unique transaction and writes the decreased nonnegative projection.
- success inserts one `effect_bundle_commits` marker and advances `processing → succeeded` in the same transaction.
- insufficient stock becomes `permanent_business_skip` without an inventory transaction/projection change, while the fact remains committed.
- technical failure rolls back to the previous durable outbox state; a later worker retries.

An already present commit marker is the exactly-once replay authority after response loss. A second effect application is forbidden.

## Query and recovery

Inventory queries read projection rows only, order deterministically and return frozen plain DTOs. Database reopen invokes the B-STOR-001 identity checks. Pending/retryable outbox enumeration is deterministic by `created_at, outbox_id` and does not mutate state.

Recovery does not infer commits from a technical log. SQLite rows and commit markers are the sole business authority.

## Concurrency

`BEGIN IMMEDIATE` plus the existing 5-second busy timeout serializes writers. Compare-and-set row counts and unique constraints are still checked; waiting for a lock is not treated as proof of identity. Focused worker tests open independent connections to the same test-owned database and prove one fact/effect physical result.

## Verification strategy

1. Add focused REDs before repository modules exist.
2. Prove input/getter rejection before SQL and exact first/replay/conflict table deltas.
3. Inject a failure immediately before commit and prove preview rows unchanged, every new business table count zero and one redacted outside-DB diagnostic.
4. Inject response loss immediately after commit; close/reopen and prove exact replay with one fact/outbox.
5. Race two independent connections for same and conflicting identities.
6. Build/query an inventory projection, process deduction, reject insufficient stock and reopen for stable projection.
7. Prove effect failure preserves fact and pending work.
8. Run focused tests, all B tests, TypeScript no-emit/build and database integrity checks.
9. Freeze the candidate, then use one bounded independent review; do not consume OpenClaw models during implementation loops.
