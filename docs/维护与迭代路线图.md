## 3. 解析器演进策略（最重要的长期方向）

解析器是这个产品能力上限的决定因素，也是最大的风险源。演进分三级，**每级都以上一级的测试全量保留为前提**：

1. **冻结例句**（0.1.0 的 purchase 现状）：整句正则，只认验收例句。价值：先证明链路。
2. **有界组合语法**（0.1.1 阶段 2 目标）：分段 + 词法组合，明确数字/单位/商品数上界，超界与歧义一律 `needs_clarification`。价值：覆盖日常说法，仍不猜。
3. **开放语法 + LLM 辅助结构化**（0.2 以后，需新 DEC）：若引入 LLM 做预结构化，其输出必须被当作**不可信 candidate**，逐字段过既有 parser 校验，且原话仍是唯一事实。绝不允许 LLM 输出直接落库。

每次放宽语法的 checklist：
- [ ] 新接受的句式有正向测试；
- [ ] 新拒绝清单（歧义/超界/小数/否定混入）有负向测试；
- [ ] "识别但不可提交"的中间态显式表达（MIXED-LIQUID-001 教训）；
- [ ] 混合语句（食物+水、购买+食用）的 fail-closed 分支重新审视；
- [ ] contract-v2 不变（变了就要 bump 契约与 Skill 同步）。

## 5. 维护操作手册（发布后）

### 日常健康检查

```powershell
# 从 version-b-lite-plugin 目录（PATH 需含 Node 24.15+ 与 pnpm）
pnpm run product:validate        # 全量门禁 + 保护文件扫描
```

### 备份策略

- 同根备份：`admin:backup`（SHA-256 校验，恢复失败自动回滚）——日常。
- 便携加密备份（0.1.1 阶段 3 起）：`admin:backup-portable`——换机/灾备，用户须同时保管备份文件和口令。

### 缺陷处理流程

1. 用真实环境记录复现（参照 `docs/work-items/PRODUCT-v1.0-openclaw-business-test-20260814.md` 的表格式记录法）。
2. 登记为 work-item（沿用 `XXX-NNN` 命名），写根因调查（参照 `MIXED-LIQUID-001-root-cause.md` 的结构：症状→设计期望→组件边界证据→根因→TDD RED）。
3. TDD 修复，全量回归，构建候选，走 0.1.x 发布流程。
4. **禁止**：跳过根因直接打补丁；把测试改成适配错误行为；在修复 PR 里夹带无关重构。

### 升级 OpenClaw 宿主版本时

1. 检查 `peerDependencies` 与宿主 Node 门是否仍匹配；
2. 跑 `plugin:validate`；
3. 契约哈希不变的前提下做一轮代表性业务验收（六实例表格法）；
4. 有 Schema 层变化 → 视为契约变更，bump contract 并同步 SKILL.md。

## 7. 何时应该推翻本路线图

出现以下任一情况时，先写 DEC 再改方向，不要静默偏离：

- 用户核心诉求变化（例如从"个人账本"变为"多人家庭共享"——会动 authority 模型）；
- SQLite 单机模型不再够用（并发写者、多设备同步）；
- OpenClaw 平台方向变化导致插件形态不可持续；
- 解析准确率证明有界语法路线无法满足日常使用（届时 LLM 辅助结构化提前，但落库校验层不变）。
