## 2. 使用和维护规则

### 2.1 状态词

所有任务只能使用以下四种状态：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚未产生可验证的实现成果 |
| 进行中 | 已开始实施，但尚未满足全部完成条件 |
| 阻塞 | 无法继续，且阻塞原因和解除条件已明确记录 |
| 已完成 | 交付物存在，验收条件全部满足，并记录了新鲜验证证据 |

不得用“基本完成”“差不多”“应该可用”等模糊词代替状态。

### 2.2 完成证据

任务只有同时满足以下条件才能标记为“已完成”：

- 实现文件或文档已落盘；
- 对应自动化测试通过；
- 相关上游和回归测试未失败；
- 数据写入边界符合本计划；
- 在本文件的“验证记录”中登记日期、命令和结果；
- 如果任务改变了既定规则，已经新增决策记录。

### 2.3 更新频率

- 每次开始开发前：更新“当前执行焦点”。
- 每次结束开发后：更新任务状态、下一步、阻塞项和验证记录。
- 每个里程碑结束时：完成一次范围、风险和决策复核。
- 每次修改业务契约、数据模型、存储边界或公开工具接口时：同步更新本文件。

### 2.4 变更约束

以下变更不得静默发生，必须先写入“决策记录”：

- 正式存储从 JSONL/SQLite 改为其他方案；
- 改变“未发生事件不得写入”的规则；
- 改变营养来源优先级；
- 允许多候选自动扣减库存；
- 允许库存出现负数；
- 添加 0.1 范围外的产品功能；
- 更改 A/B/C 的公开工具名称或命令集合；
- 宣布某个版本成为正式产品主线或停止维护某个版本。

## 3. 产品目标

饮食管家允许用户像平时说话一样报告“吃了什么”“买了什么”，或查询家庭库存和饮食记录。系统负责理解已发生的事实、保存用户原话、匹配库存批次、选择可追溯的营养资料，并把正式结果写入唯一指定的数据源。

### 3.1 0.1 成功状态

0.1 完成时，至少有一个版本能够稳定完成以下闭环：

1. 用户用自然语言报告已发生的购买或饮食事件。
2. 系统正确区分已发生、计划、假设、取消和否定。
3. 系统提取用户明确提供的原始事实，不臆造缺失值。
4. 需要确认时先给出预览，不提前正式写入。
5. 正式提交时原子地写入事件，并在规则允许时扣减库存。
6. 用户可以查询当前库存和历史饮食记录。
7. 营养数据具有明确来源；未知数据保持未知。
8. 重试不会造成重复写入，失败不会留下半完成事务。
9. 共同验收案例和版本专项测试全部通过。
10. 提供清晰、可重复的安装、升级、备份和恢复说明。

### 3.2 产品原则

- 自然语言入口可以灵活，正式数据边界必须严格。
- 保存事实，不把推测伪装成用户事实。
- 保存用户原话，所有推导结果必须可追溯。
- 未发生、计划、假设、取消或明确否定的事件不得写入。
- 用户营养标签优先于外部资料和通用估算。
- 未知营养值保持未知，不写成 0。
- 多个可靠库存候选存在时不得自动扣减。
- 库存不足不得静默产生负库存。
- 只有正式数据已持久化后才能返回 `committed`。
- 三个版本使用相同业务语义和验收口径，但使用独立可写测试数据。

## 5. 共同业务契约

### 5.1 意图

| 意图 | 定义 | 正式写入 |
| --- | --- | --- |
| `meal` | 用户明确报告已经发生的摄入 | 可能写入饮食，并可能扣减库存 |
| `purchase` | 用户明确报告已经发生的购买或入库 | 写入库存批次 |
| `query` | 用户要求读取库存或饮食记录 | 不写入 |
| `ignore` | 计划、假设、未发生、取消、否定或范围外内容 | 不写入 |
| `mixed` | 一句话中包含两个或更多有顺序的事件 | 按事件顺序分别处理，提交策略必须明确 |

### 5.2 原始事实

所有版本使用以下共同字段语义：

| 字段 | 要求 |
| --- | --- |
| `source_text` | 用户原话，正式事件必须保留 |
| `occurred_at_text` | 用户说出的时间原文；未提供则缺失 |
| `name` | 用户使用的原始名称，不擅自替换 |
| `quantity` | 用户明确提供的数值；未提供则缺失 |
| `unit` | 用户明确提供的自然单位；未提供则缺失 |
| `per_item_amount` | 单件规格数值，仅在用户或可靠商品资料提供时保存 |
| `per_item_unit` | 单件规格单位，与 `per_item_amount` 成对出现 |

### 5.3 营养来源

营养来源优先级固定为：

1. `user_label`
2. `trusted_external`
3. `generic_estimate`
4. `unknown`

每次营养选择必须保存：来源类型、来源标识、是否估算、适用数量、换算依据和缺失字段。估算值不得标记为用户标签；未知字段不得补 0。

### 5.4 库存匹配

| 结果 | 定义 | 扣减行为 |
| --- | --- | --- |
| `unique` | 一个可靠且单位可处理的批次 | 库存充足时允许扣减 |
| `multiple` | 多个不同的可靠候选 | 不扣减，要求确认 |
| `none` | 没有可靠候选 | 只记录饮食 |
| `insufficient` | 候选明确但数量不足 | 不产生负库存，返回预览或失败 |

### 5.5 写入结果

| 状态 | 含义 |
| --- | --- |
| `committed` | 正式事务已完整写入 |
| `preview` | 尚未写入，等待确认或一个关键事实 |
| `ignored` | 按规则不应写入 |
| `failed` | 未完成写入，必须说明原因 |

## 6. 总体技术方向

当前不预先宣布 A、B 或 C 为最终主线。三种方案按同一业务契约实现可比较的纵向切片，在决策门获得证据后再决定保留、合并或停止。

### 6.1 共同边界

- **对话层**：理解自然语言、保留原话、组织澄清问题和最终回复。
- **领域层**：实现事件、库存批次、营养来源、匹配和写入结果的共同语义。
- **存储层**：A 使用固定 JSONL；B/C 使用固定 SQLite。
- **验收层**：共同案例只描述业务期望，各版本使用独立适配器执行。
- **运维层**：安装、配置、备份、恢复、升级和诊断。

### 6.2 数据流

```text
用户原话
  -> 意图识别与事实提取
  -> 业务校验
  -> 库存候选与营养来源选择
  -> 预览或忽略
  -> 用户确认（需要时）
  -> 幂等检查
  -> 原子提交
  -> 写入证据与可解释回复
```

### 6.3 错误处理原则

- 输入缺失：返回 `preview`，只询问阻止提交的最小关键信息。
- 输入歧义：列出候选，不擅自选择。
- 存储失败：回滚并返回 `failed`，不得声称已写入。
- 重复提交：返回已有提交结果，不重复写入。
- 营养缺失：允许记录饮食，营养标记为 `unknown`。
- 库存无匹配：允许记录饮食，不扣减库存。
- 库存不足：不得出现负数；由规则决定预览或失败。
- 查询失败：不得返回过期缓存冒充新结果。

- 对数量、单位和规格不做未经确认的强制标准化。

### 9.3 A 路线专项方向

目标：验证在没有程序化业务工具的情况下，Skill 能否稳定遵守正式数据边界。

必须额外验证：

- 每行 JSON 都是完整合法对象；
- 追加过程中断不会破坏已有记录；
- Skill 不会改写或删除历史行；
- 对话漂移不会改变数据目录；
- 同样输入多次不会无控制地重复写入；
- 复杂匹配和原子扣减是否已超出纯 Skill 的可靠能力。

停止条件：如果 A 无法在共同高风险案例中稳定保证幂等、原子性或固定存储边界，则保留为只读/原型对照，不进入正式写入发布。

### 9.4 B 路线专项方向

目标：用一个最小公开工具承载所有校验、匹配、营养选择和 SQLite 事务，Skill 只负责理解口语。

必须额外验证：

- 单一工具接口是否仍然易于正确调用；
- 动作参数能否表达预览和幂等；
- 复杂度是否明显低于 C；
- 程序校验能否阻止 Skill 的错误推断进入正式数据；
- 不引入不必要的公开工具或配置项。

### 9.5 C 路线专项方向

目标：通过精确命令和显式状态转换，把预览、确认和提交约束放进插件。

必须额外验证：

- 预览状态能否跨真实对话安全保持；
- 提交令牌是否绑定输入、库存版本和用户确认；
- 非法状态跳转是否始终拒绝；
- 状态机增加的复杂度是否带来可量化的安全收益；
- 查询命令不应被不必要地强制进入写入状态机。

## 12. 非功能要求

### 12.1 安全与隐私

- 正式数据路径固定且可审计。
- 普通对话不能指定任意文件路径。
- 默认只保存完成业务所需的数据。
- 错误日志不得输出完整数据库内容。
- 测试、验证、构建与正式数据完全隔离。

### 12.2 可靠性

- 写入必须具备明确成功或失败结果。
- SQLite 事务失败必须回滚。
- JSONL 追加失败不得破坏已有行。
- 所有正式提交必须有稳定事件 ID 和幂等键。
- 查询结果不得虚构缺失数据。

### 12.3 兼容性

- 明确支持的 Windows、Node.js 和 OpenClaw 最低版本。
- TypeScript 构建产物和插件清单保持一致。
- 依赖版本变化必须重新运行插件验证和全部回归。

### 12.4 可维护性

- 领域规则不能只存在于聊天提示中而没有测试。
- 每个文件只承担清晰职责。
- 公开接口变更必须先更新契约和验收案例。
- 不为 0.1 范围外功能提前增加抽象。
