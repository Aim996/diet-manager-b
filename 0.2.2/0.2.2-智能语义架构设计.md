# 饮食管家 0.2.2：智能语义架构设计

- 版本定位：架构设计稿
- 形成日期：2026-08-20
- 来源：0.2.1 五个 Docker Agent 环境的真实 UI 测试
- 核心决策：由 Agent 大模型理解自然语言，由技能验证安全边界并执行；不再让技能用固定句式完整重猜一次用户原话

## 一、为什么需要 0.2.2

0.2.1 的底层账本、SQLite、事件追加、幂等、营养来源和备份机制仍然可靠，真正暴露问题的是自然语言入口。

真实测试中，Agent 已经能正确判断用户想“记录餐食”“记录饮水”“加入库存”或“撤销记录”，并选择相应工具动作；但技能随后又把原话交给确定性解析器重新理解。只要时间、副词、量词或口语动词不在固定规则里，技能就会返回 `non_self_subject`、`amount_ambiguous` 或 `ACTION_CONFLICT`。

这使整个系统出现了一个反常结果：前面的 Agent 有大模型，后面的技能却把它退化成关键词机器人。

0.2.2 不继续以扩大正则词表为主，而是调整 Agent 与技能之间的职责和接口。

## 二、目标与非目标

### 目标

1. Agent 负责理解用户自然表达，并输出可审计的结构化语义候选。
2. 技能负责验证候选、执行安全规则、调用现有确定性账本内核并返回真实结果。
3. 私人 Agent 中没有明确他人证据时，正常饮食表达默认属于本人。
4. 明确出现同事、家人、孩子或第三人称时，继续保持本人账本零写入。
5. 用户补充“是我吃的”“就是一根香蕉”时，能在同一会话承接上一轮未完成内容。
6. 回复、工具结果和数据库写入保持一致。

### 非目标

1. 不让大模型直接执行 SQL、选择任意记录或绕过领域规则。
2. 不让大模型编造营养数值、商品数量、时间或库存批次。
3. 不推倒重写现有事件账本、幂等、事务、备份和权威营养机制。
4. 不把所有不完整表达都自动提交；真实歧义仍应澄清。

## 三、三个方案与选择

### 方案 A：结构化语义候选 + 确定性验证（采用）

Agent 把理解结果作为结构化候选交给技能；技能逐字段验证证据和安全边界，再调用现有领域内核。

优点是既利用大模型理解口语，又保留可审计、可拒绝、可幂等的确定性写入。缺点是需要升级工具契约和多轮澄清状态。

### 方案 B：继续扩充固定句式（不采用）

继续给 parser 增加“中午扒了”“夜里啃了”“顺手吃了”等表达。

改动较小，但每修一批仍会漏掉下一批自然说法，长期不可维护。本轮五环境测试已经证明这种方式无法形成真正的泛化能力。

### 方案 C：让大模型直接写业务数据（不采用）

自然语言理解最灵活，但会扩大误记、误删、越权和造数风险，也破坏现有审计与幂等边界。

## 四、新的数据流

```text
用户自然表达
  ↓
Agent 大模型：理解意图、主体、实体、数量、时间和上下文
  ↓
语义候选 SemanticCandidate（保留原话和证据片段）
  ↓
技能语义验证网关：检查主体、证据、范围、会话和动作安全性
  ├─ 证据充分 → 调用现有领域内核
  ├─ 信息不足 → 返回最小澄清问题和 pending 引用
  ├─ 明确他人 → ignored，零写入
  └─ 候选与原话冲突 → rejected，零写入
  ↓
现有 Application / Domain / Repository / SQLite
  ↓
真实工具结果 → Agent 只按结果回复
```

确定性 parser 不再承担“完整理解任意口语”的职责。它保留三类作用：验证明确格式、验证安全拒绝条件、作为旧调用方的兼容入口。

## 五、语义候选契约

候选必须同时包含结构化字段与原话证据，不能只提交大模型结论。

```json
{
  "schema_version": "diet-manager/semantic-candidate/v1",
  "intent": "record_meal",
  "source_text": "刚下班路上啃了个苹果，晚饭还没吃",
  "conversation_ref": "host-authoritative-session",
  "subject": {
    "kind": "self",
    "basis": "private_agent_default",
    "explicit_other_spans": []
  },
  "items": [
    {
      "raw_name": "苹果",
      "normalized_hint": "apple",
      "amount": { "value": 1, "unit": "piece" },
      "evidence_span": "个苹果"
    }
  ],
  "time": {
    "kind": "relative",
    "evidence_span": "刚下班路上"
  }
}
```

### 契约要求

1. `source_text` 必须原样保留。
2. 结构化字段必须带来源片段或明确的默认依据。
3. Agent 不得提供数据库主键作为撤销权威；撤销目标仍由服务端按会话认证。
4. Agent 不得虚构宿主消息 ID、接收时间或会话 ID；这些字段只能由宿主或插件提供。
5. 数量不完整时应提交 `unknown` 或缺失字段，不能把未知换算成零或随意估算。
6. 营养数据不属于语义候选，仍由白名单来源解析。

## 六、主体规则

主体处理采用“默认本人、明确他人拒绝、真实歧义澄清”的产品口径。

### 默认本人

私人 Agent 中，以下条件同时满足时默认本人：

- 表达属于餐食、饮水、档案、目标、库存或本人查询；
- 原话没有明确他人主体；
- 没有否定、计划或假设证据；
- 结构化候选与原话的动作一致。

“刚才吃了苹果”“中午扒了两碗米饭”“夜里啃了饼干”不应仅因省略“我”而被拒绝。

### 明确他人

“我同事”“我妈”“孩子”“她”“室友”等明确他人表达必须返回 `ignored/non_self_subject`，本人账本零写入。Agent 可以进行普通回应，但不得声称已经记入本人饮食。

### 真正歧义

多人共同进食、代记需求、引用对象不明确等情况才进行澄清。澄清问题必须说明缺少哪一项，而不是笼统地要求用户重说整句话。

## 七、多轮澄清与上下文续接

技能返回澄清时，同时生成一个有界 `pending_candidate_ref`。它具备以下边界：

- 绑定同一会话、动作和原始候选；
- 只允许补齐明确缺失字段；
- 有短期过期时间；
- 跨会话、过期或存在多个候选时拒绝自动合并；
- 成功提交或用户取消后立即失效。

例如：

```text
用户：早上随手吃了根香蕉。
技能：确认是你自己吃的吗？（保留香蕉、早上、一根的候选）
用户：是我自己吃的。
技能：只补齐 subject=self，然后提交原候选。
```

不能要求用户再次完整复述，也不能把“是我自己吃的”当成一条孤立的新餐食解析。

在宿主无法提供权威入站消息 ID 时，插件使用宿主可验证的会话键与工具调用 ID 维护 pending 状态；绝不接受模型自造的权威标识。

## 八、安全验证网关

语义候选进入领域内核前必须经过以下检查：

1. **动作一致性**：Agent 选择的动作必须与候选内容一致；不一致返回专门的语义契约错误，不再统一包装成模糊的 `ACTION_CONFLICT`。
2. **主体安全**：明确他人优先于默认本人。
3. **数量安全**：明确毫升、克、件和外包装数量可提交；杯、瓶、口等容量未知时澄清，不得造数。
4. **时间安全**：可解析相对时间；缺少时间时按产品默认规则处理，不能让模型虚构精确时刻。
5. **撤销安全**：只允许撤销同一权威会话中唯一有效候选；多候选必须澄清。
6. **库存安全**：保留原始商品名、包装数量、位置和未知内含量；产品投影不得把“酸奶”“燕麦”无提示地显示为 `product`。
7. **幂等安全**：重试同一调用不重复写入，不同用户消息不得复用操作身份。

## 九、回复一致性

Agent 的最终回复必须由工具结果约束：

- `committed`：可以明确说已记录，并引用公开记录信息。
- `needs_clarification`：明确说尚未记录，只问缺失字段。
- `ignored`：说明没有写入及原因。
- `failed`：说明本次未生效，不把技术冲突解释成用户数量不清楚。

工具未调用时不得声称已经记录。工具失败后不得追加无关的身份初始化、内部维护命令或无依据营养建议。

当前 OpenClaw 插件接口不能保证直接改写模型最终回复，因此 0.2.2 通过技能指令、工具结果结构和真实 UI 三方验收共同约束；不把软提示冒充成强保证。

## 十、迁移顺序

### 阶段 1：冻结契约和红灯

- 新增 SemanticCandidate 契约与验证器测试。
- 把 0.2.1 五环境失败原话转成回归用例。
- 保留现有 action mismatch 守卫，但细分错误原因。

### 阶段 2：新增结构化入口

- OpenClaw 工具接受结构化候选。
- 旧 `source_text` parser 路径保留为兼容入口。
- 两条入口最终进入同一个领域内核，不复制写库逻辑。

### 阶段 3：主体、饮水、撤销和库存迁移

- 先迁移默认本人和明确他人。
- 再迁移明确毫升饮水与容量澄清。
- 再迁移唯一候选撤销和多候选保护。
- 最后迁移库存商品身份、包装与位置。

### 阶段 4：多轮 pending 状态

- 支持同会话补充主体、数量、时间和商品信息。
- 增加过期、跨会话、多候选和重放测试。

### 阶段 5：五环境真实验收

- 五个环境测相同能力类型、不同食物和不同口语。
- 每轮同时核对用户回复、工具结果和数据库。
- 全部通过后再移除对应旧句式分支。

## 十一、保留的旧架构资产

以下能力不因 0.2.2 改造而降低：

- 追加式事件账本；
- FactCommit / EffectBundle / EnvelopeFinalize；
- 幂等与重放；
- 未知不等于零；
- 权威营养白名单；
- 撤销追加纠正而非删除原事实；
- 数据库、密钥、备份和恢复机制。

0.2.2 改的是“自然语言怎样进入可靠内核”，不是放弃可靠内核。
